L'héritage

L'héritage est le troisième principe fondateur de la programmation objet : il classe les concepts par généralisation et spécialisation. Ce cours le présente sur le feuilleton des comptes en banque, le distingue de l'instanciation et de la composition, puis détaille le polymorphisme, la recherche dynamique des méthodes, super et les classes abstraites, avant le contre-exemple du carré et du rectangle, qui mène au principe de Liskov et au duck typing.

Le premier principe se détaille ainsi : le système est composé d'objets ; les objets interagissent en s'envoyant des messages ; l'envoi d'un message provoque l'exécution d'une méthode dans le contexte de l'objet receveur ; tous les objets sont instances d'une classe. Tous les langages à objets sont fondés sur ces trois principes ; les deux premiers ont fait l'objet du cours 1, ce cours est consacré au troisième.

Principe 1 : objets et messages

Un objet = une identité + un état + un comportement. En réponse à un message, l'objet destinataire déclenche un comportement (une méthode, ou fonction membre).

Principe 2 : classes et instances

Une classe est un moule pour fabriquer des objets. Elle regroupe ce qui est commun aux objets d'un même type et définit leurs attributs. Toutes ses instances répondent au même ensemble de messages, par les mêmes méthodes, et ont les mêmes champs : seules les valeurs de ces champs les distinguent.

Le principe de l'héritage p. 4

Avec l'héritage, on se centre davantage sur les classes, c'est-à-dire sur ce qui peut être commun (et donc aussi ce qui est différent) aux objets de classes distinctes.

Définition Héritage

L'héritage (inheritance) est un mécanisme qui permet de regrouper dans une superclasse ce qui est commun à plusieurs classes, appelées sous-classes.

Ce cours présente ce principe de classement des classes : en quoi les sous-classes diffèrent de leur superclasse, et comment l'héritage modifie l'association des méthodes aux messages.

Classification des composants p. 4

L'héritage s'intéresse aux composants qui sont de même nature, mais qui diffèrent quelque peu. Les différences peuvent être :

  • externes : ces composants répondent soit à des messages différents, soit différemment à des messages identiques ;
  • internes : ces composants ont des structures différentes.

L'héritage est donc un moyen, parmi d'autres, d'organiser l'ensemble des classes, en regroupant celles qui ont un certain type de propriétés en commun : la structure de leur état, leur comportement.

Généralisation et spécialisation p. 5

Une classe modélise un concept abstrait, un type utilisateur. On classe les concepts (ou les types) par une relation de généralisation et de spécialisation ; l'héritage en est une représentation partielle.

Définition Spécialisation

Soient A et B deux classes. B est une spécialisation de A si et seulement si tous les champs et tous les comportements des objets de A se retrouvent dans les objets de B. A est alors une généralisation de B.

Les différences possibles p. 5

Les instances de B ont les mêmes caractéristiques que celles de A. Les seules différences possibles : par rapport à celles de la superclasse A, toutes les instances d'une sous-classe B peuvent éventuellement…

Le feuilleton des comptes en banque p. 6–9

Le fil rouge du cours est une banque. Tous les comptes ont des points communs, et certains offrent des services de plus : c'est la situation type de l'héritage.

Une classe de base, deux sous-classes p. 6–7

Un compte connaît son titulaire, son solde et son numéro. Il est capable de retourner son solde, de déposer une somme, de retirer une somme, de retourner le seuil minimum de retrait et d'afficher ce qu'il connaît. Certains types de comptes fournissent des services supplémentaires : autoriser des découverts (CompteCourant), rapporter des intérêts (CompteEpargne).

Le code de Compte p. 7–8

Les méthodes de Compte ; sa création, son initialisation et ses accesseurs ont été vus au cours 2 :

class Compte
  # ... (création, initialisation, accesseurs : voir le cours 2)
  # Les méthodes qui suivent sont publiques (font partie de l'interface)
  #  puisqu'on ne précise rien de particulier.
  # Pour déposer une somme, on incrémente la variable d'instance @solde
  def depose (uneSomme)
    @solde += uneSomme
  end
  # Pour retirer une somme, on décrémente la variable d'instance @solde si le
  #  seuil de retrait n'est pas atteint
  def retire (uneSomme)
    puts("\# Le solde est #{@solde}, Vous retirez : #{uneSomme}");
    if @solde - uneSomme > seuil()
      @solde -= uneSomme
      puts("\# \tOk pour le retrait de #{uneSomme} Nouveau Solde = #{@solde}");
    else
      puts("\# \t\tPlus de Sous je ne retire rien, votre solde est : #{@solde}");
    end
  end
  # La méthode seuil ci-dessous n'a pas à être publique, on ne veut pas qu'elle
  #  soit utilisée à l'extérieur de la classe
  # Le seuil de retrait est 0 (pas de découvert autorisé)
  private def seuil ()
    puts "#\tJe suis la méthode seuil de Compte"
    return 0
  end
end

Placé devant def, le mot-clé private rend la méthode seuil privée : elle ne fait pas partie de l'interface et ne peut être appelée que de l'intérieur de l'objet, sans receveur explicite, comme le fait retire. Les sous-classes en héritent néanmoins, et peuvent la redéfinir.

Ajout Appelée de l'extérieur, marignan.seuil lève une erreur, que Ruby 3.4 formule private method 'seuil' called for an instance of Compte.

Le code des sous-classes p. 8–9

En Ruby, la superclasse se déclare avec < dans l'en-tête de la classe.

class CompteCourant < Compte
  # Une variable d'instance supplémentaire
  # @decouvert    Précise le découvert autorisé sur le compte
  # Génération des méthodes decouvert et decouvert=
  attr_accessor :decouvert
  # Pour ouvrir un compte, on ne peut utiliser que la méthode de classe ouvrir avec 4 arguments
  def CompteCourant.ouvrir (unNombre, unNom, uneSomme, unDecouvert)
    new(unNombre, unNom, uneSomme, unDecouvert)
  end
  # La méthode d'initialisation d'un compteCourant à 4 arguments
  def initialize(unNombre, unNom, uneSomme, unDecouvert)
    # On réutilise en le rappelant le code déjà écrit dans la classe de base
    super(unNombre, unNom, uneSomme)
    @decouvert = unDecouvert
  end
  # Le seuil de retrait est - découvert autorisé
  # Méthode privée redéfinie de la classe Compte
  private def seuil ()
    puts "Je suis la méthode seuil de CompteCourant"
    return -@decouvert
  end
end

Définition Redéfinition

On dit que CompteCourant redéfinit (override) la méthode seuil de Compte.

  • attr_accessor :decouvert génère l'accesseur en lecture decouvert et l'accesseur en écriture decouvert=.
  • CompteCourant.ouvrir est une méthode de classe : elle appelle new, qui crée l'objet puis lui envoie initialize avec les mêmes arguments.
  • initialize confie à super l'initialisation des trois champs hérités (c'est l'initialize de Compte qui s'exécute), puis initialise le seul champ propre à la sous-classe.
class CompteEpargne < Compte
  # Une variable d'instance supplémentaire
  # @taux     Précise le taux de rémunération
  # Génération des méthodes taux et taux=
  attr :taux, true
  # Pour ouvrir un compte, on ne peut utiliser que la
  #  méthode de classe ouvrir avec 4 arguments
  def CompteEpargne.ouvrir (unNombre, unNom, uneSomme, unTaux)
    new(unNombre, unNom, uneSomme, unTaux)
  end
  # La méthode d'initialisation d'un compte à 4 arguments
  def initialize(unNombre, unNom, uneSomme, unTaux)
    # On réutilise en le rappelant le code déjà écrit
    # dans la classe de base
    super(unNombre, unNom, uneSomme)
    @taux = unTaux
  end
  # La méthode qui verse les intérêts
  def verseToiTesInterets()
    @solde += (@solde * @taux/100) / 12
    # self.depose((@solde * @taux/100) / 12)
  end
end

Remarque attr :taux, true

Cette forme ancienne, qui génère taux et taux=, est obsolète : dans les versions actuelles de Ruby, on écrit attr_accessor :taux. La ligne en commentaire de verseToiTesInterets montre l'autre façon de faire : réutiliser la méthode depose plutôt que de modifier @solde directement.

Ajout Ruby 3.4 l'accepte encore, sans avertissement, et crée bien les deux méthodes ; attr_accessor reste la forme à employer.

Héritage, instanciation, composition p. 9–11

Une sous-classe n'est pas une instance de sa superclasse, et un objet n'hérite pas de sa classe : les deux liens sont de nature différente. Et l'héritage ne sert pas non plus à dire qu'un objet en contient un autre.

Distinguer héritage et instanciation p. 10–11

Le lien d'héritage, entre classes

  • Un CompteCourant est une sorte de Compte (lien a kind of) : lien de spécialisation entre deux concepts abstraits.
  • CompteCourant est un sous-type de Compte : lien de sous-typage.
  • L'ensemble des CompteCourant est un sous-ensemble de l'ensemble des Compte : lien d'inclusion ensembliste.

Le lien d'instanciation, entre une classe et un objet

Le compte tapie :

  • est un exemple de CompteCourant : lien de représentation entre un objet concret et un concept abstrait ;
  • est une variable du type CompteCourant : lien entre une variable et son type ;
  • appartient à l'ensemble des CompteCourant : lien d'appartenance entre un élément et un ensemble.

À vérifier Le support introduit cette liste par « Le compte de Després », alors qu'aucun compte de ce nom n'apparaît dans la figure : il s'agit sans doute d'un exemple des diapos d'origine. La liste vaut pour tout CompteCourant, comme celui de Tapie, retenu ici.

Règle n° 1 : « est-un », jamais « a-un » p. 11

Règle n° 1 À se rappeler jusqu'à la fin de ses jours

L'héritage (simple) modélise une relation « est-un » (inclusion, sous-ensemble, sous-type). L'héritage ne modélise jamais « a-un » ou « est-composé-de », ni « est-implémenté-en-termes-de ».

Il faut donc distinguer la relation d'héritage et la relation de composition. Les classes sont organisées en un graphe (un arbre) d'héritage.

Exercice 1 Héritage ou composition ? Ajout

  • Un cercle a un centre : composition, un champ @centre qui contient un Point.
  • Une pile est implémentée en termes de tableau : composition. Si Pile héritait d'Array, elle hériterait aussi de insert, shift, []=…, qui permettent de toucher au milieu de la pile, ce qu'une pile ne doit pas permettre.

Le polymorphisme p. 12–14

Le polymorphisme, déjà rencontré au cours 1, revient ici, car l'héritage en fournit une forme essentielle : la redéfinition.

Définition et trois types p. 12

Définition Polymorphisme

Le polymorphisme (polymorphism) est la capacité, pour des objets de classes différentes, de répondre au même message (ou appel de méthode) de manières spécifiques à leur type.

Cela permet de fournir une interface unique à des entités de types différents, c'est-à-dire d'implémenter le même comportement de différentes manières dans des classes distinctes, et de traiter des objets de types différents comme s'ils étaient du même type. C'est un concept très important en programmation, et particulièrement en programmation objet. Du grec poly (plusieurs) et morphos (formes), il signifie qu'un même nom représente plusieurs choses selon le contexte.

Le polymorphisme fait intervenir la notion de type. Pourtant, les langages objets non typés statiquement, comme Smalltalk ou Ruby, autorisent les deux premiers types ; le polymorphisme paramétrique est propre aux langages typés statiquement, comme C++ et Java.

Polymorphisme ad hoc : la surcharge p. 12–14

Le polymorphisme ad hoc est la possibilité, pour deux classes indépendantes, d'avoir des méthodes de même nom : on dit que l'on surcharge une méthode. Par exemple, l'opérateur + est polymorphe : on peut l'utiliser pour un entier, un tableau, une chaîne… Extraits de la documentation de Ruby (2.5.3) :

Java et C++ réalisent le polymorphisme ad hoc par la surcharge : un même nom désigne différentes fonctions dans une même portée, et le compilateur choisit la fonction à appliquer selon le type des arguments.

static int    max(int a, int b)       { return a > b ? a : b; }
static double max(double a, double b) { return a > b ? a : b; }
max(3, 4);       // appelle la première version
max(3.0, 4.5);   // appelle la seconde

En Ruby, les paramètres des méthodes n'ont pas de type : il n'y a donc pas de surcharge à proprement parler, mais des méthodes à nombre variable d'arguments et des arguments par défaut. L'exemple suivant simule la surcharge avec une liste de paramètres : *args regroupe tous les arguments dans un tableau.

#  Illustration par l'utilisation d'une liste de paramètres
class Test
  def Test.creer(*args)
    new(*args)
  end
  def initialize(*arguments)
    for index in 0...arguments.size
      instance_variable_set("@maVi#{index}".intern, arguments[index])
    end
  end
end

Polymorphisme d'héritage : la redéfinition p. 14

Le polymorphisme d'héritage est la possibilité, pour une sous-classe, de redéfinir le code d'une méthode héritée. Exemples en Ruby :

  • la méthode to_s() est définie dans Object et peut être redéfinie dans les classes ; elle est en particulier utilisée par les instructions d'affichage (section 7) ;
  • la méthode seuil() des classes Compte et CompteCourant.

Programmer avec l'héritage : recherche des méthodes et super p. 14–21

Écrire une sous-classe, c'est ne décrire que ce qui change. Reste à comprendre ce que l'interprète en fait : quels champs possède une instance, et quelle méthode s'exécute en réponse à un message.

Raffinements successifs et factorisation p. 14–15

L'héritage est une technique de développement par raffinements successifs, en partant des classes les plus générales, assez simples, pour arriver à des classes spécialisées complexes. Pour définir une sous-classe, on se borne à définir les champs et comportements supplémentaires, et les comportements qui diffèrent. Sa réalisation informatique repose sur deux mécanismes : l'héritage statique des champs et l'héritage dynamique des procédures qui sont amenées à différer.

On peut aussi procéder dans l'autre sens, par factorisation du code : on commence par développer des classes distinctes, on s'aperçoit que l'on duplique du code, et l'on crée alors une superclasse commune pour factoriser le code commun.

Attention Horreur !!! Le code dupliqué

Deux copies d'un même code, ce sont deux endroits à corriger à chaque modification, et tôt ou tard deux versions qui divergent. La superclasse commune supprime la duplication.

Héritage statique des champs p. 15

Tous les champs de la (des) superclasse(s) sont ajoutés à ceux qui sont déclarés dans la classe héritière : une instance possède physiquement tous les champs de sa classe et de ses superclasses. Par exemple, un CompteCourant possède un numéro, un solde et un titulaire (champs hérités de Compte), et un découvert autorisé (champ propre à CompteCourant).

Attention !!! Chacun ses variables

Une classe est responsable de l'initialisation de ses variables d'instance, pas de celles de sa superclasse.

Remarque Les champs en Ruby

En Ruby, les variables d'instance ne sont pas déclarées : elles naissent à leur première affectation. Un CompteCourant possède @numero, @solde et @titulaire parce que l'initialize de Compte, appelé par super, les affecte. D'où l'importance de cet appel.

Héritage dynamique des méthodes p. 15–16

Les textes des procédures d'une superclasse sont partagés par tous les objets de la classe et de ses sous-classes : c'est la factorisation du code. La procédure à exécuter est recherchée en remontant dans le graphe d'héritage, de la classe de l'objet receveur vers ses superclasses. À la réception d'un message, quatre cas se présentent :

À retenir Factoriser du code

L'héritage est un moyen de « factoriser du code » : les méthodes communes à toutes les sous-classes sont définies une fois et une seule dans la superclasse.

Méthode redéfinie et liaison dynamique p. 16–19

Reprenons une version courte des deux classes, où seuil est publique :

def retire(uneSomme)
  if @solde - uneSomme > self.seuil
    @solde -= uneSomme
  else
    print "\# Plus de Sous \n"
  end
end

def seuil ()
  return 0
end
def seuil ()
  return -self.decouvert()
end

Soit un CompteCourant, celui de Tapie. Le message retire(2000) provoque la recherche de la procédure retire : d'abord dans la classe de l'objet, CompteCourant, où elle est absente ; puis dans sa superclasse Compte, où elle est : jusque-là, pas de problème, cette méthode est exécutée. Mais elle appelle la méthode seuil… laquelle ? Le seuil de Compte, ou celui de CompteCourant ?

  1. tapie reçoit le message retire(2000).
  2. retire est cherchée dans CompteCourant, la classe du receveur : absente.
  3. On remonte dans Compte : trouvée. Elle s'exécute dans le contexte du receveur (self est toujours tapie).
  4. retire envoie seuil à self : la recherche repart de la classe du receveur, CompteCourant.
  5. seuil y est redéfinie : c'est elle qui s'exécute et retourne -decouvert. Le seuil de Compte n'est pas utilisé.

Exemple Les retraits, exécutés Ajout

Avec la version longue du code (section 2.2), où chaque seuil se présente, trois retraits : 500 sur le compte de Marignan, 2000 sur celui de Tapie, et 250 sur un compte courant de 100 avec 300 de découvert autorisé.

Liaison statique et liaison dynamique p. 18

Dans un langage compilé, par défaut, lors de la compilation des méthodes de la classe Compte, c'est le code de seuil de Compte qui est lié au nom seuil dans la méthode retire : c'est une liaison statique. Pour que, à la réception de retire par un CompteCourant, ce soit le seuil de CompteCourant qui s'applique, il faut lier le nom de la méthode à son code au moment de l'exécution, d'après la classe du receveur : c'est une liaison retardée (late binding) ou liaison dynamique (dynamic binding).

Si une classe définit une procédure de même nom qu'une procédure d'une classe mère, on dit que la procédure héritée est redéfinie (to override : supplanter, outrepasser) : c'est le polymorphisme d'héritage. Il nécessite une liaison dynamique : le lien entre le nom du message et la procédure à invoquer doit être établi à l'exécution, et non à la compilation.

À retenir Liaison retardée

Dès qu'une méthode d'une classe mère est susceptible d'être redéfinie par une classe héritière, le code de la procédure associée au message doit être lié dynamiquement, à l'exécution et non à la compilation. Un langage qui supporte l'héritage comporte un mécanisme de liaison retardée. Contrairement à Java et C++, en Ruby comme en Smalltalk, la liaison du nom de la procédure avec le code a toujours lieu à l'exécution.

Remarque Java et C++

En C++, seules les méthodes déclarées virtual sont liées dynamiquement. En Java, toutes les méthodes d'instance le sont, sauf les méthodes private, static et final, liées à la compilation.

Méthode Détermination de la méthode à appliquer

Quand un message est reçu, l'interprète cherche dans la classe du receveur une méthode de même sélecteur :

  1. s'il la trouve, il l'exécute ;
  2. sinon, il cherche dans la superclasse du receveur ;
  3. et ainsi de suite en remontant dans l'arbre d'héritage, jusqu'à ce qu'il en trouve une, qui est alors appliquée, ou qu'il n'en trouve aucune : il envoie alors le message d'erreur à l'objet receveur, ce qui déclenche une erreur d'exécution.
CompteCourant.superclass   #=> Compte
CompteCourant.ancestors    #=> [CompteCourant, Compte, Object, Kernel, BasicObject]

Ajout ancestors donne exactement l'ordre de la recherche ; Ruby 3.4 renvoie bien cette liste. Kernel n'est pas une classe mais un module, inclus dans Object : c'est lui qui fournit puts, print ou p.

En Ruby, envoyer à un objet un message qui n'appartient pas à l'interface de sa classe provoque une erreur d'exécution. Ce qui explique que Ruby soit un langage idéal pour le prototypage, mais pas pour le génie logiciel, où l'on préfère détecter les erreurs à la compilation, donc les langages fortement typés ; or ceux-ci s'accommodent mal de l'héritage, qui viole le contrôle de type. Toujours des compromis à faire.

Exercice 2 Quelle méthode s'exécute ? Ajout

Qu'affiche ce programme ?

class A
  def m
    "A#m appelle #{n}"
  end
  def n
    "A#n"
  end
end
class B < A
  def n
    "B#n"
  end
end
class C < B
  def m
    "C#m, puis " + super
  end
end

puts B.new.m
puts C.new.m
Indice

Chaque envoi de message, même écrit dans le code d'une superclasse, repart de la classe du receveur ; super, lui, repart de la superclasse de la classe où il est écrit.

Solution proposée 
$ ruby exo.rb
A#m appelle A#n
A#m appelle B#n
C#m, puis A#m appelle B#n

Pour B.new.m, m est trouvée dans A, mais le message n qu'elle envoie à self repart de B, la classe du receveur : c'est B#n. Pour C.new.m, C#m s'exécute, puis super cherche m à partir de B, la superclasse de C : il trouve A#m, qui envoie n à self, toujours l'instance de C ; la recherche part de C et trouve B#n.

Réutiliser sans dupliquer : super p. 19

Lors de la redéfinition d'une méthode, le code de la méthode de la classe mère ne doit pas être dupliqué, quelle que soit sa longueur : la méthode redéfinie doit, si besoin, réutiliser le code de la méthode de la classe mère. En Ruby, on utilise pour cela le mot-clé super, qui fait référence à la méthode de même nom dans la classe de base. Dans d'autres langages, l'écriture est différente (super.toString() en Java, Compte::toString() en C++), mais le principe est le même.

Définition La pseudo-variable super

super est une pseudo-variable qui permet de faire référence à une méthode de même nom définie dans la classe supérieure (mère). Plus précisément, la recherche commence dans la superclasse de la classe où est écrite la méthode qui contient super.

Remarque Les arguments de super

  • super seul transmet à la méthode de la superclasse les mêmes arguments que ceux reçus ;
  • super() n'en transmet aucun ;
  • super(a, b) transmet exactement a et b, comme dans l'initialize de CompteCourant.

Exemple et règles d'utilisation de super p. 19–20

Pour afficher un CompteCourant, on utilise le to_s de Compte pour les champs hérités, puis on traite les champs propres à la sous-classe. La méthode to_s() de CompteCourant redéfinit celle héritée de Compte, mais en la complétant, par un appel de la méthode héritée : on dit qu'elle la spécialise.

#On complète la méthode de conversion
def to_s()
  super + "#\tDécouvert Autorisé : #{@decouvert}\n"
end
#On complète la méthode de conversion
def to_s
  super + "#\tTaux d'intérêts : #{@taux}\n"
end

Ajout Avec le to_s de Compte reconstitué (section 2.3), puts tapie et puts charlemagne affichent, après le versement des intérêts :

#	CompteCourant N°2345
#	Titulaire : Tapie
#	Solde : -3000000000
#	Découvert Autorisé : 3000000000
#	CompteEpargne N°800
#	Titulaire : Charlemagne
#	Solde : 5018.75
#	Taux d'intérêts : 4.5

Règles Conception objet (à retenir)

  • Règle n° 1 : super est utilisée pour redéfinir une méthode dans une sous-classe en spécialisant la méthode héritée, tout en réutilisant le code déjà écrit.
  • Règle n° 2 : l'emploi de super prévient le lecteur du programme que la classe se décharge d'une part de sa responsabilité en déléguant à l'une de ses superclasses.

Idée directrice : toujours déléguer le travail à la classe compétente. En particulier, une sous-classe délègue à sa superclasse le traitement des champs hérités (par exemple l'initialisation), et ne se charge que de ce qui la regarde : le traitement des champs propres.

Retour sur le codage des comptes p. 20–21

Dans CompteCourant comme dans CompteEpargne, l'initialisation et la conversion en chaîne délèguent donc à Compte ce qui concerne les champs hérités, comme dans le code des sections 2.3 et 5.6. Et surtout pas une conversion qui recopie celle de Compte, ni une initialisation qui affecte elle-même les champs hérités :

def to_s()
  "#\t#{self.class} N°#{@numero}\n" +
  "#\tTitulaire : #{@titulaire}\n#\tSolde : #{@solde}\n" +
  "#\tDécouvert Autorisé : #{@decouvert}\n"
end
def initialize(unNombre, unNom, uneSomme, unDecouvert)
  @numero, @titulaire, @solde = unNombre, unNom, uneSomme
  @decouvert = unDecouvert
end

Attention Licenciement immédiat

Ces deux versions dupliquent le code de Compte : la première recopie son affichage, la seconde prend en charge l'initialisation de champs qui ne sont pas les siens. La moindre modification de Compte (un champ de plus, un format d'affichage différent) les rendrait fausses.

Classes abstraites et hiérarchie des classes Ruby p. 21–24

En haut d'une hiérarchie se trouvent souvent des classes trop générales pour avoir des instances : elles rassemblent ce que leurs sous-classes ont en commun. La bibliothèque de Ruby en offre de nombreux exemples.

Classe abstraite et classe concrète p. 21–22

Une classe peut être une description partielle mais générale d'objets dont les détails seront spécifiés plus tard, par héritage. Une telle classe déclare des champs et des comportements communs à plusieurs classes, la définition précise des comportements étant de la responsabilité des sous-classes.

Définition Classe abstraite, classe concrète

Une classe abstraite (abstract class) est une classe définie pour être sous-classée, pas pour être instanciée. Elle n'a pas d'instance, mais est la racine d'une hiérarchie d'héritage ; elle ne définit pas (ou pas tous) les comportements des objets qu'elle décrit.

Une classe concrète est une classe qui a des instances, et où sont définis tous les comportements des objets qu'elle décrit.

Exemples de classes abstraites
Classe abstraiteClasses concrètes
figure géométriquecercle, rectangle
touche d'une calculatricetouches numériques, touches fonction, touches opérations binaires, opérations unaires, touches spéciales
Compte (on pourrait aussi le considérer ainsi)CompteCourant, CompteEpargne

Souvent, une classe abstraite n'a pas d'attributs, mais définit un ensemble d'opérations communes à toute la hiérarchie : elle fournit une interface commune sans exposer la réalisation.

Complément Une classe abstraite en Ruby

Ruby n'a pas de mot-clé abstract (Java en a un). Par convention, la classe abstraite déclare la méthode et lève NotImplementedError : chaque sous-classe concrète doit la redéfinir.

class Figure                       # abstraite : jamais instanciée
  def surface
    raise NotImplementedError, "#{self.class} doit définir surface"
  end
  def to_s                         # comportement commun, écrit une seule fois
    "#{self.class} de surface #{surface}"
  end
end
class Cercle < Figure
  def initialize(rayon)
    @rayon = rayon
  end
  def surface
    Math::PI * @rayon ** 2
  end
end
class Rectangle < Figure
  def initialize(largeur, longueur)
    @largeur, @longueur = largeur, longueur
  end
  def surface
    @largeur * @longueur
  end
end
puts Cercle.new(1)          # Cercle de surface 3.141592653589793
puts Rectangle.new(2, 3)    # Rectangle de surface 6

to_s, écrite une seule fois dans Figure, envoie surface à self : grâce à la liaison dynamique, c'est la version de la sous-classe du receveur qui s'exécute. Ajout Les deux sorties sont confirmées ; et puts Figure.new échoue bien : Figure doit définir surface. Rien n'empêche pourtant d'écrire Figure.new : en Ruby, l'abstraction n'est qu'une convention.

Exemple : chansons et karaoké p. 25–27

Un exemple complet montre comment une méthode héritée de Object, to_s, se redéfinit, puis se spécialise dans une sous-classe sans dupliquer de code.

La classe Chanson et son affichage p. 25

class Chanson
  def initialize(nom, artiste, duree)
    @nom     = nom
    @artiste = artiste
    @duree   = duree
  end
end
uneChanson = Chanson.new("Wish You Were Here", "Pink Floyd", 340)
# La méthode inspect permet d'afficher des informations sur les objets
print uneChanson.inspect, "\n"
# Que se passe-t-il lors de l'appel de
print uneChanson, "\n"
#<Chanson:0x2777918 @nom="Wish You Were Here", @artiste="Pink Floyd", @duree=340>
#<Chanson:0x2777918>

Redéfinir to_s p. 25–26

print utilise la représentation de l'objet sous forme de chaîne, et l'affiche. Cette représentation est donnée par la méthode to_s de l'objet : print uneChanson, c'est comme si l'on avait écrit print uneChanson.to_s(). to_s est appelée automatiquement par les méthodes d'affichage ; son comportement par défaut, celui de Object, est de renvoyer le nom de la classe suivi d'un nombre « représentant » l'adresse en mémoire. Pour obtenir un affichage convenable, il suffit donc de redéfinir to_s :

class Chanson
  def to_s
    "#  Chanson : #{@nom}--#{@artiste} (#{@duree})"
  end
end
print uneChanson, "\n"
#  Chanson : Wish You Were Here--Pink Floyd (340)

Rouvrir la classe (voir l'ouverture des classes au cours 2) suffit : la nouvelle to_s de Chanson redéfinit celle héritée de Object.

Une classe dérivée : ChansonKaraoke p. 26

class ChansonKaraoke < Chanson
  def initialize(nom, artiste, duree, texte)
    super(nom, artiste, duree)
    @paroles = texte
  end
end
autreChanson = ChansonKaraoke.new("My Way", "Sinatra", 225, "And now, the...")
print autreChanson, "\n"
#  Chanson : My Way--Sinatra (225)

Évidemment, cela n'affiche pas les paroles, puisque la méthode to_s utilisée est celle de Chanson, qui ne gère pas les paroles. Il faut donc la redéfinir.

Redéfinir to_s dans la sous-classe p. 26–27

Solution 1 : tout redéfinir.

class ChansonKaraoke
  def to_s
    "#  ChansonKaraoke : #{@nom}--#{@artiste} (#{@duree}) [#{@paroles}]"
  end
end
# Maintenant cela marche
print autreChanson, "\n"
#  ChansonKaraoke : My Way--Sinatra (225) [And now, the...]

Solution 2 : utiliser super. La solution 1 n'est pas bonne : on ne tire pas parti de l'héritage. Il faut réutiliser ce qui est déjà écrit dans la classe supérieure, en concaténant (+) la chaîne produite par le to_s de la classe supérieure avec les paroles :

class ChansonKaraoke
  def to_s
    super + " [#{@paroles}]"
  end
end
print autreChanson, "\n"
#  Chanson : My Way--Sinatra (225) [And now, the...]

Attention C'est mieux, mais quand même…

… ce n'est pas une Chanson !!! Le nom de la classe est écrit en dur dans le to_s de Chanson.

La bonne solution.

class Chanson
  def to_s
    "#  #{self.class} : #{@nom}--#{@artiste} (#{@duree})"
  end
end
class ChansonKaraoke < Chanson
  def to_s
    super + " [#{@paroles}]"
  end
end
print uneChanson, "\n"
print autreChanson, "\n"
#  Chanson : Wish You Were Here--Pink Floyd (340)
#  ChansonKaraoke : My Way--Sinatra (225) [And now, the...]

self.class est évalué à l'exécution, sur le receveur : même quand c'est le code du to_s de Chanson qui s'exécute (appelé par super), self est la ChansonKaraoke. Une seule méthode, écrite une seule fois, affiche correctement toutes les chansons, y compris celles des sous-classes à venir.

Le carré et le rectangle : Liskov et duck typing p. 27–34

Un contre-exemple célèbre : en mathématiques, un carré est un rectangle ; en programmation objet, faire hériter le carré du rectangle est une erreur. Il conduit au principe de substitution de Liskov, puis au duck typing.

Le rectangle p. 28

Soit le concept de rectangle. En programmation objet, on peut le représenter par la classe Rectangle, définie par deux attributs, longueur et largeur, avec des accesseurs pour y accéder et les modifier librement.

class Rectangle
  private_class_method :new
  def self.definir(la, lo)
    new(la, lo)
  end
  def initialize(la, lo)
    @largeur, @longueur = la, lo
  end
  attr_accessor :largeur, :longueur
  def to_s
    return "Quel Beau #{self.class} : largeur = #{@largeur}, longueur = #{@longueur}"
  end
end
r = Rectangle.definir(10, 20)
puts r.inspect
r.largeur = 12
r.longueur = 23
puts r.inspect
#<Rectangle:0x00007f8b7f8a0f68 @largeur=10, @longueur=20>
#<Rectangle:0x00007f8b7f8a0f68 @largeur=12, @longueur=23>

Un carré est-il un rectangle ? p. 28–30

Considérons maintenant le concept de carré. En mathématiques, un carré est un rectangle. En programmation objet, on pourrait donc vouloir faire hériter la classe Carre de la classe Rectangle (figure, cas a), ce qui revient à dire que l'on peut utiliser une instance de Carre partout où un Rectangle est attendu. Or, si un carré est utilisé là où l'on s'attend à un rectangle, des comportements incohérents peuvent survenir :

  • les côtés d'un carré ne peuvent pas être changés indépendamment, contrairement à ceux d'un rectangle ;
  • une mauvaise solution consisterait à modifier les setters du carré ; mais ceci violerait la postcondition des setters du rectangle, qui spécifie que l'on peut modifier hauteur et largeur indépendamment.

Pour faire hériter Carre de Rectangle malgré tout, il faut des « bidouilles » :

class Carre < Rectangle

  def self.definir(cote)
    new(cote)
  end

  # Bidouille 1
  def initialize(cote)
    @largeur = @longueur = cote
  end

  # Bidouille 2
  def to_s()
    return "Quel Beau #{self.class} : cote = #{@largeur} "   # ou Longueur !!!
  end

  # Bidouille 3
  def cote=(c)
    initialize(c)
  end
  def cote
    return @largeur        # Ou longueur ????
  end
end
c = Carre.definir(10)
puts c.inspect
c.cote = 12
puts c.inspect
# problème
# on peut modifier la largeur : c.largeur=28
c.largeur = 28
puts c                  # => on dirait que ça marche : ===> Quel Beau Carre : cote = 28
puts "Cote = #{c.cote}" # => on dirait que ça marche : ===> Cote = 28
# on peut modifier la longueur : c.longueur=35
c.longueur = 35
puts c                  # Ah Bah non ça marche pas ===> Quel Beau Carre : cote = 28
puts "Cote = #{c.cote}" # Cote = 28
# on pourrait trouver une bidouille 4 pour que ça le fasse

Après c.largeur = 28, l'objet n'est déjà plus un carré (largeur 28, longueur 12) : l'affichage fait illusion parce qu'il ne lit que @largeur. Après c.longueur = 35, la longueur a changé sans que le « carré » s'en aperçoive.

Ajout Exécuté, le programme affiche bien deux fois Quel Beau Carre : cote = 28 et Cote = 28 ; un dernier puts c.inspect révèle l'objet réel, @longueur=35, @largeur=28.

Complément La bidouille 4 casse le code client

Redéfinir largeur= et longueur= pour qu'elles modifient les deux côtés garde le carré cohérent, mais trahit le contrat du rectangle : un code écrit pour des rectangles ne fonctionne plus.

class Carre < Rectangle
  def largeur=(c)
    @largeur = @longueur = c
  end
  def longueur=(c)
    @largeur = @longueur = c
  end
end
def aire_apres_redimensionnement(r)   # code client, écrit pour des rectangles
  r.largeur = 5
  r.longueur = 4
  r.largeur * r.longueur              # un rectangle 5 × 4 : on attend 20
end
aire_apres_redimensionnement(Rectangle.definir(1, 1))   #=> 20
aire_apres_redimensionnement(Carre.definir(1))          #=> 16 : surprise !

Ajout Résultats confirmés à l'exécution : 20, puis 16.

Lecture seule ou classes indépendantes p. 30–31

Une solution pour éviter ces incohérences est de retirer la nature modifiable des classes Carre et Rectangle : elles ne sont accessibles qu'en lecture (figure, cas b). Mais on devra implémenter des méthodes « hauteur » et « largeur » pour un carré, ce qui, sémantiquement, est un non-sens.

Conclusion Deux classes indépendantes

En programmation objet, les classes Carre et Rectangle sont deux classes indépendantes (figure, cas c) : un Rectangle a une longueur et une largeur modifiables séparément, un Carre a une taille.

Le principe de substitution de Liskov p. 31

Principe Substitution de Liskov

« Si S est un sous-type de T, alors les objets de type T peuvent être remplacés par des objets de type S sans altérer les propriétés désirables du programme. » (Barbara Liskov)

En clair : le code client ne doit jamais être « surpris ou cassé » quand on lui passe une sous-classe à la place de la classe mère. C'est pourtant le cas avec Carre qui hérite de Rectangle.

Attention Le piège : le « faux héritage »

La vision mathématique ou linguistique : un carré est un rectangle ; une autruche est un oiseau. La réalité en programmation objet : l'héritage est un héritage de comportements (de méthodes). Si la classe de base propose un comportement qu'une sous-classe ne peut pas honorer (par exemple Rectangle#largeur= ou Oiseau#voler), l'héritage est une erreur de conception.

La règle n° 1 (« est-un ») doit donc s'entendre au sens du comportement : une sous-classe doit savoir faire tout ce que promet sa superclasse.

Complément Extraction de capacité

module Volant                  # la capacité, isolée dans un module
  def voler
    "#{self.class} s'envole"
  end
end
class Oiseau
end
class Moineau < Oiseau
  include Volant               # seuls les oiseaux qui volent l'intègrent
end

end
Moineau.new.voler              #=> "Moineau s'envole"

Ajout Exécuté : "Moineau s'envole", puis undefined method 'voler' for an instance of Autruche.

Le duck typing p. 32–33

« Si ça ressemble à un canard, si ça nage comme un canard et si ça fait coin-coin, alors c'est un canard. » Le concept clé : des contrats comportementaux plutôt qu'une hiérarchie de classes. Le type d'un objet est défini par son comportement, ses méthodes.

Définition Duck typing

Avec le duck typing (typage « canard »), deux objets sans aucun lien de parenté, sans héritage commun, peuvent s'interchanger s'ils partagent les mêmes signatures de méthodes. Le contrat n'est plus dicté par un nom de classe, mais par l'aptitude à répondre à un message.

Le type d'un objet est défini parsa classe (typage nominal)uniquement son comportement
On demande à l'objet« Qui es-tu ? »« Que sais-tu faire ? »
 
# Deux classes distinctes, AUCUN héritage commun
class Canard
  def faire_coin_coin = "Coin !"
end
class CyberCanardRobot
  def faire_coin_coin = "C01N ! [Bip]"
end
# Le code client : il s'en moque tant que l'objet sait faire "coin-coin"
def simuler_mare(animal)
  puts animal.faire_coin_coin
end
simuler_mare(Canard.new)             # => "Coin !"
simuler_mare(CyberCanardRobot.new)   # => "C01N ! [Bip]"

La méthode simuler_mare n'impose aucune contrainte de type ou d'héritage. Si on lui passe un objet Chien sans méthode faire_coin_coin, le programme lèvera une erreur à l'exécution (NoMethodError). La forme def nom = expression (méthode sur une ligne) existe depuis Ruby 3.0 ; elle équivaut à un def … end qui retourne l'expression.

Avantages

  • Code minimaliste : pas besoin d'interfaces ou de hiérarchies complexes.
  • Tests unitaires simplifiés : on remplace facilement un objet complexe (une base de données) par un faux objet de test, sans créer d'interface.

Risques et limites

  • Erreurs tardives : les erreurs de type surviennent à l'exécution, pas à la compilation.
  • Contrat implicite : rien n'oblige le développeur à écrire la méthode. Sans une bonne documentation ou des tests, le code peut planter en secret.

Duck typing et principe de Liskov p. 33–34

Le duck typing pousse la logique du principe de Liskov au maximum : au lieu de forcer un Carre à hériter d'un Rectangle, on crée deux objets indépendants, que le code client substitue de manière fluide sans casser leurs invariants internes. L'invariant d'un rectangle : sa largeur et sa hauteur peuvent être différentes et varier indépendamment. Celui d'un carré : sa largeur et sa hauteur doivent obligatoirement, et tout le temps, être égales.

Complément Deux classes indépendantes, un même message

class Rectangle
  def initialize(largeur, longueur)
    @largeur, @longueur = largeur, longueur
  end
  def surface = @largeur * @longueur
end
class Carre
  def initialize(taille)
    @taille = taille
  end
  def surface = @taille * @taille
end
[Rectangle.new(2, 3), Carre.new(4)].each { |f| puts f.surface }   # 6, puis 16

Remarque Fin du contre-exemple et de la parenthèse

Certaines de ces dernières notions dépassent un peu le cadre de ce cours d'introduction à la programmation objet. On les retrouvera plus tard, dans le cours de POO avancée en Java et dans le cours de design patterns.

À retenir

L'essentiel

  • B hérite de A : les instances de B ont les champs et les comportements de celles de A, plus d'autres. Relation « est-un », jamais « a-un » (composition).
  • Héritage (classe → classe) : spécialisation, sous-typage, inclusion. Instanciation (objet → classe) : représentation, type, appartenance.
  • Héritage statique : une instance possède tous les champs de sa classe et de ses superclasses ; chaque classe initialise les siens.
  • Héritage dynamique : la méthode est cherchée dans la classe du receveur, puis en remontant les superclasses (ancestors) ; erreur d'exécution (NoMethodError) si elle n'existe nulle part.
  • Redéfinition : même nom dans la sous-classe ; elle nécessite une liaison dynamique, qui a toujours lieu en Ruby. Un message envoyé à self repart toujours de la classe du receveur.
  • super réutilise la méthode de même nom de la superclasse : ne jamais dupliquer son code. super seul transmet les mêmes arguments, super() aucun.
  • Polymorphisme : ad hoc (surcharge), d'héritage (redéfinition), paramétrique (généricité).
  • Classe abstraite : définie pour être sous-classée, pas pour être instanciée ; en Ruby, par convention, ses méthodes lèvent NotImplementedError.
  • Substitution de Liskov : une sous-classe doit pouvoir remplacer sa superclasse sans surprendre ni casser le code client ; d'où Carre et Rectangle indépendants.
  • Duck typing : le type d'un objet est défini par les messages auxquels il sait répondre.

Plusieurs points de vue sur l'héritage : ensembliste (l'inclusion), type (le sous-type et l'héritage dynamique des méthodes), style de programmation (la factorisation du code, la programmation par raffinements successifs, DRY, Don't Repeat Yourself : ne pas se répéter).

Auto-évaluation

Qu'est-ce qui peut distinguer une sous-classe de sa superclasse ?

Des champs supplémentaires (différence interne), des messages supplémentaires, et des messages traités différemment, par des méthodes redéfinies (différences externes). Elle ne peut rien retirer.

Pourquoi une voiture ne doit-elle pas hériter de moteur ?

Une voiture n'est pas un moteur : elle en a un. C'est une composition (un champ @moteur), pas un héritage, qui modélise « est-un » et jamais « a-un ».

retire, définie dans Compte, appelle seuil. Pour un CompteCourant, quel seuil s'exécute ?

Celui de CompteCourant : la recherche de seuil repart de la classe du receveur, même si le code qui envoie le message est celui de Compte. C'est la liaison dynamique.

Où commence la recherche de méthode d'un appel super ?

Dans la superclasse de la classe où est écrite la méthode qui contient super, et non dans la superclasse du receveur.

Quelle différence entre super, super() et super(a, b) ?

super transmet les mêmes arguments que ceux reçus, super() n'en transmet aucun, super(a, b) transmet exactement a et b.

Pourquoi écrire self.class plutôt que "Chanson" dans le to_s de Chanson ?

self.class est évalué sur le receveur : appelé par super depuis une ChansonKaraoke, il donne ChansonKaraoke. La méthode reste juste pour toutes les sous-classes, sans être recopiée.

En quoi Carre < Rectangle viole-t-il le principe de Liskov ?

Un code écrit pour des rectangles suppose qu'il peut changer la largeur sans changer la longueur. Un carré ne peut pas honorer cette promesse : soit il cesse d'être un carré, soit il casse le code client (une aire de 16 au lieu de 20).

Qu'est-ce que le duck typing ?

Le type d'un objet est défini par les messages qu'il sait traiter, pas par sa classe : deux objets sans lien d'héritage s'interchangent s'ils répondent aux mêmes messages. En contrepartie, une erreur (NoMethodError) n'apparaît qu'à l'exécution.
