Héritage et polymorphisme

Quatre sujets pour bâtir des hiérarchies de classes : deux sortes de comptes en banque, des documents manipulés de façon homogène, des afficheurs lumineux qui se spécialisent l'un l'autre, et une paie calculée sans aucun test de type. Les diagrammes se dessinent dans l'atelier, le code s'écrit dans un éditeur Ruby.

Objectifs

  • Spécialiser une classe existante : ajouter des variables d'instance, redéfinir une méthode en réutilisant celle de la superclasse avec super.
  • Factoriser ce qui est commun dans une classe abstraite, et laisser aux sous-classes ce qui varie (méthodes abstraites).
  • Manipuler des objets de classes différentes de façon homogène, par polymorphisme, sans tester leur type.
  • Dessiner la hiérarchie dans un diagramme de classes, puis l'écrire en Ruby.

Notions utilisées

  • Héritage, super, liaison dynamique, classes abstraites (cours 3)
  • Accesseurs et méthodes de création « métier » (cours 2)
  • La classe Compte et le décaleur des TD précédents : TD 2

Mode d'emploi

  • Diagrammes : double-clic sur le fond pour une classe, sur une classe pour la modifier ; « Les deux » montre aussi la vue texte. Le code s'écrit dans l'éditeur Ruby (Tab indente) ; Ruby ne s'exécute pas ici.
  • « Vérifier » contrôle la forme, « Comparer » mesure l'écart d'un diagramme avec la référence. Le bouton Correction montre la correction de l'enseignant (diagrammes Mermaid et code CompteEpisode3.rb du dossier TD/TD3/) ; le bouton Solution, une solution proposée, exécutée avec Ruby 3.3. Les deux demandent une confirmation : fais l'exercice d'abord.
  • Le travail s'enregistre tout seul. Avec le serveur local (studies/lancer.bat), il va dans td_results/ et Claude est disponible pour t'aider ou te corriger.

Le compte en banque, épisode 3 TD, sujet 1

Sujet 1 Le compte en Banque (Épisode 3)

À partir de la classe Compte du cours 2/TD 2, nous définissons deux sous-classes : la classe CompteEpargne et la classe CompteCourant.

  • Un compte courant est un compte sur lequel des découverts sont autorisés.
  • Un compte épargne est un compte qui rapporte des intérêts mensuels.
  1. Donnez en français la modélisation de ces deux classes.
  2. Écrire en Ruby le code nécessaire à l'implémentation de ces deux classes ainsi qu'un programme de test.
Indice

Pour chaque sous-classe : ce qu'elle a en plus (une variable d'instance, ses accès), ce qu'elle redéfinit (la création, le seuil de retrait, l'affichage) et ce qu'elle sait faire de nouveau. Le seuil de retrait du TD 2 est une méthode privée : c'est elle que le compte courant redéfinit.

Les documents TD, sujet 2

Sujet 2 Les Documents

Pour la gestion d'une bibliothèque, on nous demande d'écrire une application manipulant des documents de nature diverse : des livres, des dictionnaires, etc.

Tous les documents ont un numéro d'enregistrement et un titre. Les livres ont, en plus, un auteur et un nombre de pages, les dictionnaires ont une langue et un nombre d'articles. Ces diverses sortes de choses doivent pouvoir être manipulées de façon homogène en tant que documents.

On souhaite pouvoir créer tous les documents en fournissant les paramètres nécessaires à l'initialisation des variables d'instances.

Exemple :

liv1=Livre.nouveau("Ruby pour les Nuls","Ocaj",43)
liv2=Livre.nouveau("Ruby pour les mauvais","Jaco",143)
dic=Dictionnaire.nouveau ("Le dico de la langue","Ruby",652)
  1. Élaborer le diagramme de classe, Écrire les classes en Ruby.
  2. On souhaite afficher les informations relatives aux documents de la façon suivante :
Livre  : Numéro = 1, Titre = Ruby pour les Nuls, Auteur = Ocaj, Nombre de pages=43
Livre  : Numéro = 2, Titre = Ruby pour les mauvais, Auteur = Jaco, Nombre de pages=143
Dictionnaire  : Numéro = 3, Titre = Le dico de la langue, Langue = Ruby, Nombre d'Articles = 652
  1. Définissez une classe Bibliothèque réduite à une méthode de classe permettant de tester les classes précédentes.

Attention Une espace dans l'exemple À vérifier

La troisième ligne de l'exemple, Dictionnaire.nouveau ("Le dico de la langue","Ruby",652), a une espace entre le nom de la méthode et la parenthèse. Ruby lit alors ("…","Ruby",652) comme une seule expression entre parenthèses, et refuse la ligne (syntax error, unexpected ',' avec Ruby 3.3). Sans l'espace, elle fonctionne.

Indice

Le numéro d'enregistrement n'est pas fourni à la création : c'est un compteur commun à tous les documents (une variable de classe @@…), incrémenté à chaque création. Le début de l'affichage est le même pour tous les documents : il va dans la superclasse.

Les afficheurs lumineux, partie 2 TD, sujet 3

Sujet 3 Simulation d'afficheurs lumineux – Partie 2

Le but de cet exercice est de simuler en Ruby les afficheurs lumineux qui font circuler un texte en boucle. Des exemples d'utilisations sont donnés en Annexes et votre code DOIT permettre de faire fonctionner ces exemples de la même façon.

A) Le décaleur (Exercice effectué au TD1). Intéressons-nous d'abord au décaleur. C'est un objet qui stocke une suite de l caractères (avec l > 0). l est constant et est appelé largeur du décaleur. Initialement, un décaleur contient l espaces. Les quatre fonctionnalités d'un décaleur sont : fournir un accès à la largeur du décaleur ; remettre à zéro : force tous les caractères à espace ; décaler d'une position vers la gauche sa suite de caractères : le caractère le plus à gauche est supprimé de la suite et est renvoyé par la méthode. Le nouveau caractère le plus à droite est fixé à la valeur du paramètre fourni ; l'affichage d'un décaleur affiche le contenu de celui-ci.

Définir entièrement en Ruby la classe Decaleur. Écrire en Ruby le code de toutes les méthodes de la classe, sans oublier en particulier les méthodes de création/initialisation.

On rappelle ci-dessous le code de la classe Decaleur (sans les commentaires) :

class Decaleur
    # @texte    => Le texte du Décaleur
    # @largeur  => La Largeur du Décaleur

    attr_reader :largeur

    private_class_method :new

    def Decaleur.creer(largeur)
        new(largeur)
    end

    def initialize(largeur)
        @texte=Array.new(largeur)
        @largeur=largeur
        raz()
    end

    def raz()
        @texte.fill('-')
    end

   def decale(caractereEntrant)
    @texte.push(caractereEntrant)
    return @texte.shift()
   end
# … (la suite de la classe n'est pas reproduite dans le sujet)

B) Les afficheurs lumineux. Les caractéristiques d'un afficheur lumineux sont les suivantes : il ne peut visualiser simultanément qu'un nombre N fixe et entier de caractères avec N > 0. Le message qui se déroule en boucle sur l'afficheur ne doit pas avoir une longueur nulle, en revanche, celle-ci peut être plus petite, égale ou supérieure à N.

Le message défile dans l'afficheur en se décalant d'une position vers la gauche à chaque top d'une horloge. Quand le dernier caractère du message vient juste d'entrer dans la partie visualisée, au prochain top horloge, c'est le premier caractère du message qui y entre à son tour.

L'interface de la classe Afficheur pourra ressembler à :

# fixe un nouveau message a afficher
setMessage(UnTableauDeCaractere)
# un top d'horloge
top()
# renvoie ce qui doit être affiche
to_s()

C) Les afficheurs avec latence. On remarque que pour les afficheurs de l'exercice précédent il est difficile de voir où se termine le message. Pour éviter ce problème, on veut une nouvelle classe d'afficheurs pour lesquels on pourra spécifier lors de leur création un « temps de latence » entre l'entrée du dernier et celle du premier caractère. Ce temps de latence sera exprimé par un nombre positif ou nul d'espaces à insérer entre ces deux caractères. Appelons Latence cette nouvelle classe d'afficheurs.

D) Les afficheurs avec latence et vitesse paramétrable. À chaque top d'horloge, les afficheurs précédents font un seul décalage. On voudrait une nouvelle sorte d'afficheur dont on pourrait fixer le nombre de décalages effectués à chaque top. Ce nombre sera un entier positif ou nul. Appelons Vitesse cette nouvelle classe d'afficheurs.

  1. Élaborer le diagramme de classe correspondant à cet énoncé.
  2. Définir entièrement en Ruby la classe Afficheur. Préciser en particulier les variables d'instances et ce qu'elles représenteront. Écrire en Ruby le code de toutes les méthodes de la classe, sans oublier en particulier les méthodes de création/initialisation.
  3. Définir entièrement en Ruby la classe Latence. Préciser en particulier les variables d'instances et ce qu'elles représenteront. Écrire en Ruby le code de toutes les méthodes de la classe, sans oublier en particulier les méthodes de création/initialisation.
  4. Définir entièrement en Ruby la classe Vitesse. Préciser en particulier ses variables d'instances et ce qu'elles représenteront. Écrire en Ruby le code de toutes les méthodes de la classe, sans oublier en particulier les méthodes de création/initialisation.
  5. On devra pouvoir utiliser ce programme de test :
load "Vitesse.rb"

def testNFois(combienDeFois,unPanneau,unMessage)
  unPanneau.setMessage(unMessage.split(//))
  1.upto(combienDeFois) do
    sleep(0.3)
    unPanneau.top()
    puts unPanneau
  end
end

combien = 20
message="Vive la POO"

puts "\nTest de la classe Afficheur"
aff=Afficheur.creer(20)
testNFois(combien,aff,message)


puts "\nTest de la classe Latence"
lat=Latence.creer(20,2)
testNFois(combien,lat,message)


puts "\nTest de la classe Vitesse"
vit=Vitesse.creer(20,2,2)
testNFois(combien,vit,message)

Remarque Le décaleur du sujet

Le décaleur rappelé ici remplit avec des tirets (fill('-')) et non des espaces, comme le disait l'énoncé du TD 2 : on voit ainsi la partie vide de l'afficheur. L'extrait s'arrête après decale : il manque le to_s (et le end de la classe), que l'afficheur utilise pour s'afficher.

Indice

Un afficheur a un décaleur (composition) ; il n'en est pas un. Une latence est un afficheur dont le message se termine par des espaces : seul setMessage change. Une vitesse est une latence dont le top fait plusieurs décalages : seul top change.

La masse salariale TD, sujet 4

Sujet 4 Modélisation et Calcul de la Masse Salariale

1) Contexte. Une société de services informatiques souhaite moderniser son application interne de gestion des ressources humaines afin d'automatiser le calcul de la paie mensuelle de son personnel. Le service RH vous charge de concevoir le modèle objet de ce module en respectant au maximum les principes fondamentaux de la programmation orientée objet (encapsulation, factorisation du code, héritage et polymorphisme).

2) Description du domaine et règles de gestion.

2.1. Généralités sur le personnel.

  • Chaque personne travaillant dans l'entreprise possède un matricule unique et un nom.
  • Tout collaborateur doit obligatoirement être en mesure de fournir le montant de son salaire mensuel.

2.2. Les profils au forfait mensuel.

  • Les cadres perçoivent un salaire mensuel fixe, négocié lors de leur embauche.
  • Les directeurs sont des cadres qui bénéficient en plus, au vu de leurs responsabilités de direction, d'un bonus de performance qui s'ajoute à leur salaire mensuel de cadre.

2.3. Les profils rémunérés à l'heure.

  • Certains collaborateurs sont payés sur la base d'un nombre d'heures effectuées dans le mois et d'un taux horaire.
  • Pour tous ces profils, le calcul du salaire mensuel suit la même règle commune :
\[ \text{Salaire} = (\text{heures travaillées} \times \text{taux horaire}) + \text{prime} \]

Cependant, la façon de déterminer cette prime dépend obligatoirement du type de contrat :

  • Pour un stagiaire, la prime est une gratification forfaitaire fixe.
  • Pour un intérimaire, la prime est une prime de précarité, calculée sous la forme d'un pourcentage (taux de précarité, ex. 10 %) appliqué sur le montant horaire brut du mois (heures × tauxHoraire).

2.4. Traitement global. Le système doit être capable de regrouper l'ensemble des collaborateurs dans une seule et même collection afin d'afficher la fiche de paie de chacun et de calculer automatiquement la masse salariale totale de l'entreprise, sans recourir à des tests de type conditionnels (instanceof, kind_of?, switch, etc.).

3) Travail demandé.

Partie 1 — Analyse et Conception.

  • Identification des entités :
    • Listez les différentes classes à créer pour modéliser le problème.
    • Organisez-les sous forme d'une hiérarchie d'héritage. Combien de niveaux d'héritage identifiez-vous ?
  • Classes et méthodes abstraites :
    • Quelles sont les classes qui ne doivent pas être instanciables directement (classes abstraites) ? Justifiez votre choix à partir des règles métier.
    • Quelles sont les classes instanciables (classes concrètes) ?
    • Quelles méthodes doivent être déclarées abstraites et à quel niveau de la hiérarchie ? Justifiez l'intérêt pour la factorisation du code.
  • Diagramme de classes :
    • Réalisez le diagramme de classes complet du système (attributs, visibilités, méthodes, relations d'héritage, classes abstraites et concrètes).

Partie 2 — Implémentation en Ruby.

Partie 3 — Validation et Polymorphisme.

  • Écrire un programme de test (Main) qui :
    • crée une collection contenant au moins un représentant de chaque type de contrat réel de l'entreprise ;
    • parcourt cette collection pour afficher les informations de chaque collaborateur ainsi que sa paie calculée ;
    • calcule et affiche la masse salariale totale à verser ce mois-ci.
Indice

Deux familles de salaires : au forfait (cadre, directeur) et à l'heure (stagiaire, intérimaire). La règle « heures × taux + prime » est commune à la seconde famille : elle s'écrit une fois, dans une classe abstraite qui laisse la prime à ses sous-classes. Un directeur est un cadre.

À retenir

Les méthodes

  • Une sous-classe ajoute des variables d'instance et redéfinit ce qui change ; elle réutilise le code de sa superclasse par super (dans initialize, to_s, ou un calcul).
  • Une méthode privée de la superclasse (le seuil de retrait) est un point d'extension : la redéfinir suffit à changer une règle sans toucher aux méthodes qui l'appellent.
  • Une classe abstraite factorise ce qui est commun ; une méthode abstraite (qui lève une exception) oblige chaque sous-classe concrète à fournir sa version.
  • Le polymorphisme évite les tests de type : on envoie le même message (to_s, calculerSalaire) à tous les objets d'une collection, et chacun répond à sa façon.
  • « Est un » donne un héritage (un directeur est un cadre) ; « a un » donne une composition (un afficheur a un décaleur).
  • private_class_method :new et une méthode de création métier (creer, ouvrir, nouveau, recruter) contrôlent la création ; une sous-classe hérite de ce new privé.

Auto-évaluation

Pourquoi le compte courant redéfinit-il seuil plutôt que retire ?

La règle du retrait (« le solde ne passe pas sous le seuil ») est la même ; seul le seuil change (−découvert au lieu de 0). Redéfinir la petite méthode privée évite de recopier retire.

Où ranger le compteur qui donne les numéros d'enregistrement des documents ?

Dans une variable de classe (@@numeroCourant) de Document, partagée par toutes ses sous-classes : livres et dictionnaires sont numérotés à la suite.

Dans Vitesse, que fait @vitesse.times { super() } ?

Il appelle @vitesse fois le top hérité (celui d'Afficheur, à travers Latence) : autant de décalages par top. Les parenthèses vides évitent de retransmettre les arguments.

Combien de niveaux compte la hiérarchie de la paie, et pourquoi EmployeHoraire est-elle abstraite ?

Trois niveaux (Employe ; Cadre et EmployeHoraire ; Directeur, Stagiaire et Intérimaire). On n'embauche personne « à l'heure » sans contrat précis : la prime n'est pas définie à ce niveau.

Pourquoi l'énoncé interdit-il kind_of? pour calculer la masse salariale ?

Un test de type obligerait à modifier le calcul à chaque nouveau contrat. Par polymorphisme, chaque employé sait calculer son salaire, et la somme ne change jamais.
