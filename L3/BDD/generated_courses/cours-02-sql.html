Les familles de commandes SQL diapos 2–4

SQL (Structured Query Language) est un seul langage, mais ses commandes se rangent en familles selon ce qu'elles font : décrire la structure de la base, en manipuler le contenu, gérer les droits ou les transactions.

À vérifier Les rôles de DQL et de DCL semblent inversés ou décalés par rapport à l'usage le plus répandu. Dans la plupart des ouvrages, DQL désigne l'interrogation (SELECT), DCL la gestion des droits (GRANT, REVOKE), et les transactions (BEGIN, COMMIT, ROLLBACK) forment une sixième famille, TCL (Transaction Control Language). Le cours range SELECT dans le DML, ce qui est aussi une classification courante.

Complément SQL intégré, et quelques règles d'écriture

Le SQL intégré (embedded SQL) désigne des requêtes SQL écrites à l'intérieur d'un programme dans un autre langage (C, Java…), qui les envoie au SGBD et récupère les résultats.

Quelques règles valent pour toutes les commandes :

  • une commande se termine par ; ;
  • les mots-clés ne tiennent pas compte de la casse (select = SELECT), mais les valeurs, si : 'Manager' ≠ 'manager' ;
  • les chaînes s'écrivent entre apostrophes droites '…' ; les guillemets doubles "…" servent à nommer un objet ("$user") ;
  • -- commence un commentaire jusqu'à la fin de la ligne.

Attention Copier-coller depuis les diapos

Ajout Les diapos affichent des apostrophes typographiques : ‘%A%’. Collées dans psql, elles provoquent une erreur de syntaxe. Il faut les remplacer par l'apostrophe droite du clavier : '%A%'. Les exemples de cette page utilisent déjà la bonne.

Manipuler les données : INSERT, UPDATE, DELETE diapos 4–7

Le langage de manipulation des données (DML) compte trois commandes de base pour écrire dans les tables, et une quatrième, SELECT, pour les consulter. SELECT, associée à ses mots-clés et à ses clauses, permet de retrouver et d'afficher quasiment toutes les informations possibles : c'est l'instruction la plus puissante et la plus complexe, à laquelle la section 3 est consacrée.

  • INSERT : insertion de nouvelles données dans une table ;
  • UPDATE : mise à jour des données ;
  • DELETE : suppression d'enregistrements.

Insérer : INSERT INTO diapo 5

INSERT INTO crée une nouvelle donnée : elle ajoute une ligne dans une table, en respectant le schéma et les contraintes définis par le DDL.

INSERT INTO nom_table [ ( nom_colonne [, ...] ) ]
    { DEFAULT VALUES
    | VALUES ( { expression | DEFAULT } [, ...] )
    | requête
    };

Complément Exemples sur la table EMP

Avec la liste des colonnes, les colonnes omises prennent leur valeur par défaut (DEFAULT), ou NULL s'il n'y en a pas :

INSERT INTO emp (id_emp, nom_emp, metier, id_chef, date_emb, id_dep)
VALUES (8001, 'DUPONT', 'Vendeur', 7698, '2026-09-01', 30);
-- sal vaut 0.00 (sa valeur par défaut), comm vaut NULL

Les contraintes de la table sont vérifiées à chaque insertion :

INSERT INTO emp VALUES (8002, 'DURAND', 'Vendeur', 7698, '2026-09-01', 1500, NULL, 40);
-- ERREUR : insert or update on table "emp" violates foreign key constraint "emp_id_dep_fkey"
--          (le département 40 n'existe pas)

INSERT INTO emp (id_emp, metier, id_dep) VALUES (8003, 'Vendeur', 30);
-- ERREUR : null value in column "nom_emp" of relation "emp" violates not-null constraint

Sans liste de colonnes, il faut fournir une valeur pour toutes les colonnes, dans l'ordre de la table : c'est fragile, et à éviter dans un script.

Mettre à jour : UPDATE diapo 6

UPDATE modifie les valeurs des enregistrements : pour chaque colonne spécifiée, et pour chaque enregistrement qui satisfait la condition (si elle est exprimée). Les valeurs des autres colonnes sont conservées.

UPDATE nom_table [ AS nom_alias ]
    SET { nom_colonne = { expression | DEFAULT }
        | ( nom_colonne [, ...] ) = ( { expression | DEFAULT } [, ...] )
        } [, ...]
    [ FROM liste_sources ]
    [ WHERE condition ];

Exemple Augmenter les vendeurs de 5 % Ajout

UPDATE emp SET sal = sal * 1.05 WHERE metier = 'Vendeur';
-- UPDATE 4 : ALLEN passe de 1845.85 à 1938.14, WARD de 1253.12 à 1315.78…

Sans clause WHERE, toutes les lignes de la table sont modifiées.

Supprimer : DELETE diapo 7

DELETE supprime des enregistrements d'une table.

DELETE FROM nom_table [ [ AS ] nom_alias ]
    [ USING liste_using ]
    [ WHERE condition ];

Attention Danger : la suppression est définitive

Une ligne supprimée est perdue, sauf si l'on travaille dans une transaction. Sans WHERE, DELETE FROM emp; vide toute la table.

Complément « Sauf transaction » : annuler une suppression

Une transaction ouverte par BEGIN peut être annulée par ROLLBACK tant qu'elle n'a pas été validée par COMMIT :

BEGIN;
DELETE FROM emp WHERE metier = 'Secretaire';   -- DELETE 4
SELECT count(*) FROM emp;                      -- 10
ROLLBACK;                                      -- on annule
SELECT count(*) FROM emp;                      -- 14 : rien n'a été perdu

Les clés étrangères protègent aussi les données : DELETE FROM emp WHERE id_emp = 7698; échoue, car BLAKE est le chef d'autres employés (violates foreign key constraint "emp_id_chef_fkey").

Interroger les données : SELECT diapos 8–38

SELECT lit les données sans les modifier. Son résultat est lui-même une relation, que l'on peut trier, restreindre ou réutiliser dans une autre requête.

Les clauses de SELECT diapo 8

La commande compte neuf clauses, dont sept optionnelles : seules SELECT et FROM sont présentes dans presque toute requête.

SELECT [ ALL | DISTINCT ] { * | expression [ AS nom_affiché ] } [, ...]
FROM nom_table [ [ AS ] alias ] [, ...]
[ WHERE prédicat ]
[ GROUP BY expression [, ...] ]
[ HAVING condition [, ...] ]
[ { UNION | INTERSECT | EXCEPT } [ ALL ] requête ]
[ ORDER BY expression [ ASC | DESC ] [, ...] ]
[ LIMIT { ALL | nombre } ]
[ OFFSET début ]

Projection et sélection diapo 9

Les deux opérateurs de base de l'algèbre relationnelle se retrouvent dans deux clauses :

  • la projection, qui élimine des attributs d'une relation, correspond à la clause SELECT : SELECT att1, att2, … attN FROM nom_table; ;
  • la sélection sur une condition C, qui garde les n-uplets satisfaisant C, correspond à la clause WHERE : SELECT * FROM nom_table WHERE condition;.

Attention Le « SELECT » de SQL n'est pas la sélection

Ajout Piège de vocabulaire : la clause SELECT fait une projection (elle choisit des colonnes). La sélection de l'algèbre relationnelle (choisir des lignes) s'écrit avec WHERE.

La clause FROM et les jointures diapos 11–13

FROM désigne l'ensemble des données sur lesquelles la requête travaille. Est-elle réellement obligatoire ? Oui, dès qu'on travaille sur des données ; non, pour simplement appeler une fonction (SELECT now();). Elle permet aussi de combiner plusieurs tables par une jointure (join) : le résultat est toujours une relation.

Une jointure s'écrit avec le mot-clé JOIN, dans la clause FROM. Il en existe trois types :

  • la jointure croisée CROSS JOIN, qui associe chaque ligne de A à chaque ligne de B (produit cartésien) ;
  • la jointure interne INNER JOIN ou NATURAL JOIN, qui ne garde que les couples de lignes associées ;
  • la jointure externe [LEFT | RIGHT | FULL] OUTER JOIN, qui garde aussi les lignes sans correspondance d'un côté ou des deux.

Règles d'écriture (diapo 13) :

  • un même FROM peut contenir plusieurs jointures, lues de gauche à droite ;
  • une jointure réflexive (une table jointe à elle-même) oblige à renommer au moins une des deux occurrences avec AS ; les attributs se désignent alors en notation préfixée, alias_table.nom_attribut ;
  • on peut joindre une table avec l'ensemble de n-uplets produit par une requête SELECT, qu'il faut alors nommer avec AS. À n'utiliser que si nécessaire, par exemple pour récupérer un attribut calculé.

Complément Les jointures sur EMP et DEPT

-- Jointure interne : le département de chaque manager
SELECT e.nom_emp, d.nom_dep
FROM emp AS e INNER JOIN dept AS d ON e.id_dep = d.id_dep
WHERE e.metier = 'Manager';          -- CLARK Comptabilité, JONES Recherche, BLAKE Ventes

-- Même résultat : NATURAL JOIN joint sur les colonnes de même nom (ici id_dep)
SELECT nom_emp, nom_dep FROM emp NATURAL JOIN dept WHERE metier = 'Manager';

-- Jointure croisée : 14 employés × 3 départements = 42 lignes
SELECT count(*) FROM emp CROSS JOIN dept;

-- Jointure réflexive : chaque employé et son chef (13 lignes, KING n'a pas de chef)
SELECT e.nom_emp AS employe, c.nom_emp AS chef
FROM emp AS e JOIN emp AS c ON e.id_chef = c.id_emp;

-- Jointure externe : on garde KING, avec un chef NULL
SELECT e.nom_emp AS employe, c.nom_emp AS chef
FROM emp AS e LEFT OUTER JOIN emp AS c ON e.id_chef = c.id_emp;

NATURAL JOIN est pratique mais risqué : il joint sur toutes les colonnes de même nom. Si emp et dept avaient chacune une colonne nom, la jointure exigerait aussi l'égalité des noms, et ne renverrait plus rien. JOIN … ON dit exactement sur quoi l'on joint.

La clause WHERE diapos 14–15

WHERE pose une condition sur les lignes : WHERE expression1 OPÉRATEUR expression2. Les opérateurs disponibles :

  • comparaison, six opérateurs : =, <> (différent), <, >, <=, >= ;
  • étendue : BETWEEN valeur1 AND valeur2, bornes comprises ;
  • appartenance : IN (ensemble_valeurs) ;
  • correspondance à un modèle : LIKE modèle ;
  • valeur absente : IS NULL.

NOT nie une condition, pour exclure des enregistrements du résultat : NOT BETWEEN, NOT IN, NOT LIKE, IS NOT NULL. Plusieurs conditions se combinent avec AND (vrai si les deux sont vraies) et OR (vrai si l'une au moins l'est). On peut en enchaîner plusieurs, mais l'ordre d'écriture compte.

Exemple L'ordre d'écriture compte : AND passe avant OR Ajout

SELECT nom_emp FROM emp
WHERE metier = 'Vendeur' OR metier = 'Analyste' AND sal > 3100;
-- 5 lignes : SCOTT et les 4 vendeurs, car lu comme
--            Vendeur OR (Analyste AND sal > 3100)

SELECT nom_emp FROM emp
WHERE (metier = 'Vendeur' OR metier = 'Analyste') AND sal > 3100;
-- 1 ligne : SCOTT

Des parenthèses lèvent toute ambiguïté.

Complément LIKE et NULL

  • Dans un modèle LIKE, % remplace une suite quelconque de caractères (y compris vide) et _ exactement un caractère : nom_emp LIKE '_A%' donne WARD, MARTIN et JAMES. LIKE tient compte de la casse ; PostgreSQL propose ILIKE pour l'ignorer.
  • NULL signifie « valeur inconnue » : toute comparaison avec NULL donne inconnu, jamais vrai. WHERE comm = NULL ne renvoie donc aucune ligne ; il faut écrire WHERE comm IS NULL.

Sous-requêtes et filtrage diapo 16

Une sous-requête utilise le résultat d'une requête comme élément de comparaison dans la condition de la clause WHERE. Quatre opérateurs leur sont spécifiques : IN, EXISTS, ALL et ANY, tous niables par NOT. On a les équivalences :

  • IN équivaut à = ANY ;
  • NOT IN équivaut à <> ALL.

Complément Un exemple par opérateur

-- Une valeur : les employés payés plus que la moyenne (6 lignes, de KING à CLARK)
SELECT nom_emp, sal FROM emp WHERE sal > (SELECT avg(sal) FROM emp);

-- IN : les employés qui sont chefs de quelqu'un
-- (BLAKE, CLARK, FORD, JONES, KING, SCOTT)
SELECT nom_emp FROM emp WHERE id_emp IN (SELECT id_chef FROM emp);

-- NOT EXISTS : ceux qui ne dirigent personne (8 employés)
SELECT nom_emp FROM emp AS e
WHERE NOT EXISTS (SELECT * FROM emp AS s WHERE s.id_chef = e.id_emp);

-- ALL : plus que TOUS les managers (KING, FORD, SCOTT)
SELECT nom_emp, sal FROM emp
WHERE sal > ALL (SELECT sal FROM emp WHERE metier = 'Manager');

-- ANY : plus qu'AU MOINS UN manager (BLAKE, JONES, FORD, SCOTT, KING)
SELECT nom_emp, sal FROM emp
WHERE sal > ANY (SELECT sal FROM emp WHERE metier = 'Manager');

EXISTS ne regarde pas les valeurs renvoyées, seulement s'il y en a au moins une. La sous-requête est ici corrélée : elle utilise e.id_emp, qui vient de la requête principale, et elle est réévaluée pour chaque ligne.

Attention NOT IN et les NULL

Ajout Pour trouver les employés qui ne dirigent personne, WHERE id_emp NOT IN (SELECT id_chef FROM emp) renvoie zéro ligne. En cause, le NULL de KING dans id_chef : NOT IN équivaut à <> ALL, et une comparaison avec NULL n'est jamais vraie. Il faut filtrer les NULL dans la sous-requête (WHERE id_chef IS NOT NULL), ou utiliser NOT EXISTS.

Fonctions d'agrégation diapos 17–18

Une fonction d'agrégation calcule une seule valeur à partir d'un ensemble de valeurs en entrée. Les plus utilisées sont count, sum, avg, min et max. On les emploie dans les clauses SELECT et HAVING, sous quatre formes :

nom_agrégat (expression)
nom_agrégat (ALL expression)
nom_agrégat (DISTINCT expression)
nom_agrégat (*)

Exemple Compter avec count

SELECT count(id_chef)          AS manager,
       count(ALL id_chef)      AS tous_manager,
       count(DISTINCT id_chef) AS nombre_manager,
       count(*)                AS toutes_lignes
FROM emp;
managertous_managernombre_managertoutes_lignes
1313614
  • count(*) compte les lignes : 14.
  • count(id_chef), qui équivaut à count(ALL id_chef), compte les valeurs non NULL : 13, KING n'ayant pas de chef.
  • count(DISTINCT id_chef) compte les valeurs différentes : 6 chefs distincts.

À vérifier La diapo nomme la colonne mgr, son nom dans la version anglaise de la table ; c'est id_chef dans la table EMP du cours.

Complément Les agrégats ignorent les NULL

Sur les quatre vendeurs, seuls trois ont une commission. avg(comm) vaut 733,33 : la moyenne des trois commissions connues. La moyenne sur les quatre vendeurs, en comptant 0 pour TURNER, vaut sum(comm) / count(*) = 550.

De même, sal + comm vaut NULL pour TURNER, car toute opération avec NULL donne NULL. coalesce(comm, 0) remplace le NULL par 0 : sal + coalesce(comm, 0).

La clause GROUP BY diapos 19–26

GROUP BY classe les lignes par groupes. Un groupe est un sous-ensemble de lignes qui ont la même valeur pour les attributs précisés.

GROUP BY expression [, ...]
  • expression est un nom de colonne en entrée, un nom ou un numéro de colonne en sortie, ou une expression sur les champs en entrée.
  • La clause se place après WHERE et avant ORDER BY.

Règle Ce que peut contenir le SELECT d'une requête groupée

Chaque attribut de la clause SELECT doit soit figurer dans la clause GROUP BY, soit être dans une fonction d'agrégation. Et la requête produit une seule ligne par groupe.

Exemple Du salaire moyen au salaire moyen par métier

SELECT avg(sal) FROM emp;                   -- 2227.1107… : une ligne pour toute la table
SELECT metier, avg(sal) FROM emp GROUP BY metier;
metieravg
Vendeur1532.22
Manager2827.91
President5000.00
Analyste3145.48
Secretaire1319.00

Une seule ligne est renvoyée par groupe, et la moyenne est calculée au sein de chaque groupe.

Remarques diapo 22

  • La colonne calculée porte seulement le nom de la fonction appliquée (avg), sans indication d'attribut.
  • Si l'« attribut groupé » (metier) n'est pas repris dans le SELECT, on obtient cinq moyennes sans savoir à quel métier chacune correspond : on ne comprend rien !

Ajout D'où l'habitude de nommer et d'arrondir : SELECT metier, round(avg(sal), 2) AS sal_moyen FROM emp GROUP BY metier;

Exemple Compter les personnes, en tout et par département diapos 23–24

SELECT count(*) FROM emp;                              -- 14
SELECT count(*), id_dep FROM emp GROUP BY id_dep;      -- 6 au 30, 3 au 10, 5 au 20

Exemple GROUP BY combiné avec WHERE diapo 25

Le WHERE est appliqué avant le regroupement : on ne garde que les employés dont le nom contient un A, puis on groupe par métier.

SELECT metier, avg(sal) FROM emp WHERE nom_emp LIKE '%A%' GROUP BY metier;

SELECT nom_emp, metier, avg(sal) FROM emp WHERE nom_emp LIKE '%A%' GROUP BY metier;
-- ERREUR : column "emp.nom_emp" must appear in the GROUP BY clause
--          or be used in an aggregate function

Exemple Des sous-groupes diapo 26

On peut grouper sur plusieurs colonnes : un groupe réunit alors les lignes qui ont la même valeur pour toutes ces colonnes. L'ordre des colonnes dans GROUP BY n'a pas d'importance : GROUP BY metier, id_chef et GROUP BY id_chef, metier donnent des valeurs identiques (seul l'ordre d'affichage peut changer).

La clause HAVING diapos 27–30

Définition HAVING

HAVING applique une restriction sur les groupes. HAVING est à GROUP BY ce que WHERE est à SELECT :

  • WHERE restreint les enregistrements ;
  • HAVING restreint les groupes.

Sa syntaxe est celle de WHERE, mais sa condition ne peut porter que sur une fonction d'agrégation ou sur une expression qui figure dans la clause GROUP BY.

Exemple Les métiers dont le salaire moyen dépasse 1 500 diapos 28–29

SELECT metier, avg(sal) FROM emp GROUP BY metier HAVING avg(sal) > 1500;
metieravg(sal)
Vendeur1532.22
Manager2827.91
Analyste3145.48
President5000.00

Le groupe des secrétaires (1 319,00) est écarté après le calcul des moyennes.

Question du cours « Pbm or not pbm ? » diapo 29

Ces trois requêtes posent-elles problème ?

SELECT avg(sal) FROM emp HAVING nom_emp LIKE '%A%';                       -- (1)
SELECT nom_emp FROM emp GROUP BY metier HAVING nom_emp LIKE '%A%';         -- (2)
SELECT metier, avg(sal) FROM emp GROUP BY metier HAVING metier LIKE '%A%'; -- (3)
Solution proposée
  1. Problème. Sans GROUP BY, toute la table forme un seul groupe, et nom_emp n'est ni groupé ni agrégé. PostgreSQL refuse : column "emp.nom_emp" must appear in the GROUP BY clause…. Une condition sur les lignes s'écrit avec WHERE : SELECT avg(sal) FROM emp WHERE nom_emp LIKE '%A%';.
  2. Problème, même erreur : un groupe de métier contient plusieurs noms, nom_emp ne peut apparaître ni dans le SELECT ni dans le HAVING.
  3. Pas de problème : metier figure dans le GROUP BY. Résultat : une seule ligne, Analyste | 3145.48, car LIKE tient compte de la casse et seul « Analyste » contient un A majuscule. Une telle condition, qui ne porte pas sur un agrégat, s'écrirait plutôt dans le WHERE : on filtre avant de grouper, c'est plus efficace.

Exemple Le métier au salaire moyen le plus élevé diapo 30

SELECT metier, avg(sal) FROM emp GROUP BY metier; donne les cinq moyennes ; on veut la ligne du président, la plus haute. L'astuce : copier-coller cette requête comme sous-requête dans le HAVING.

SELECT metier, avg(sal) FROM emp GROUP BY metier
HAVING avg(sal) >= ALL (SELECT avg(sal) FROM emp GROUP BY metier);
-- President | 5000.00

La sous-requête renvoie la colonne des cinq moyennes. On compare chaque moyenne de groupe à toutes les moyennes : seule la plus forte est supérieure ou égale à toutes, et l'emporte.

Complément Vu en séance : les catégories au-dessus de la moyenne notes de séance

En séance, l'exemple de HAVING avec une sous-requête portait sur la base Dingo Fringo : des vendeurs, avec un parrainage entre vendeurs (association réflexive vue au cours 1), et les articles qu'ils ont vendus. Cette base sert de fil rouge au cours 3, qui donne son script complet et ses données.

Vendeurs(id, nom, #id_parrain)

Articles(id, nom, categorie, prix, date_vente, #id_vendeur)

On cherche les catégories dont le chiffre d'affaires total dépasse la moyenne des chiffres d'affaires par catégorie. La moyenne se calcule sur le résultat d'une première requête groupée, placée dans le FROM et nommée avec AS :

SELECT categorie, SUM(prix) AS ca_total
FROM articles
GROUP BY categorie
HAVING SUM(prix) > (
    SELECT AVG(ca) FROM (
        SELECT SUM(prix) AS ca
        FROM articles
        GROUP BY categorie
    ) AS sous_requete
);
--  categorie | ca_total
--  Vêtements |   118.00

Sur les données du cours 3, les chiffres d'affaires par catégorie valent 85,00 (Chaussures), 118,00 (Vêtements) et 54,00 (Accessoires), et leur moyenne 85,67 environ : seuls les Vêtements la dépassent. On ne peut pas écrire directement AVG(SUM(prix)), car PostgreSQL refuse d'imbriquer deux agrégats (aggregate function calls cannot be nested) : d'où la table intermédiaire. Jusqu'à PostgreSQL 15, celle-ci doit porter un nom (AS sous_requete) ; il est facultatif depuis la version 16.

Le cours 3 décompose cette requête de l'intérieur vers l'extérieur, puis la réécrit plus lisiblement avec une expression de table commune (WITH) : voir Une requête difficile à lire et Les CTE : WITH. Les deux CREATE TABLE vus en séance sont repris en section 4.5.

ORDER BY, LIMIT et OFFSET diapos 31–36

Sans ORDER BY, l'ordre des n-uplets du résultat est aléatoire et n'est pas garanti. ORDER BY trie les n-uplets résultats de la requête :

ORDER BY expression [ ASC | DESC ] [, ...]
  • expression : un champ, un numéro de colonne (ordinal) ou une opération mathématique de base ;
  • ASC : ordre croissant, par défaut ; DESC : ordre décroissant ;
  • on peut trier selon plusieurs champs, dans l'ordre précisé.

Exemple Trier sur plusieurs colonnes, par leur numéro diapos 32–33

SELECT * FROM emp ORDER BY nom_emp; liste les employés par ordre alphabétique, d'ADAMS à WARD. Avec des numéros de colonnes :

SELECT sal, comm FROM emp ORDER BY 2, 1;   -- par commission, puis par salaire

Les trois lignes avec commission viennent en premier (300, 500, 1 400), puis les onze lignes sans commission, triées par salaire de 1 212,24 à 5 000,00.

Remarque : la valeur NULL est considérée supérieure à toute autre valeur. En ordre croissant, les NULL sont donc à la fin.

Ajout PostgreSQL permet d'en décider : ORDER BY comm NULLS FIRST ou NULLS LAST.

LIMIT et OFFSET restreignent le nombre de n-uplets renvoyés :

LIMIT { ALL | nombre }
OFFSET début
  • ALL, par défaut : pas de limite ;
  • nombre : le nombre total de n-uplets à afficher ;
  • début : le nombre de n-uplets à sauter avant d'afficher les suivants.

Exemple Page de 4 employés, à partir du deuxième diapos 35–36

SELECT * FROM emp ORDER BY nom_emp LIMIT 4 OFFSET 1;

OFFSET 1 saute ADAMS, LIMIT 4 garde les quatre suivants : ALLEN, BLAKE, CLARK, FORD.

Attention LIMIT n'est pas un MAX

LIMIT et OFFSET ne s'utilisent qu'en complément d'ORDER BY, et jamais à la place d'un MAX : risques d'incohérence.

Ajout Sans ORDER BY, les lignes gardées sont arbitraires. Et même trié, ORDER BY sal DESC LIMIT 1 ne renvoie qu'un employé si deux sont à égalité au sommet, alors que WHERE sal = (SELECT max(sal) FROM emp) les renvoie tous.

L'ordre dans lequel le SGBD exécute ces clauses n'est pas l'ordre dans lequel on les écrit :

  1. FROM : on constitue les données de travail, jointures comprises.
  2. WHERE : on filtre les lignes.
  3. Fonctions de groupe et GROUP BY : on forme les groupes.
  4. HAVING : on filtre les groupes.
  5. SELECT : on calcule les colonnes affichées.
  6. UNION / INTERSECT / EXCEPT : on combine avec d'autres requêtes.
  7. ORDER BY : on trie.
  8. DISTINCT : on retire les doublons.
  9. OFFSET : on saute les premières lignes.
  10. LIMIT : on garde les suivantes.

Complément Ce que cet ordre explique

  • Un alias défini dans le SELECT n'existe pas encore au moment du WHERE : SELECT sal * 12 AS annuel FROM emp WHERE annuel > 30000; échoue (column "annuel" does not exist). On répète l'expression dans le WHERE (WHERE sal * 12 > 30000). L'alias est en revanche utilisable dans ORDER BY, exécuté après.
  • WHERE ne peut pas contenir d'agrégat, puisque les groupes ne sont pas encore formés : c'est le rôle de HAVING.
  • Les opérateurs ensemblistes combinent deux requêtes de même forme. Les métiers présents au département 10 ou au 20 : SELECT metier FROM emp WHERE id_dep = 10 UNION SELECT metier FROM emp WHERE id_dep = 20; (Analyste, Manager, President, Secretaire) ; avec INTERSECT, ceux présents dans les deux (Manager, Secretaire).

À vérifier La diapo place DISTINCT après ORDER BY. La documentation de PostgreSQL le traite juste après le calcul du SELECT, donc avant le tri. C'est pourquoi PostgreSQL refuse SELECT DISTINCT metier FROM emp ORDER BY sal; (for SELECT DISTINCT, ORDER BY expressions must appear in select list) : une fois les doublons retirés, il n'y a plus un seul salaire par ligne sur lequel trier.

Définir les données : le DDL diapos 39–67

Le langage de définition des données (DDL) manipule les objets SQL eux-mêmes, et non leur contenu. Il tient en trois commandes : CREATE crée un nouvel objet, ALTER le modifie, DROP le supprime.

Définition Catalogues système

Les catalogues système sont des tables particulières, dont le nom commence par pg_. Elles stockent toutes les métadonnées des objets de la base : on les interroge pour obtenir la liste des tables, des utilisateurs, des vues… Chaque catalogue système est propre à sa base de données, sauf rares exceptions (comme pg_database, commun à toutes).

Attention

Il est possible de modifier ou de supprimer les catalogues (!!). Le faire à la main peut rendre la base inutilisable : on ne les consulte qu'en lecture.

Toute nouvelle base contient aussi un schéma information_schema, défini par la norme SQL. Ses tables décrivent ce que le serveur sait faire : sql_languages liste les versions de la norme prises en charge (ISO 9075, années 1999 et 2003, niveau CORE), sql_features détaille chaque fonctionnalité (types numériques, COUNT, AVG, GROUP BY, sous-requêtes, UNION…) et indique si elle est supportée.

SELECT * FROM information_schema.sql_languages;

Complément pg_catalog ou information_schema ?

Les deux décrivent la base. pg_catalog est propre à PostgreSQL, complet, et c'est lui que lisent les commandes \dt, \dv… de psql. information_schema suit la norme SQL : une requête écrite sur lui fonctionne aussi dans d'autres SGBD.

Les bases de données diapos 43–45, 49

Le mot-clé DATABASE désigne un conteneur pour un ensemble nommé d'objets SQL. Chaque objet appartient à une seule base, sauf certains catalogues système. Une base se manipule comme les autres objets : CREATE, ALTER, DROP DATABASE.

  • Les bases sont séparées physiquement : une connexion n'a accès qu'aux objets de la base à laquelle elle est connectée.
  • Pour partager des ressources entre utilisateurs, il faut donc travailler au sein de la même base (et la séparer en schémas, voir plus bas).
  • On se connecte au serveur sur une base de données, et le contrôle d'accès se fait au niveau de la connexion : psql -d nom_de_la_base. Par défaut, le nom de la base est le nom de l'utilisateur.
  • Une nouvelle base se crée depuis n'importe quelle autre. Elle est une recopie de la base modèle template1, qui contient notamment l'ensemble des catalogues nécessaires.

Les schémas diapos 50–54

Le mot-clé SCHEMA (propre à PostgreSQL, non standard sous cette forme) définit un espace de nommage : deux objets de schémas différents peuvent porter le même nom sans conflit. Une base contient un ou plusieurs schémas, et tout objet de la base est contenu dans un schéma. Le catalogue correspondant est pg_namespace.

À quoi servent-ils ? À faire travailler différents utilisateurs sur une même base sans interférence, et à organiser les objets en groupes logiques pour faciliter leur gestion.

CREATE SCHEMA nom_schema;                                   -- création
nom_schema.nom_objet                                        -- accès à un objet du schéma
CREATE TABLE nom_schema.nom_objet (...);                    -- création d'un objet dans le schéma
CREATE SCHEMA nom_schema AUTHORIZATION nom_utilisateur;     -- propriétaire à la création
ALTER SCHEMA nom_schema OWNER TO nouvel_utilisateur;        -- changement de propriétaire
DROP SCHEMA nom_schema [ CASCADE | RESTRICT ];              -- suppression

Toute nouvelle base contient par défaut le schéma public. Il n'est pas obligatoire et peut être supprimé ; si aucun schéma n'est créé, tous les objets le sont dans public. Par défaut, CREATE TABLE ma_table (...); équivaut donc à CREATE TABLE public.ma_table (...);.

Dans quel schéma travaille-t-on ?

Le chemin de parcours des schémas, search_path, liste les schémas par ordre de recherche. Quand un objet est nommé sans préfixe, PostgreSQL le cherche dans chacun de ces schémas, dans l'ordre. Préfixer est donc obligatoire pour un objet situé dans un schéma absent du search_path.

SHOW search_path;                               -- "$user", public
SET search_path TO "toto", "$user", public;     -- toto est désormais cherché en premier
  • La modification est locale à la connexion, sur la base courante, et le search_path se réinitialise à chaque nouvelle connexion.
  • "$user" désigne le schéma qui porte le nom de l'utilisateur connecté, s'il existe.
  • Le schéma toto doit exister.

À vérifier Testé sous PostgreSQL 18, SET search_path accepte un schéma inexistant sans erreur : il est simplement ignoré tant qu'il n'existe pas. Le schéma doit donc exister pour que la commande serve, mais son absence n'est pas signalée.

Créer une table diapos 55–56

CREATE TABLE définit une nouvelle table. Il faut choisir son nom, qui commence par une lettre, n'est pas un mot-clé, et est unique dans le schéma. Puis, pour chaque attribut, définir un nom, un type et des contraintes.

CREATE TABLE nom_table (
    { nom_col type [ DEFAULT expr_defaut ] [ contrainte_col [...] ]
    | contrainte_table }
    [, ...]
);

Exemple La table emp, dans sa version anglaise

CREATE TABLE emp (
    empno     integer        NOT NULL,     -- contraintes de colonne
    name      varchar(10)    NOT NULL,
    job       varchar(10)    NOT NULL,
    mgr       integer,
    hiredate  date,
    sal       numeric(7,2)   DEFAULT 0.00,
    comm      numeric(7,2),
    deptno    integer        NOT NULL,
    PRIMARY KEY (empno)                    -- contrainte de table
);

Une contrainte de colonne s'écrit à la suite de l'attribut qu'elle concerne. Une contrainte de table s'écrit à part, et peut porter sur plusieurs colonnes, comme une clé primaire composée. numeric(7,2) désigne un nombre de 7 chiffres dont 2 après la virgule : jusqu'à 99 999,99.

Les contraintes d'intégrité diapos 57–60

Les contraintes d'intégrité assurent la précision, la logique et la validité des données. On les précise généralement à la création de la table :

  • PRIMARY KEY, sur un ou plusieurs attributs : l'unicité de la clé garantit l'unicité de l'enregistrement ;
  • UNIQUE : la valeur de la colonne est unique pour chaque enregistrement ;
  • NOT NULL : une valeur doit être saisie dans ce champ à chaque nouvel enregistrement.

Définition Contrainte de clé étrangère

Une contrainte de clé étrangère assure l'intégrité des données par un lien entre un attribut et celui d'une autre table (la table cible), ou entre plusieurs attributs et leurs correspondants. L'attribut est alors obligé de prendre ses valeurs parmi celles de l'attribut cible.

  • Elle définit l'ordre d'insertion des enregistrements : la table cible avant la table qui y fait référence.
  • Les attributs cibles doivent être uniques : au minimum une contrainte UNIQUE, le plus souvent la clé primaire.
-- À la création de la table, contrainte de colonne :
nom_attribut type REFERENCES table_cible (attribut_cible)

-- À la création de la table, contrainte de table :
FOREIGN KEY (nom_attribut) REFERENCES table_cible (attribut_cible)

-- Après la création de la table :
ALTER TABLE nom_table ADD CONSTRAINT nom_contrainte
    FOREIGN KEY (nom_attribut) REFERENCES table_cible (attribut_cible);

À vérifier La diapo 59 écrit la contrainte de table sans parenthèses : FOREIGN KEY nom_attribut REFERENCES …. PostgreSQL la refuse (syntax error at or near "nom_attribut") : les parenthèses autour de la liste des attributs sont obligatoires. Elles sont rétablies ci-dessus.

On précise enfin ce qui doit se passer quand la valeur cible change ou disparaît, avec ON UPDATE action et ON DELETE action :

Actions d'une clé étrangère
ActionEffet sur les lignes qui font référence à la valeur modifiée ou supprimée

RESTRICTcomme NO ACTION, mais la vérification ne peut pas être différée
CASCADEla modification est répercutée : les lignes sont mises à jour, ou supprimées

Complément Les règles du cours 1, écrites en SQL

Les tables vues en séance, celles de la base Dingo Fringo (script complet et données au cours 3), traduisent une association réflexive (le parrain) et une association 0..1 — * (le vendeur d'un article) :

CREATE TABLE vendeurs (
    id          INT PRIMARY KEY,
    nom         VARCHAR(50),
    id_parrain  INT REFERENCES vendeurs (id)          -- réflexive : NULL si pas de parrain
);

CREATE TABLE articles (
    id          INT PRIMARY KEY,
    nom         VARCHAR(50),
    categorie   VARCHAR(50),
    prix        NUMERIC(6,2),
    date_vente  DATE,
    id_vendeur  INT REFERENCES vendeurs (id) ON DELETE SET NULL
);

Avec ON DELETE SET NULL, supprimer un vendeur garde ses articles, dont id_vendeur devient NULL. Pour une composition, comme le bâtiment et ses salles du cours 1, on choisit au contraire CASCADE : supprimer le « tout » supprime ses parties.

CREATE TABLE salle (
    id_salle  int,
    id_bat    int REFERENCES batiment ON DELETE CASCADE,
    nom       varchar(30),
    PRIMARY KEY (id_salle, id_bat)
);
-- DELETE FROM batiment WHERE id_bat = 1;  supprime aussi toutes les salles du bâtiment 1

Les multiplicités se traduisent aussi en contraintes : un minimum de 1 donne NOT NULL sur la clé étrangère, une association 1 — 0..1 ajoute UNIQUE. Enfin, CHECK exprime une règle quelconque : ALTER TABLE emp ADD CONSTRAINT ck_sal_positif CHECK (sal >= 0); refuse tout salaire négatif.

Créer une table à partir de l'existant diapos 61–62

À partir des données d'une requête SELECT, complète, on recopie tout ou partie des enregistrements :

CREATE TABLE emp2 AS SELECT * FROM emp;                                          -- recopie complète
CREATE TABLE emp3 AS SELECT id_emp, nom_emp, sal FROM emp WHERE nom_emp LIKE 'A%';  -- recopie partielle

Attention Les données, mais pas les contraintes

Les données sont copiées, les contraintes perdues. Ajout Après CREATE TABLE emp2 AS SELECT * FROM emp;, on peut insérer dans emp2 un second KING d'identifiant 7839, dans un département 99 inexistant : ni clé primaire, ni clé étrangère.

À partir de la structure d'une table existante, avec LIKE :

CREATE TABLE emp4 (LIKE emp);          -- structure + contraintes NOT NULL
CREATE TABLE emp4 (LIKE emp INCLUDING DEFAULTS INCLUDING CONSTRAINTS INCLUDING INDEXES);
                                       -- structure, contraintes et index

Attention La structure, mais pas les données

Cette fois, la structure est copiée, mais la table est vide. Ajout La clé primaire n'est recopiée qu'avec INCLUDING INDEXES, et les clés étrangères ne le sont jamais, même avec INCLUDING ALL.

Modifier et supprimer une table diapos 63–65

ALTER TABLE modifie la structure d'une table après sa création, même après l'insertion de données : colonnes, contraintes, propriétaire… Usages courants :

ALTER TABLE emp ADD COLUMN telephone varchar(15);          -- ajout d'une colonne
ALTER TABLE emp RENAME COLUMN telephone TO tel;            -- changement de nom
ALTER TABLE emp ALTER COLUMN tel TYPE varchar(20);         -- modification du type
ALTER TABLE emp DROP COLUMN tel;                           -- suppression d'une colonne
ALTER TABLE emp RENAME TO employes;                        -- renommer la table
ALTER TABLE emp ADD CONSTRAINT ck_sal_positif CHECK (sal >= 0);  -- ajout d'une contrainte

DROP TABLE supprime une table : sa structure et son contenu. Pour ne supprimer que le contenu, on utilise DELETE. Seul le propriétaire de la table peut la supprimer.

DROP TABLE nom_table [, ...] [ RESTRICT | CASCADE ];
  • Les index, déclencheurs (triggers) et contraintes de la table sont supprimés avec elle.
  • RESTRICT : la suppression est impossible si un autre objet dépend de la table.
  • CASCADE : les vues et les contraintes de clés étrangères qui en dépendent sont supprimées aussi.

Complément RESTRICT par défaut, et ce que CASCADE ne supprime pas

RESTRICT est le comportement par défaut : DROP TABLE dept; échoue (cannot drop table dept because other objects depend on it) tant que emp y fait référence. Avec DROP TABLE dept CASCADE;, la vue v_nom_emp_dept et la contrainte de clé étrangère de emp disparaissent, mais la table emp et ses lignes restent : seul le lien est supprimé.

Les vues diapos 66–67

Définition Vue

Une vue (VIEW) est une table « virtuelle » : ses données ne sont pas stockées physiquement, seule la requête qui la crée l'est. Son nom doit différer de celui de toute table, index ou séquence.

C'est un objet dynamique : si les données sources changent, les données de la vue changent aussi.

On l'utilise pour réutiliser fréquemment le résultat d'une requête, et pour alléger des requêtes trop lourdes.

CREATE VIEW v_nom_emp_dept AS                         -- création
    SELECT nom_emp, nom_dep FROM emp NATURAL JOIN dept;
SELECT * FROM v_nom_emp_dept WHERE nom_emp LIKE '%A%'; -- utilisation, comme une table
DROP VIEW v_nom_emp_dept;                              -- suppression
SELECT * FROM pg_views;                                -- lister les vues (catalogue des vues)

Dans psql, \dv liste aussi les vues.

Exemple Une vue suit ses données sources Ajout

UPDATE dept SET nom_dep = 'Commercial' WHERE id_dep = 30;
SELECT * FROM v_nom_emp_dept WHERE nom_emp = 'ALLEN';   -- ALLEN | Commercial

La vue n'a pas été recréée : elle rejoue sa requête à chaque utilisation.

Les fonctions SQL diapos 68–82

Après les bases, schémas, tables et vues, le cours aborde un autre objet du SGBD : la fonction.

Principe diapos 71–73

Définition Fonction SQL

Une fonction (FUNCTION) est un identificateur qui demande, au sein d'une requête SQL, l'exécution d'une opération programmée. Le résultat renvoyé s'insère à la place de l'appel. Comme les tables, les vues ou les index, c'est un objet lié à une base de données.

Une fonction sert à étendre les capacités de SQL, et à simplifier l'écriture des requêtes. On en distingue trois types :

  • les fonctions prédéfinies classiques : abs(), upper()… ;
  • les fonctions d'agrégation prédéfinies : sum(), avg()… ;
  • les fonctions définies par l'utilisateur, avec la syntaxe suivante.
CREATE [ OR REPLACE ] FUNCTION nom ( [ type_argument [, ...] ] )
RETURNS type_retour AS
    'définition'
LANGUAGE nom_langage;
  • Les arguments se déclarent par leur type. Ils ne sont pas obligatoires, mais les parenthèses le sont toujours.
  • RETURNS type_retour indique le type des données renvoyées.
  • AS 'définition' contient la requête, le code exécuté par la fonction.
  • LANGUAGE précise le langage de ce code : SQL, ou le langage procédural PL/pgSQL.
  • OR REPLACE remplace une fonction existante, à prototype inchangé (voir plus bas).
  • Dans psql, \df liste ses fonctions.

Exemples diapos 74–75

Le paramètre se désigne par sa position, $1 :

CREATE FUNCTION f_get_metier (varchar(20))
RETURNS varchar(30) AS
    'SELECT metier FROM emp WHERE nom_emp = $1'
LANGUAGE SQL;

SELECT f_get_metier('BLAKE');     -- Manager

ou par un nom, déclaré dans le prototype :

CREATE FUNCTION f_get_metier (name varchar(20))
RETURNS varchar(30) AS
    'SELECT metier FROM emp WHERE nom_emp = name'
LANGUAGE SQL;

Complément Les apostrophes dans le corps de la fonction

Le corps est lui-même une chaîne entre apostrophes. Une apostrophe à l'intérieur doit donc être doublée : 'SELECT * FROM emp WHERE metier = ''Manager'''. PostgreSQL accepte aussi le délimiteur $$ … $$, qui évite ce doublement : AS $$ SELECT * FROM emp WHERE metier = 'Manager' $$.

Le type de retour diapos 76–77

Bien définir le type de sortie de la fonction est très important. Une fonction déclarée RETURNS NUMERIC renvoie une seule valeur :

CREATE FUNCTION f_get_salaire_metier (job varchar(20))
RETURNS NUMERIC AS
    'SELECT sal FROM emp WHERE metier = job'
LANGUAGE SQL;

SELECT f_get_salaire_metier('Manager');    -- 2975.24 : il manque les autres managers !

Pour renvoyer plusieurs lignes, il faut un type de retour composite, avec SETOF : SETOF varchar(20) désigne un ensemble de lignes de type varchar(20).

CREATE OR REPLACE FUNCTION f_get_salaire_metier (job varchar(20))
RETURNS SETOF NUMERIC AS
    'SELECT sal FROM emp WHERE metier = job'
LANGUAGE SQL;

SELECT f_get_salaire_metier('Manager');    -- 2975.24, 2852.56, 2655.92 : cette fois, c'est bon

Ajout La première version ne renvoie pas une erreur, mais la première ligne du résultat, arbitraire faute d'ORDER BY : un bug silencieux. Et comme le type de retour change, la seconde version ne peut pas remplacer la première avec CREATE OR REPLACE (voir ci-dessous) : il faut d'abord supprimer la première.

À vérifier Les diapos appellent f_get_salaire_metier('manager'), en minuscules, et obtiennent d'autres salaires : leur table n'est pas celle de la diapo 10. Avec la table du cours, où le métier s'écrit Manager, l'appel en minuscules ne renvoie aucune ligne, car la comparaison de chaînes tient compte de la casse.

Complément Renvoyer des lignes entières

Le type de retour peut être le type ligne d'une table : RETURNS SETOF emp. La fonction s'utilise alors dans le FROM, comme une table paramétrée :

CREATE FUNCTION f_emp_dep (integer) RETURNS SETOF emp AS
    'SELECT * FROM emp WHERE id_dep = $1'
LANGUAGE SQL;

SELECT nom_emp, metier FROM f_emp_dep(10);   -- KING, CLARK, MILLER

Modifier une fonction diapos 78–81

Qu'est-ce que CREATE OR REPLACE permet de modifier ?

  • le corps de la fonction : oui ;
  • le prototype : non. On ne peut changer ni les types d'entrée ni le type de sortie. Il faut supprimer la fonction, ou en créer une autre sous un autre nom.

Si f_get_salaire_metier existe déjà avec RETURNS NUMERIC, la version RETURNS SETOF NUMERIC ci-dessus échoue : cannot change return type of existing function.

Règle Unicité d'une fonction diapo 80

Une fonction est identifiée par son nom, plus le type de ses paramètres d'entrée, plus le nom de ses paramètres d'entrée.

  • Deux types d'entrée différents donnent deux fonctions différentes : f(varchar) et f(integer) coexistent (on parle de surcharge).
  • Renommer un paramètre avec CREATE OR REPLACE est refusé : cannot change name of input parameter "nname". PostgreSQL suggère alors : Use DROP FUNCTION f_nb_objet_dispo(character varying) first.

En résumé : CREATE OR REPLACE sert à modifier le corps de la fonction uniquement ; modifier les entrées revient à créer une nouvelle fonction ; les paramètres de sortie ne se modifient pas.

La commande ALTER FUNCTION modifie le reste. Il faut être propriétaire de la fonction, et identifier celle-ci par son nom et ses paramètres :

-- Renommer la fonction
ALTER FUNCTION f_nb_objet_dispo (name varchar(20)) RENAME TO f_dispo;
-- Changer le propriétaire (il faut pouvoir SET ROLE, et avoir le privilège CREATE)
ALTER FUNCTION f_nb_objet_dispo (name varchar(20)) OWNER TO other;
-- Changer de schéma (il faut avoir le privilège CREATE)
ALTER FUNCTION f_nb_objet_dispo (name varchar(20)) SET SCHEMA public;

SET ROLE et les privilèges sont vus au cours 3.

Supprimer une fonction diapo 82

DROP FUNCTION demande de préciser le nom de la fonction et ses paramètres d'entrée : leur type, mais pas leur nom, et pas le type de sortie.

nath=# drop function which_id;
ERREUR:  erreur de syntaxe sur ou près de « ; »      ← NON : préciser les paramètres
nath=# drop function which_id();
ERREUR:  la fonction which_id() n'existe pas          ← potentiellement OUI, si which_id (void) existe
nath=# drop function which_id(int);
DROP FUNCTION                                        ← OUI !

À vérifier Depuis PostgreSQL 10, DROP FUNCTION which_id; sans parenthèses est accepté si une seule fonction porte ce nom ; sinon, PostgreSQL répond function name "which_id" is not unique. La capture de la diapo vient d'une version plus ancienne. Préciser les types reste la bonne habitude, indispensable dès qu'une fonction est surchargée.

S'entraîner Ajout

Ces exercices ne figurent pas dans le support. Ils portent sur les tables emp et dept du script de la section 3.2, et toutes les solutions ont été exécutées.

Exercice 1 Filtrer et trier

Afficher le nom et le salaire des employés du département 20, du mieux payé au moins bien payé.

Solution proposée 
SELECT nom_emp, sal FROM emp WHERE id_dep = 20 ORDER BY sal DESC;
-- SCOTT 3234.62, FORD 3056.33, JONES 2975.24, ADAMS 1304.67, SMITH 1212.24

Exercice 2 Grouper et filtrer les groupes

Pour chaque département d'au moins 5 employés, afficher le nombre d'employés et le salaire le plus élevé.

Indice

La condition « au moins 5 employés » porte sur un groupe : elle va dans HAVING.

Solution proposée 
SELECT id_dep, count(*) AS nb, max(sal) AS sal_max
FROM emp
GROUP BY id_dep
HAVING count(*) >= 5;
-- 20 | 5 | 3234.62
-- 30 | 6 | 2852.56

Exercice 3 Jointure réflexive

Afficher le nom de chaque employé avec celui de son chef, y compris le président. Puis lister les employés embauchés avant leur chef.

Indice

Joindre emp à elle-même, en la renommant deux fois. Pour garder KING, qui n'a pas de chef, il faut une jointure externe.

Solution proposée 
SELECT e.nom_emp AS employe, c.nom_emp AS chef
FROM emp AS e LEFT JOIN emp AS c ON e.id_chef = c.id_emp;
-- 14 lignes ; KING a un chef NULL

SELECT e.nom_emp AS employe, c.nom_emp AS chef
FROM emp AS e JOIN emp AS c ON e.id_chef = c.id_emp
WHERE e.date_emb < c.date_emb;
-- ALLEN, BLAKE, CLARK, JONES, SMITH, WARD

Dans la seconde requête, une jointure interne suffit : KING n'a pas de chef, il ne peut pas avoir été embauché avant lui.

Exercice 4 Sous-requêtes

a) Les employés payés plus que la moyenne de leur propre métier. b) Le ou les métiers au salaire moyen le plus élevé, sans utiliser ALL.

Solution proposée 
-- a) sous-requête corrélée : la moyenne est recalculée pour le métier de chaque ligne
SELECT nom_emp, metier, sal FROM emp AS e
WHERE sal > (SELECT avg(sal) FROM emp WHERE metier = e.metier);
-- SCOTT (Analyste), BLAKE et JONES (Manager), MILLER (Secretaire), ALLEN et TURNER (Vendeur)

-- b) le maximum des moyennes, calculé sur une table intermédiaire
SELECT metier, avg(sal) FROM emp GROUP BY metier
HAVING avg(sal) = (SELECT max(m) FROM (SELECT avg(sal) AS m FROM emp GROUP BY metier) AS t);
-- President | 5000.00

Exercice 5 Contrainte de clé étrangère

La table emp a été créée sans clé étrangère vers dept. Ajouter cette contrainte, de sorte qu'il soit impossible de supprimer un département qui contient encore des employés. Que se passe-t-il si l'on choisit ON DELETE CASCADE ?

Solution proposée 
ALTER TABLE emp ADD CONSTRAINT fk_emp_dept
    FOREIGN KEY (id_dep) REFERENCES dept (id_dep) ON DELETE RESTRICT;

RESTRICT (ou NO ACTION, la valeur par défaut) fait échouer DELETE FROM dept WHERE id_dep = 10;. Avec ON DELETE CASCADE, la même commande supprimerait silencieusement KING, CLARK et MILLER : un choix dangereux, réservé aux vraies compositions.

Exercice 6 Écrire une fonction

Écrire une fonction f_nb_emp_dep qui renvoie le nombre d'employés d'un département, puis l'utiliser pour afficher l'effectif de chaque département.

Indice

count(*) renvoie un bigint : c'est le type de retour à déclarer.

Solution proposée 
CREATE FUNCTION f_nb_emp_dep (integer) RETURNS bigint AS
    'SELECT count(*) FROM emp WHERE id_dep = $1'
LANGUAGE SQL;

SELECT id_dep, nom_dep, f_nb_emp_dep(id_dep) AS effectif FROM dept ORDER BY id_dep;
-- 10 | Comptabilité | 3
-- 20 | Recherche    | 5
-- 30 | Ventes       | 6

À retenir

L'essentiel

  • Le DDL définit les objets (CREATE, ALTER, DROP), le DML manipule les données (INSERT, UPDATE, DELETE, SELECT).
  • UPDATE et DELETE sans WHERE touchent toute la table ; une suppression est définitive, sauf dans une transaction.
  • SELECT fait la projection, WHERE la sélection. Les jointures s'écrivent dans le FROM ; une jointure réflexive exige des alias.
  • NULL ne se compare pas avec = mais avec IS NULL ; les agrégats l'ignorent ; NOT IN face à un NULL ne renvoie rien.
  • Avec GROUP BY, chaque colonne du SELECT est groupée ou agrégée, et le résultat compte une ligne par groupe.
  • WHERE filtre les lignes avant le regroupement, HAVING filtre les groupes après.
  • Ordre d'exécution : FROM, WHERE, GROUP BY, HAVING, SELECT, ensemblistes, ORDER BY, OFFSET, LIMIT.
  • LIMIT et OFFSET s'utilisent avec ORDER BY, jamais à la place d'un MAX.
  • Une base contient des schémas, qui contiennent les tables ; search_path décide où chercher un nom sans préfixe.
  • Une clé étrangère impose l'ordre des insertions et un comportement ON DELETE / ON UPDATE ; CREATE TABLE AS copie les données sans les contraintes, LIKE la structure sans les données.
  • Une fonction se modifie avec CREATE OR REPLACE (le corps seulement) et s'identifie par son nom et ses types d'entrée ; SETOF pour renvoyer plusieurs lignes.

Auto-évaluation

Quelle différence entre WHERE et HAVING ?

WHERE filtre les lignes, avant le regroupement ; il ne peut pas contenir d'agrégat. HAVING filtre les groupes, après le regroupement ; sa condition porte sur un agrégat ou sur une colonne du GROUP BY.

Pourquoi SELECT nom_emp, avg(sal) FROM emp GROUP BY metier; échoue-t-elle ?

Un groupe de métier contient plusieurs noms : nom_emp n'est ni dans le GROUP BY ni dans un agrégat, et le SGBD ne peut pas choisir lequel afficher.

Que donnent count(*), count(comm) et count(DISTINCT comm) sur la table EMP ?

14 lignes ; 3 commissions non NULL ; 3 valeurs distinctes (300, 500 et 1 400).

Pourquoi un alias défini dans le SELECT n'est-il pas utilisable dans le WHERE ?

Parce que WHERE est exécuté avant SELECT : l'alias n'existe pas encore. Il est en revanche utilisable dans ORDER BY, exécuté après.

DROP TABLE ou DELETE FROM : lequel garde la table ?

DELETE FROM vide la table mais la garde. DROP TABLE supprime la structure et le contenu.

Quelle différence entre CREATE TABLE t AS SELECT … et CREATE TABLE t (LIKE …) ?

La première copie les données sans les contraintes ; la seconde copie la structure (et, selon les options, les contraintes et index) sans les données.

Une vue stocke-t-elle des données ?

Non : seule sa requête est stockée. Elle est rejouée à chaque utilisation, donc toujours à jour.

Peut-on passer une fonction de RETURNS numeric à RETURNS SETOF numeric avec CREATE OR REPLACE ?

Non : le prototype, type de sortie compris, ne se modifie pas. Il faut supprimer la fonction (DROP FUNCTION nom(type)) puis la recréer.
