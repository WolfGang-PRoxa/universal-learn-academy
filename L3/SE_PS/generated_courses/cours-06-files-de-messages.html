Communiquer par messages : les files de messages

Un tube transporte un flot d'octets sans repères, entre des processus qui ont un ancêtre commun ou qui connaissent un nom de fichier. La file de messages, l'un des trois mécanismes IPC d'Unix System V, transporte des messages entiers, chacun muni d'un type, que chaque lecteur peut trier. Ce cours présente ses quatre primitives, msgget, msgsnd, msgrcv et msgctl, puis un exemple complet : un client et deux serveurs qui partagent une seule file.

Le principe de la boîte aux lettres p. 1–2

Avec un tube, ce qu'un processus écrit est lu par le premier lecteur venu, dans l'ordre d'arrivée. Pour que plusieurs processus se partagent un même canal et que chacun n'y prenne que ce qui le concerne, il faut des messages identifiables.

Des messages typés

Définition File de messages

Une file de messages (message queue) implémente le concept de boîte aux lettres (BAL) : un processus peut y déposer des lettres, les messages, pour qu'ils soient lus par d'autres processus, et il peut en extraire les lettres qui lui sont destinées. À chaque message est accolé un type, un entier strictement positif, qui permet aux processus qui extraient les messages de distinguer ceux qui les intéressent.

Une structure de message commence donc par son type, suivi du corps du message, que le programmeur définit librement. Le polycopié donne ce modèle :

struct exemple_msg
{
   int type ;   /* entier > 0 */
   /*
    * corps du message
    */
} ;

À vérifier Le type est déclaré int, mais les primitives attendent un long en tête de la zone (voir msgbuf ci-dessous) : sur une machine 64 bits, où un long fait 8 octets et un int 4, le corps serait décalé. Dans ses propres programmes (p. 5), l'enseignant écrit bien long type, et c'est la forme à retenir.

Les primitives manipulent les messages à travers un type générique :

struct msgbuf
{
   long  mtype ;      /* message type */
   char  mtext[1] ;   /* message text */
};

Ce type ne peut pas être utilisé tel quel.

Complément Pourquoi on ne se sert pas de msgbuf

Son corps ne fait qu'un caractère : msgbuf sert seulement à décrire la forme attendue, un long suivi d'octets. Chaque programme déclare sa propre structure, dont le premier champ est un long et dont le reste est aussi grand qu'il le faut. Les primitives reçoivent un void *, et c'est la longueur passée en paramètre qui leur dit combien d'octets lire après le type.

Un des trois mécanismes IPC

Les files de messages sont l'un des trois mécanismes de communication et de synchronisation entre processus d'un même système, les IPC (Inter-Process Communication). Les deux autres sont la mémoire partagée et les sémaphores. Tous les objets IPC créés peuvent être manipulés par deux commandes du shell :

ipcs
Consulte tous les objets IPC. Le polycopié indique que l'option -m affiche toutes les files de messages actives. À vérifier Sous Linux, c'est -q (queues) qui liste les files de messages ; -m liste les segments de mémoire partagée, et -s les sémaphores.
ipcrm
Supprime un objet IPC. Avec l'option -q msgid, on supprime la file de messages d'identifiant msgid, donné dans la deuxième colonne de ipcs.
$ ipcs -q

------ Message Queues --------
key        msqid      owner      perms      used-bytes   messages
0x000010e1 1          root       666        0            0

$ ipcrm -q 1

Des messages indivisibles, dans l'ordre d'arrivée

Propriété Indivisibilité d'un message

Un message est un objet indivisible : quand un message est déposé dans une BAL, il en est obligatoirement extrait dans sa totalité.

C'est la différence essentielle avec les tubes, qui transfèrent des flots de caractères sans repères : plusieurs caractères peuvent être écrits en un seul write et lus par une suite de read, ou l'inverse. Enfin, une file de messages est gérée comme une file FIFO : parmi les messages qu'un lecteur accepte, il reçoit le plus ancien.

Créer ou retrouver une file : msgget p. 2

Pour que deux processus utilisent la même file, il faut qu'ils puissent la désigner. Comme tout objet IPC, une file de messages est repérée par un identifiant géré par le système, et éventuellement par une clé gérée par l'utilisateur. Des primitives permettent d'obtenir l'identifiant à partir de la clé.

#include <sys/msg.h>
int msgget( key_t cle ,      /* Cle de file de messages */
            int   option ) ; /* Option de creation */

msgget renvoie l'identifiant de la file de messages associée à cle, ou −1 en cas d'échec. Elle crée une nouvelle file si l'une des conditions suivantes est vérifiée :

  • cle vaut IPC_PRIVATE ;
  • cle n'a pas de file de messages associée, et option & IPC_CREAT est vrai.

Sinon, elle renvoie l'identifiant de la file qui existe déjà pour cette clé.

Complément Ce que contient option

  • Les neuf bits de poids faible sont les droits d'accès de la file, comme pour un fichier : 0666 pour tous en lecture et en écriture, 0600 pour le seul propriétaire. Ils ne servent qu'à la création.
  • IPC_CREAT crée la file si la clé n'en a pas.
  • IPC_CREAT | IPC_EXCL exige la création : si la file existe déjà, msgget échoue avec errno = EEXIST. C'est ainsi que le serveur de l'exemple s'assure qu'il est le premier.
  • 0 (ni l'un ni l'autre) retrouve une file existante, et échoue avec ENOENT si la clé n'a pas de file.

Avec IPC_PRIVATE, la file n'a pas de clé : seuls le créateur et ses descendants, qui héritent de la variable contenant l'identifiant, peuvent s'en servir.

Complément Choisir une clé : ftok

Le polycopié passe la clé en paramètre des programmes, sous forme d'entier. Pour éviter que deux applications choisissent la même, on la calcule souvent avec ftok, à partir d'un fichier qui existe et d'un caractère :

#include <sys/ipc.h>
key_t cle = ftok("/home/moi/projet", 'A') ;

Tous les processus qui appellent ftok avec le même fichier et le même caractère obtiennent la même clé.

Envoyer un message : msgsnd p. 2–3

Une fois la file désignée, un processus y dépose un message en donnant l'adresse d'une zone qui commence par le type.

#include <sys/msg.h>
int msgsnd( int          fileid , /* Identifiant de file */
            const void * p_mess , /* Pt sur message a envoyer */
            size_t       lg ,     /* Longueur du message */
            int          option ) ; /* Option d'emission */

Cette primitive envoie dans la file identifiée par fileid le message contenu dans la zone mémoire pointée par p_mess. Cette zone doit contenir :

  • le type du message, un entier strictement positif ;
  • le corps du message.

Attention La longueur ne compte pas le type

Le paramètre lg contient la longueur du corps du message, sans la place occupée par le type. Avec la structure requete_t de l'exemple, on passe sizeof(req_corps_t), et non sizeof(requete_t).

Quand la file est pleine

Une file a une capacité limitée. Quand elle est pleine :

  • si option vaut 0, msgsnd est bloquant : le processus est mis en sommeil, et il sera réveillé quand l'écriture dans la file sera rendue possible. Si un signal interrompt cet appel bloquant et que l'on ne reprend pas les appels système (c'est-à-dire si sa_flags de sigaction ne contient pas SA_RESTART), msgsnd renvoie −1 et errno vaut EINTR ;
  • si option vaut IPC_NOWAIT, msgsnd n'est pas bloquant : la primitive renvoie −1 et positionne errno. Le polycopié indique ENOMSG. À vérifier Sous Linux, msgsnd renvoie EAGAIN dans ce cas, comme le prévoit POSIX ; ENOMSG est l'erreur de msgrcv sur une file sans message du type voulu. L'essai ci-dessous le confirme.

Complément Limites et erreurs

  • Un type nul ou négatif est refusé : msgsnd renvoie −1 avec EINVAL.
  • Sous Linux, un message ne dépasse pas 8 192 octets (/proc/sys/kernel/msgmax), et une file contient au plus 16 384 octets (msg_qbytes, par défaut /proc/sys/kernel/msgmnb). La file est « pleine » quand le nouveau message ferait dépasser cette limite.
  • Si la file est supprimée pendant que l'émetteur attend, il est réveillé avec EIDRM.

L'essai suivant réduit la capacité d'une file à 100 octets, puis y dépose des corps de 60 octets avec IPC_NOWAIT :

$ ./essais
msg_qbytes = 16384
…
msgsnd type 0 : -1, errno EINVAL
pleine apres 1 messages : errno EAGAIN

Recevoir un message : msgrcv p. 3–4

Le lecteur dit quel type de message il attend et quelle place il lui réserve. C'est ce choix du type qui permet à plusieurs processus de partager une seule file.

#include <sys/msg.h>
ssize_t msgrcv( int      fileid , /* Identifiant de la file */
                void   * p_mess , /* Pt sur zone reception */
                size_t   lgmax ,  /* Longueur max prevue */
                long int type ,   /* Type de message attendu */
                int      option ) ; /* Option de reception */

La primitive msgrcv extrait de la file identifiée par fileid un message de type type, et le range dans la zone pointée par p_mess.

Un message trop long

lgmax donne la taille maximale du corps du message que l'on peut extraire.

  • Si le message que l'on veut extraire est trop long :
    • si option contient MSG_NOERROR, le message est extrait dans sa totalité, mais il est tronqué à lgmax octets dans la zone de réception : le reste est perdu ;
    • sinon, msgrcv échoue, avec errno = E2BIG, et le message reste dans la file.
  • Sinon, tout va bien : le message est stocké dans la zone mémoire pointée par p_mess.

Une file sans message du type voulu

Quand la file ne contient pas de message du type souhaité :

  • si option vaut 0, msgrcv est bloquant : le processus est mis en sommeil jusqu'à ce qu'un message du bon type arrive. Si l'appel bloquant est interrompu, msgrcv renvoie −1 et errno vaut EINTR ;
  • si option vaut IPC_NOWAIT, msgrcv n'est pas bloquant : la primitive renvoie −1 et positionne errno à ENOMSG.

Si le message est extrait de la BAL, msgrcv renvoie la longueur du corps du message stocké. Si le message a été tronqué, on ne sait donc pas combien d'octets ont été perdus.

Choisir le message à extraire

Le paramètre type indique quel message on souhaite extraire :

  1. type = 0 : le premier message de la file est extrait, quel que soit son type ;
  2. type > 0 : le premier message de type type est extrait ;
  3. type < 0 : le polycopié indique que le premier message de type \( \le |\mathtt{type}| \) est extrait. À vérifier Linux et POSIX sont plus précis : c'est le premier message du plus petit type parmi ceux de type \( \le |\mathtt{type}| \). Les deux lectures diffèrent quand un message de type 2 précède un message de type 1 (essai ci-dessous). Un type négatif sert ainsi de priorité : les petits types passent d'abord.

Dans les cas 1 et 3, le champ mtype de la zone de réception contient au retour le type du message extrait, ce qui permet de savoir ce que l'on a reçu.

Exemple Ajout Les trois façons de choisir, à l'essai

Un programme dépose dans une file vide des messages de types 2, 1 et 3, dans cet ordre, puis appelle deux fois msgrcv avec le type −2 :

$ ./neg
msgrcv(..., -2, ...) : m1
msgrcv(..., -2, ...) : m2

Le premier appel extrait le message de type 1, bien qu'il soit arrivé après celui de type 2 : c'est le plus petit type \( \le 2 \). Le second extrait celui de type 2. Le message de type 3 reste dans la file.

Sur une autre file qui contient des messages de types 3, 1 et 2, les autres cas donnent :

$ ./essais
…
msg_qnum = 3, msg_cbytes = 9
type -2 : m1 (type 1, 3 octets)
lgmax 2 : -1, Argument list too long
lgmax 2 + MSG_NOERROR : 2, type 3, m3
type 0 : m2 (type 2)
vide + IPC_NOWAIT : -1, errno ENOMSG

« Argument list too long » est le texte de E2BIG : le message m3, de 3 octets avec son '\0', ne tient pas dans 2 octets. Avec MSG_NOERROR, il est extrait, et msgrcv renvoie 2 : le '\0' final est perdu.

Contrôler et supprimer une file : msgctl p. 4

Une file survit aux processus qui l'ont créée. Il faut donc une primitive pour la supprimer, et pour consulter ou modifier ses caractéristiques.

#include <sys/msg.h>
int msgctl( int               fileid , /* Identifiant de la file */
            int               cmd ,    /* Operation a effectuer */
            struct msqid_ds * p_buf ) ; /* Arguments de l'operation */

Cette primitive réalise sur la file d'identifiant fileid l'opération cmd, avec les paramètres p_buf. Les opérations possibles sont :

IPC_RMID
Suppression de la file fileid (p_buf = NULL).
IPC_STAT
Copie dans la zone pointée par p_buf l'entrée de fileid dans la table des files de messages.
IPC_SET
Modifie l'entrée de la file fileid dans la table des files de messages avec la structure pointée par p_buf. Les seuls champs modifiables par un utilisateur ordinaire sont msg_perm.uid, msg_perm.gid et msg_perm.mode.

Une entrée de la table des files de messages a la structure suivante :

struct msqid_ds {
    struct ipc_perm  msg_perm ;   /* structure des droits d'acces */
    struct msg     * msg_first ;  /* ptr sur le 1er message */
    struct msg     * msg_last ;   /* ptr sur le dernier message */
    msglen_t         msg_cbytes ; /* nb total d'octets dans la file */
    msgqnum_t        msg_qnum ;   /* nb de messages dans la file */
    msglen_t         msg_qbytes ; /* nb max d'octets */
    pid_t            msg_lspid ;  /* pid du dernier processus emetteur */
    pid_t            msg_lrpid ;  /* pid du dernier processus recepteur */
    time_t           msg_stime ;  /* date du dernier envoi */
    time_t           msg_rtime ;  /* date de la derniere reception */
    time_t           msg_ctime ;  /* date dernier changement par msgctl */
};

Remarque Ajout La structure vue par un programme Linux

Les pointeurs msg_first et msg_last appartiennent à la table interne du noyau : la structure msqid_ds que voit un programme sous Linux ne les contient pas. Les autres champs y sont, et le nombre de messages en attente se lit dans msg_qnum. Sous Linux, un utilisateur ordinaire peut aussi baisser msg_qbytes avec IPC_SET ; seul l'administrateur peut le relever au-delà de la limite du système.

Attention Ajout Supprimer une file que d'autres utilisent

IPC_RMID supprime la file immédiatement, avec les messages qu'elle contient. Les processus bloqués dans msgsnd ou msgrcv sur cette file sont réveillés, et la primitive renvoie −1 avec errno = EIDRM ; les appels suivants échouent avec EINVAL. C'est ce qui arrive au serveur de décodage de l'exemple quand le serveur d'encodage s'arrête.

Exemple : un client et deux serveurs p. 4–10

L'exemple du polycopié est un client-serveur sur une seule machine. Un serveur encode des chaînes de caractères, un autre les décode, et des clients leur envoient des chaînes. Tous partagent une seule file : ce sont les types qui aiguillent les messages.

Les messages échangés

Les requêtes portent le type du serveur visé, SERVEUR_ENCODAGE (1) ou SERVEUR_DECODAGE (2). Leur corps contient le pid du client et la chaîne. Les réponses portent pour type le pid du client qui a fait la requête : chaque client ne lit ainsi que ses propres réponses.

#ifndef _MESSAGES_H_
#define _MESSAGES_H_

#include <unistd.h>

#define SERVEUR_ENCODAGE 1
#define SERVEUR_DECODAGE 2

typedef struct req_corps
{
     pid_t pid_client ;
     char msg[256] ;
} req_corps_t ;

typedef struct requete
{
     long type ;
     req_corps_t corps ;
} requete_t ;

typedef struct reponse
{
     long type ;
     char msg[256] ;
} reponse_t ;

#endif
#ifndef _SERVEURS_H_
#define _SERVEURS_H_

#define CLE_INTERNE 10

#endif

Astuce Ajout Pourquoi le pid fait un bon type de réponse

Un pid est strictement positif, comme un type doit l'être, et il est unique parmi les processus vivants : deux clients ne peuvent pas attendre le même type. Il ne doit pas non plus valoir 1 ou 2, les types des requêtes : c'est le cas en pratique, car le pid 1 est init et le pid 2 un processus du noyau. Le polycopié appelle serveurs.h « Types des messages échangés », mais ce fichier ne contient que la constante de l'encodage, CLE_INTERNE ; les types sont dans messages.h.

Le serveur d'encodage

Le serveur encode les chaînes envoyées par les clients. Il reçoit les messages de type SERVEUR_ENCODAGE, et répond par des messages dont le type a pour valeur le pid du client. C'est lui qui crée la file, avec IPC_CREAT | IPC_EXCL, et qui la supprime quand on l'arrête par SIGINT ou SIGQUIT.

#include <stdio.h>
#include <stdlib.h>
#include <sys/msg.h>
#include <string.h>
#include <signal.h>
#include <messages.h>
#include <serveurs.h>

/* variable globales */
int fileid ;

/* Handler pour Arret du serveur */
void hand_arret( int sig )
{
     msgctl( fileid , IPC_RMID , 0 ) ;
     printf("Terminaison du serveur\n");
     exit(0);
}

/* On suppose que c'est le serveur d'encodage qui doit creer la BAL */
int
main( int nb_arg , char * tab_arg[] )
{
     int filecle ;
     int i , p ;
     requete_t requete ;
     reponse_t reponse ;
     /*-----*/

     if( nb_arg != 2 )
     {
          fprintf( stderr , "usage : %s <cle de file>\n" , tab_arg[0] );
          exit(-1);
     }

     if( sscanf( tab_arg[1] , "%d" , &filecle) != 1 )
     {
          fprintf( stderr , "%s : erreur , mauvaise cle de file (%s)\n" ,
                   tab_arg[0] , tab_arg[1] ) ;
          exit(-2);
     }

     signal( SIGINT , hand_arret ) ;
     signal( SIGQUIT , hand_arret ) ;

     /* Creation de la file de messages */
     if( ( fileid = msgget( filecle , IPC_CREAT | IPC_EXCL | 0666 ) ) == -1 )
     {
          perror("pb creation file ") ;
          exit(-3);
     }

     while(1)
     {
          /* Attente requete d'un client */
          if( msgrcv( fileid ,
                      &requete , sizeof(req_corps_t) ,
                      SERVEUR_ENCODAGE ,
                      0 ) == -1 )
          {
               perror("Pb msgrcv ") ;
               exit(-4);
          }

          printf("%s : message recu = %s\n" , tab_arg[0] , requete.corps.msg ) ;
          /* Encodage du message de la requete */
          p = ( requete.corps.pid_client * CLE_INTERNE ) % 26 ;
          for( i=0 ; i < strlen(requete.corps.msg) ; i++ )
               requete.corps.msg[i] = ( requete.corps.msg[i] + p ) ;

          /* Envoi du message crypte au client */
          reponse.type = requete.corps.pid_client ;
          strcpy( reponse.msg , requete.corps.msg ) ;

          if( ( msgsnd( fileid ,
                        &reponse , strlen(reponse.msg)+1 ,
                        0 ) ) == -1 )
          {
               perror("Pb msgsnd ") ;
               exit(-5);
          }
          printf("%s : message envoye = %s\n" , tab_arg[0] , requete.corps.msg ) ;
     }
}

L'encodage est un décalage de César : chaque caractère est augmenté de \( p = (10 \times \mathit{pid}) \bmod 26 \), qui dépend du client. La réponse n'envoie que les octets utiles de la chaîne, '\0' compris (strlen + 1), alors que la requête envoie tout le corps.

Le serveur de décodage

Le serveur de décodage fait l'inverse : il reçoit les messages de type SERVEUR_DECODAGE, retranche le même décalage, et répond au client par le même procédé. Il ne crée pas la file : il retrouve celle du serveur d'encodage, avec msgget(filecle, 0), et doit donc être lancé après lui.

Le programme complet du serveur de décodage 
#include <stdio.h>
#include <stdlib.h>
#include <sys/msg.h>
#include <string.h>
#include <signal.h>
#include <messages.h>
#include <serveurs.h>

/* variable globales */

{

     }

Les commentaires « Creation de la file de messages » et « Envoi du message crypte » et le message « pb recherhe file » sont ceux du polycopié, recopiés tels quels : ici, la file est seulement recherchée, et le message envoyé est décodé.

Le client

Le client retrouve la file, envoie une chaîne au serveur d'encodage, attend la réponse dont le type est son pid, puis renvoie la chaîne encodée au serveur de décodage et attend de nouveau sa réponse.

#include <stdio.h>
#include <stdlib.h>
#include <sys/msg.h>
#include <string.h>
#include <messages.h>

int
main( int nb_arg , char * tab_arg[] )
{
     int filecle ;
     requete_t requete ;
     reponse_t reponse ;
     int fileid ;
     /*-----*/

     if( nb_arg != 2 )
     {
          fprintf( stderr , "usage : %s <cle de file>\n" , tab_arg[0] );
          exit(-1);
     }

     if( sscanf( tab_arg[1] , "%d" , &filecle) != 1 )
     {
          fprintf( stderr , "%s : erreur , mauvaise cle de file (%s)\n" ,
                   tab_arg[0] , tab_arg[1] ) ;
          exit(-2);
     }

     /* Recherche de la file de messages */
     if( ( fileid = msgget( filecle , 0 ) ) == -1 )
     {
          perror("pb recherche file ") ;
          exit(-3);
     }

     /* Saisie d'un message */
     requete.type = SERVEUR_ENCODAGE ;
     requete.corps.pid_client = getpid() ;
     printf("Saisissez le message a encoder\n") ;
     scanf( "%s" , requete.corps.msg ) ;

     /* Envoi du message en clair au serveur */
     if( ( msgsnd( fileid ,
                   &requete , sizeof(req_corps_t) ,
                   0 ) ) == -1 )
     {
          perror("Pb msgsnd ") ;
          exit(-4);
     }

     /* Attente reponse du serveur */
     if( msgrcv( fileid ,
                 &reponse , sizeof(reponse.msg) ,
                 requete.corps.pid_client ,
                 0 ) == -1 )
     {
          perror("Pb msgrcv ") ;
          exit(-5);
     }

     printf("Message encode = %s\n" , reponse.msg ) ;

     /* Envoi du message encode au serveur decodage */
     requete.type = SERVEUR_DECODAGE ;
     requete.corps.pid_client = getpid() ;
     strcpy( requete.corps.msg , reponse.msg ) ;

     if( ( msgsnd( fileid ,
                   &requete , sizeof(req_corps_t) ,
                   0 ) ) == -1 )
     {
          perror("Pb msgsnd ") ;
          exit(-4);
     }

     /* Attente reponse du serveur */
     if( msgrcv( fileid ,
                 &reponse , sizeof(reponse.msg) ,
                 requete.corps.pid_client ,
                 0 ) == -1 )
     {
          perror("Pb msgrcv ") ;
          exit(-5);
     }
     printf("Message decode = %s\n" , reponse.msg ) ;

     exit(0);
}

Compilation et exécution

Ajout Les programmes incluent <messages.h> et <serveurs.h> entre chevrons : ces fichiers ne sont pas dans les répertoires du système, et il faut ajouter le répertoire courant à la recherche avec -I.. On lance le serveur d'encodage, puis celui de décodage, en arrière-plan, avec la même clé (ici 4321), puis un client. cat -v rend visibles les caractères que l'encodage a rendus non imprimables.

$ gcc -I. serveur_encodage.c -o serveur_encodage
$ gcc -I. serveur_decodage.c -o serveur_decodage
$ gcc -I. client.c -o client
$ ./client 4321

$ ./serveur_encodage 4321 > enc.log &
$ ./serveur_decodage 4321 > dec.log &
$ ipcs -q

0x000010e1 5          root       666        0            0
$ echo bonjour | ./client 4321 | cat -v
Saisissez le message a encoder
Message encode = tM-^AM-^@|M-^AM-^GM-^D
Message decode = bonjour
$ ./serveur_encodage 4321
pb creation file : File exists
$ kill -INT %1
$ cat -v enc.log dec.log
./serveur_encodage : message recu = bonjour
./serveur_encodage : message envoye = tM-^AM-^@|M-^AM-^GM-^D
Terminaison du serveur
./serveur_decodage : message recu = tM-^AM-^@|M-^AM-^GM-^D
./serveur_decodage : message envoye = bonjour
Pb msgrcv : Identifier removed

La clé 4321 s'affiche en hexadécimal dans ipcs (0x10e1). Un client lancé avant les serveurs ne trouve pas la file (ENOENT), et un second serveur d'encodage est refusé par IPC_EXCL (EEXIST). Quand le serveur d'encodage supprime la file, le serveur de décodage, bloqué dans msgrcv, s'arrête sur EIDRM (« Identifier removed »).

Attention Ajout Ce que l'exemple simplifie

  • Le décalage déborde. Pour ce client, \( p = 18 \) : 'b' devient 't', mais 'o' (111) devient 129, au-delà des caractères ASCII. Le texte encodé n'est pas lisible, ce qui n'empêche pas le décodage de retrouver la chaîne. Un octet qui deviendrait nul couperait en revanche la chaîne au décodage.
  • Le handler n'est pas sûr. printf et exit ne font pas partie des fonctions que l'on peut appeler sans risque dans un handler (cours 3). On préfère y positionner un indicateur, ou appeler write puis _exit.
  • La saisie n'est pas bornée. scanf("%s", …) écrit au-delà des 256 caractères de msg si la chaîne est plus longue ; "%255s" l'évite.
  • Le serveur de décodage ne supprime rien en temps normal : seul le serveur d'encodage crée et détruit la file. Si un serveur meurt sans passer par son handler (par SIGKILL), la file reste : on la retire avec ipcrm -q.

Exemple Ajout Un père et son fils

Un exemple plus court montre le tri par type. Le père dépose un message de type 1, puis un de type 2 ; le fils demande d'abord le type 2, puis le type 1. La clé vient de ftok.

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>
#include <sys/msg.h>

typedef struct
{
     long type ;            /* > 0 */
     char texte[64] ;       /* corps du message */
} message_t ;

int main(void)
{
     key_t cle = ftok(".", 'A') ;          /* cle calculee a partir d'un fichier existant */
     int fileid = msgget(cle, IPC_CREAT | 0600) ;
     message_t m ;

     if (fileid == -1) { perror("msgget") ; exit(1) ; }

     if (fork() == 0)
     {
          /* Fils : lit les messages de type 2, puis de type 1 */
          msgrcv(fileid, &m, sizeof(m.texte), 2, 0) ;
          printf("fils : type %ld, %s\n", m.type, m.texte) ;
          msgrcv(fileid, &m, sizeof(m.texte), 1, 0) ;
          printf("fils : type %ld, %s\n", m.type, m.texte) ;
          exit(0) ;
     }

     /* Pere : depose un message de type 1, puis un de type 2 */
     m.type = 1 ; strcpy(m.texte, "premier depose") ;
     msgsnd(fileid, &m, strlen(m.texte) + 1, 0) ;
     m.type = 2 ; strcpy(m.texte, "second depose") ;
     msgsnd(fileid, &m, strlen(m.texte) + 1, 0) ;

     wait(NULL) ;
     msgctl(fileid, IPC_RMID, NULL) ;      /* sinon la file survit au programme */
     return 0 ;
}
$ ./pere_fils
fils : type 2, second depose
fils : type 1, premier depose

Le fils reçoit les messages dans l'ordre de ses demandes, et non dans l'ordre des dépôts. S'il démarre avant que le père ait déposé le message de type 2, il attend dans msgrcv, même si le message de type 1 est déjà là.

Exercices Ajout

Ces exercices vérifient la lecture du cours. Le TD sur les files de messages (td_rpc_file_messages.pdf, une bibliothèque de fonctions partagée à la manière des RPC) les prolonge, sur papier.

Exercice 1 Quel message sort ?

Une file contient, dans l'ordre d'arrivée, des messages de types 5, 3, 7, 3 et 1. Pour chacun des appels suivants, faits chacun sur cette file intacte, quel message est extrait ? On note les messages par leur rang d'arrivée (1er à 5e).

  1. msgrcv(id, &m, lg, 0, 0)
  2. msgrcv(id, &m, lg, 3, 0)
  3. msgrcv(id, &m, lg, -4, 0)
  4. msgrcv(id, &m, lg, 4, IPC_NOWAIT)
Indice

Avec un type négatif, on cherche le plus petit type qui ne dépasse pas la valeur absolue, puis le premier message de ce type.

Solution proposée
  1. Le 1er message (type 5) : avec 0, on prend le plus ancien.
  2. Le 2e (le premier de type 3).
  3. Le 5e : parmi les types \( \le 4 \) (3, 3 et 1), le plus petit est 1. Avec la lecture du polycopié (« le premier de type \( \le 4 \) »), on aurait répondu le 2e.
  4. Aucun : il n'y a pas de message de type 4. msgrcv renvoie −1 avec ENOMSG ; sans IPC_NOWAIT, le processus attendrait.

Exercice 2 Longueurs

Dans l'exemple, le client envoie sa requête avec la longueur sizeof(req_corps_t), et le serveur d'encodage répond avec strlen(reponse.msg)+1. Le client reçoit la réponse avec lgmax = sizeof(reponse.msg).

  1. Que se passerait-il si le client envoyait sa requête avec sizeof(requete_t) ?
  2. Pour une chaîne de 7 caractères, quelle valeur msgrcv renvoie-t-elle au client ?
  3. Pourquoi le client n'a-t-il pas besoin de MSG_NOERROR ?
Solution proposée
  1. sizeof(requete_t) compte aussi le long du type : msgsnd lirait 8 octets au-delà de la structure, et le serveur, qui ne prévoit que sizeof(req_corps_t) octets, échouerait avec E2BIG.
  2. 8 : les 7 caractères et le '\0' final, la longueur du corps reçu.
  3. Le serveur n'envoie jamais plus que strlen + 1 octets d'une chaîne qui tient dans 256 octets : la réponse tient toujours dans reponse.msg.

Exercice 3 Vider une file

Écrire une fonction int vider(int fileid) qui extrait tous les messages présents dans une file, sans jamais rester bloquée, et renvoie le nombre de messages extraits. Les corps font au plus 256 octets.

Indice

Type 0 pour accepter tout message, IPC_NOWAIT pour ne pas attendre, et MSG_NOERROR au cas où un message serait plus long que prévu.

Solution proposée 
#include <sys/msg.h>

int vider(int fileid)
{
     struct { long type ; char corps[256] ; } m ;
     int n = 0 ;
     while (msgrcv(fileid, &m, sizeof(m.corps), 0, IPC_NOWAIT | MSG_NOERROR) != -1)
          n++ ;
     return n ;   /* la boucle s'arrete sur ENOMSG : la file est vide */
}

À retenir

L'essentiel

  • Une file de messages est une boîte aux lettres : on y dépose des messages, chacun muni d'un type entier strictement positif.
  • Un message commence par un long (le type), suivi d'un corps défini par le programme ; msgbuf n'en décrit que la forme.
  • Un message est indivisible, à la différence du flot d'un tube, et la file est gérée en FIFO.
  • msgget(cle, option) crée la file (IPC_PRIVATE, ou IPC_CREAT sur une clé libre) ou retrouve celle de la clé ; IPC_EXCL exige la création.
  • msgsnd prend la longueur du corps seul, sans le type ; il attend si la file est pleine, sauf avec IPC_NOWAIT.
  • msgrcv choisit le message par son type : 0 pour le premier, \( t \gt 0 \) pour le premier de type \( t \), \( t \lt 0 \) pour le plus petit type \( \le |t| \).
  • Un message trop long fait échouer msgrcv (E2BIG), sauf avec MSG_NOERROR, qui le tronque.
  • Sans message du type voulu, msgrcv attend, ou renvoie −1 avec ENOMSG sous IPC_NOWAIT.
  • Une file survit aux processus : on la supprime par msgctl(id, IPC_RMID, NULL) ou par ipcrm -q ; ipcs -q les liste.
  • Une seule file suffit pour un client-serveur : les requêtes portent le type du serveur, les réponses le pid du client.

Auto-évaluation

Qu'apporte le type d'un message ?

Il permet à chaque processus de n'extraire que les messages qui le concernent, alors que tous partagent la même file.

Un émetteur dépose deux messages de 10 octets. Le récepteur peut-il lire les 20 octets en un seul appel ?

Non : chaque msgrcv extrait un seul message, en entier. Avec un tube, un seul read pourrait lire les 20 octets.

Quelle longueur passe-t-on à msgsnd ?

Celle du corps du message, sans le long du type.

À quoi sert IPC_CREAT | IPC_EXCL ?

À créer la file en exigeant qu'elle n'existe pas encore : sinon, msgget échoue avec EEXIST. Le premier serveur lancé est ainsi le seul créateur.

Que fait msgrcv avec type = -3 ?

Il extrait le premier message du plus petit type parmi les types 1, 2 et 3 présents dans la file, et il attend s'il n'y en a aucun.

Un programme se termine sans appeler msgctl(…, IPC_RMID, …). Que devient sa file ?

Elle reste dans le système, avec ses messages, visible par ipcs -q, jusqu'à ce qu'on la supprime avec ipcrm -q ou jusqu'au redémarrage.

Pourquoi le client de l'exemple attend-il un message de type égal à son pid ?

Parce que les serveurs répondent avec ce type : un client ne prend ainsi que ses propres réponses, même si plusieurs clients attendent en même temps.

Un serveur est bloqué dans msgrcv quand un autre supprime la file. Que se passe-t-il ?

Il est réveillé : msgrcv renvoie −1 avec errno = EIDRM.
