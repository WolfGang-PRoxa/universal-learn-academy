Sécurité informatique TP 5 · L2 S4

Connexion TLS à un serveur web

On installe un petit site PHP avec authentification sous Apache2, on constate dans Wireshark que le login et le mot de passe passent en clair, puis on crée un certificat auto-signé, on passe le site en HTTPS et on lit la négociation TLS. En salle, tout se fait sur un Raspberry Pi ; chez soi, un conteneur Docker en tient lieu.

Objectifs

  • Configurer un site sous Apache2 avec a2ensite, a2dissite, a2enmod.
  • Créer un certificat auto-signé avec OpenSSL et l'utiliser pour HTTPS (cours 3).
  • Lire dans une capture la version de TLS, les suites de chiffrement et le mode de partage du secret négociés (cours 3).

À rendre

  • Rien à déposer : chaque étape est validée par l'enseignant pendant la séance, en binôme.

Le sujet p. 1–3

On travaille en administrateur sur des copies, jamais sur les fichiers originaux. Les étapes 1 et 5 (brancher puis ranger le Raspberry) ne concernent que la salle de TP.

  1. Site non sécurisé. Vérifier que http://localhost répond, étudier /etc/apache2 et les commandes a2enmod, a2dismod, a2ensite, a2dissite (man). Créer /var/www/tp5 et y copier les deux scripts PHP de la clé USB. Dupliquer sites-available/000-default.conf en sitetp5.conf, le faire pointer sur tp5, activer ce site et désactiver le site par défaut, puis redémarrer Apache (sudo systemctl restart apache2). Donner au site le droit d'écrire dans tp5 (sudo chgrp www-data tp5, sudo chmod g+w tp5).
  2. Tester et capturer. Créer un compte et se connecter, capturer l'échange avec Wireshark : le login et le mot de passe doivent apparaître en clair dans le protocole HTTP.
  3. Site sécurisé. Lire la documentation d'Apache (« Exemple de configuration basique » du document 2, trois premières questions « Certificats » de la FAQ, document 4) et sites-available/default-ssl.conf. Créer avec openssl un certificat auto-signé, ranger le certificat dans /etc/ssl/certs et la clé privée dans /etc/ssl/private. Dupliquer default-ssl.conf en sitetp5ssl.conf, l'adapter, activer le module ssl et le nouveau site.
  4. Tester et capturer en HTTPS (https://localhost), filtrer sur TLS et relever : les versions de TLS proposées par le client et celle choisie par le serveur, les suites de chiffrement proposées et celle choisie, le mode de partage du secret proposé (PSK, (EC)DHE ou les deux) et celui choisi.
  5. Revenir à la configuration initiale : supprimer le site, le certificat, la clé privée, sitetp5.conf et sitetp5ssl.conf, et remettre les modules et sites d'origine avec les commandes a2*.

Le refaire sans Raspberry Pi

Le dossier TP/TP5/ contient un conteneur Docker qui joue le rôle du Raspberry : Ubuntu avec Apache2, PHP, OpenSSL, tcpdump et la documentation man, Apache déjà lancé avec son site par défaut, et la « clé USB » de l'encadrant montée dans /media/cle-usb. Le TP s'y fait avec les commandes de l'énoncé, sudo systemctl restart apache2 compris. Il faut Docker : Docker Desktop sous Windows, le paquet docker.io sous Ubuntu.

Dans Wireshark, le filtre d'affichage http montre la requête POST et ses champs en clair ; le filtre tls.handshake isole le ClientHello et le ServerHello, où se lisent les versions (extension supported_versions), les suites de chiffrement et le partage du secret (extensions key_share et pre_shared_key). Les captures sont faites dans le conteneur, sur les ports 80 et 443 : l'interface loopback de Windows n'a pas besoin d'être capturée.

Complément Sans Docker : Apache dans WSL

Faute de Docker, le TP marche aussi dans WSL (Ubuntu), qui est un Linux complet. On y installe une fois ce qu'a le Raspberry :

$ sudo apt install apache2 libapache2-mod-php openssl tshark
$ sudo service apache2 start

Le site répond alors sur http://localhost depuis le navigateur de Windows. Si systemctl refuse de fonctionner (WSL sans systemd), sudo service apache2 restart le remplace. La capture se fait avec sudo tshark -i any -w /tmp/http.pcap, que l'on copie ensuite côté Windows pour l'ouvrir dans Wireshark. À la fin, l'étape 4 de l'énoncé remet Apache dans son état initial.

À retenir

Apache et TLS

  • Sous Debian et Ubuntu, Apache sépare ce qui existe (sites-available, mods-available) de ce qui est actif (sites-enabled, mods-enabled) ; les commandes a2* ajoutent ou retirent les liens, et Apache doit être redémarré ensuite.
  • Sans TLS, un formulaire envoie login et mot de passe en clair dans la requête HTTP : tout observateur du réseau les lit.
  • Un certificat auto-signé permet de chiffrer, mais n'authentifie pas le serveur, puisqu'aucune autorité de certification ne s'en porte garante : le navigateur prévient.
  • La clé privée reste dans /etc/ssl/private, lisible par l'administrateur seulement ; le certificat, public, va dans /etc/ssl/certs.
  • Dans le handshake, le client propose (versions, suites, partage du secret) dans le ClientHello, le serveur choisit dans le ServerHello.

Auto-évaluation

Que fait a2ensite sitetp5, concrètement ?

Il crée dans sites-enabled un lien symbolique vers sites-available/sitetp5.conf ; a2dissite le supprime. Le fichier lui-même n'est pas touché.

Pourquoi le navigateur affiche-t-il un avertissement sur https://localhost ?

Le certificat est signé par sa propre clé et non par une autorité que le navigateur connaît : la connexion est chiffrée, mais rien ne prouve qu'on parle au bon serveur.

En TLS 1.3, où lit-on la version réellement négociée ?

Dans l'extension supported_versions du ServerHello : le vieux champ de version de l'en-tête vaut toujours 0x0303 (TLS 1.2), par compatibilité.

Une fois en HTTPS, que voit encore un observateur du réseau ?

Les adresses IP, les ports, la taille et le rythme des échanges, et le nom du site, envoyé en clair dans l'extension SNI du ClientHello. Le contenu (URL, formulaire, cookies) est chiffré.
