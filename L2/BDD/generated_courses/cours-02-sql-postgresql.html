SQL avec PostgreSQL

Le modèle relationnel est prêt : il faut maintenant le faire vivre dans un SGBD. Ce cours présente le langage SQL et le client de PostgreSQL, puis les trois familles de commandes utilisées en TP : définir les tables (CREATE, ALTER, DROP), modifier les données (INSERT, UPDATE, DELETE) et les interroger (SELECT).

SQL et le vocabulaire des bases relationnelles diapos 1–7

Le cours suit un plan habituel : un bref historique du SQL, la différence entre la norme, le langage et ses implémentations, la présentation de PostgreSQL… et, plus tard, les jointures. Mais d'abord, il faut s'accorder sur les mots.

Un peu d'histoire diapo 4

  • 1960–1970 : bases de données hiérarchiques (liens 1 à *) et bases de données en réseau (liens * à *).
  • 1970 : Edgar Frank Codd publie « A Relational Model of Data for Large Shared Data Banks » (revue de l'ACM). Le modèle est fondé sur la logique des prédicats du premier ordre ; c'est le fondement de l'algèbre relationnelle.
  • 1970–1975 : première version de SQL, développée chez IBM. À vérifier La diapo écrit « 1070-1975 », faute de frappe pour 1970.
  • 1979 : Relational Software, Inc. (futur Oracle) sort la première version commerciale.
  • 1986 : SQL est normalisé par l'ANSI, puis par l'ISO en 1987.

Les concepts de base diapos 5–7

Table table
L'implémentation concrète d'un schéma de relation : une structure de données formée de colonnes et de lignes.
Enregistrement, ligne row, record
Une instance d'entité ou d'association : un tuple.
Attribut, colonne column
Une caractéristique d'un élément.
Champ, cellule field
La donnée, plus petit élément d'information insécable : l'intersection d'une ligne et d'une colonne.
Clé primaire primary key
L'ensemble des attributs qui assure l'unicité d'un enregistrement.
Clé étrangère foreign key
Un ensemble d'attributs d'une table dont la valeur est définie et unique dans une autre table (souvent sa clé primaire).
Contrainte constraint
Un mécanisme de contrôle de validité (type, unicité, valeur non nulle, fonction trigger…), qui assure la précision, la logique et la validité des données.

L'environnement PostgreSQL diapos 8–9

PostgreSQL fonctionne en client-serveur : le serveur garde les bases, et l'on s'y connecte avec un client. En TP, le client est psql, dans un terminal, et le serveur du département s'appelle erebor.

Se connecter avec psql diapo 8

$ psql -U user -d database -h host
  • -U : l'utilisateur PostgreSQL ;
  • -d : le nom de la base de données ;
  • -h : le nom de la machine qui héberge le serveur PostgreSQL (pour nous, erebor).

Sur la diapo, la connexion donne ceci ; l'invite nath=# attend ensuite des commandes.

$ psql -U nath
Password for user nath:
psql (9.4.19)
Type "help" for help.

nath=#

Deux sortes de commandes diapo 9

Dans psql, on tape soit des commandes PostgreSQL, qui commencent toutes par un antislash (voir le fichier d'aide PostgreSQL sur UMTICE), soit des commandes SQL, sans antislash et terminées par un point-virgule.

À vérifier La diapo donne \dt nom_table pour les détails d'une table. \dt nom_table ne fait que lister la table si elle existe ; c'est \d nom_table qui affiche sa structure.

Astuce Quitter et relancer

Ajout \q quitte psql. Une commande SQL qui semble ne rien faire attend souvent son point-virgule : l'invite passe de =# à -# tant que la commande n'est pas terminée. \! commande exécute une commande Unix sans quitter psql (question 9 du TP 1).

Le langage SQL diapos 10–14

SQL est le langage commun des SGBD relationnels. Il a une norme, mais chaque SGBD l'implémente à sa façon, et il ne ressemble pas aux langages de programmation que l'on connaît.

Définition SQL diapo 10

SQL (Structured Query Language) est le langage de communication avec un SGBD relationnel, pour accéder aux données et les gérer.

  • Un langage normalisé n'est pas un langage implémenté : la norme a connu de nombreuses versions (SQL-86, SQL-89, SQL-92, SQL:1999, SQL:2003, SQL:2008, SQL:2011, SQL:2016), et chaque SGBD en implémente une partie.
  • En plus, chaque SGBD a son propre langage : PL/pgSQL pour PostgreSQL, par exemple.

Ce que SQL n'est pas diapo 11

SQL n'est pas un langage procédural comme C : c'est un langage déclaratif. On ne code pas comment obtenir ce que l'on veut ; on dit « simplement » ce que l'on veut. C'est le SGBD relationnel qui détermine comment l'obtenir de façon optimale.

Un langage fortement typé diapo 12

  • Une donnée a un type, ce qui rejoint la 1NF (à discuter).
  • Un type définit un ensemble d'opérations applicables : on additionne des nombres, on concatène des chaînes.
  • Le type est une contrainte, fixée lors de la création de la table : il est important d'y penser dès la modélisation.
  • PostgreSQL a plus d'une trentaine de types, certains fondés sur une norme ISO, d'autres non standard, ce qui pose la question de la compatibilité avec les autres SGBD.

La valeur NULL diapo 13

Définition NULL diapo 13

Le mot-clé NULL est une méta-valeur qui représente une absence de valeur.

  • On peut l'affecter à tout champ, quel que soit son type, sauf si une contrainte l'interdit.
  • NULL n'est ni la valeur booléenne false, ni la chaîne de caractères vide.
  • C'est la valeur par défaut d'un champ, si elle est autorisée et si aucune autre valeur par défaut n'a été définie à la création de la table.

Attention NULL ne se compare pas

Ajout Une comparaison avec NULL ne vaut jamais vrai : sur la table EMP, WHERE comm = NULL ne renvoie aucune ligne, alors que dix employés n'ont pas de commission. Pour tester l'absence de valeur, on écrit comm IS NULL (section 6). De même, un calcul qui contient NULL donne NULL.

Complément Les noms habituels

À vérifier Les rôles de DQL et DCL semblent décalés sur la diapo. Dans la classification la plus courante : le DCL gère les droits d'accès (GRANT, REVOKE) ; le TCL (Transaction Control Language) gère les transactions (BEGIN, COMMIT, ROLLBACK) ; le DQL, quand on le distingue, désigne l'interrogation, c'est-à-dire SELECT, que ce cours range dans le DML (diapo 31).

Définir les tables : le DDL diapos 15–29

Avant de stocker la moindre donnée, il faut créer les tables du modèle relationnel, avec leurs types et leurs contraintes. Ce semestre, on ne manipule que des tables, avec trois commandes : CREATE (création d'un nouvel « objet »), ALTER (modification) et DROP (suppression). Référence : documentation PostgreSQL, chapitre 5 (« Définition des données »), sections 5.1 à 5.4 et 5.6.

Créer une table diapos 17–18

Pour définir une nouvelle table, on choisit son nom, puis, pour chaque attribut, son nom, son type et ses contraintes.

CREATE TABLE table_name (
    column1 data_type PRIMARY KEY,  -- Clé primaire
    column2 data_type,              -- Autres colonnes
    column3 data_type
);

Complément Deux types absents du tableau, et serial

  • date : une date sans heure, écrite '1981-11-17' (année, mois, jour).
  • numeric(p, s) (alias decimal) : un nombre décimal exact de p chiffres, dont s après la virgule. numeric(7,2) va jusqu'à 99 999,99 : c'est le type des salaires, car un flottant arrondit les centimes.
  • serial n'est pas un vrai type : PostgreSQL crée un compteur, et la colonne prend la valeur suivante quand on ne la donne pas. Le cours 4 montre l'écriture normalisée, GENERATED AS IDENTITY.

Les contraintes de colonne diapos 19–20

Une contrainte est une règle appliquée à une colonne pour garantir l'intégrité des données : elle empêche les erreurs et les incohérences dans la base (documentation PostgreSQL, chapitre 5.4).

Mots-clés des contraintes (diapo 19)
Mot-cléGarantie
NOT NULLLa colonne ne peut pas contenir de valeur NULL.
UNIQUEChaque valeur de la colonne est unique.
DEFAULTValeur par défaut de la colonne quand aucune valeur n'est spécifiée.
CHECKLes valeurs de la colonne satisfont une condition.
PRIMARY KEYLa colonne identifie de manière unique chaque enregistrement.
FOREIGN KEYLes valeurs de la colonne correspondent à celles d'une autre table.

Exemple Des employés dans une entreprise diapo 20

CREATE TABLE emp (
    id_emp   serial PRIMARY KEY,
    nom_emp  varchar(10) UNIQUE,
    metier   varchar(10) NOT NULL,
    id_chef  integer DEFAULT 0,
    date_emb date,
    sal      numeric(7,2) CHECK (sal > 0),
    comm     numeric(7,2)
);

À vérifier La diapo met une virgule après comm numeric(7,2), juste avant la parenthèse fermante : PostgreSQL refuse alors toute la commande (syntax error at or near ")"). Elle est retirée ici.

Ajout Une fois la table créée, PostgreSQL refuse un salaire négatif (violates check constraint "emp_sal_check"), un deuxième employé nommé KING (violates unique constraint "emp_nom_emp_key") et un employé sans métier (violates not-null constraint). Un employé inséré sans id_emp reçoit 1, puis 2… grâce à serial, et sans id_chef reçoit 0.

Les contraintes de table diapos 21–22

Quand une contrainte porte sur plusieurs colonnes, on l'écrit après les colonnes, comme un élément de la table. Les mots-clés sont UNIQUE, CHECK, PRIMARY KEY et FOREIGN KEY.

CREATE TABLE products (
    product_id INT,
    price DECIMAL(10, 2),
    quantity INT,
    CHECK (price > 0 AND quantity >= 0)
);

CREATE TABLE orders (
    order_id INT,
    product_id INT,
    -- Clé primaire composite
    PRIMARY KEY (order_id, product_id)
);

CREATE TABLE order_items (
    order_id INT,
    product_id INT,
    quantity INT,
    -- Clé étrangère composite
    FOREIGN KEY (order_id, product_id)
        REFERENCES orders (order_id, product_id)
);

Complément Clé composite

Une clé primaire composite se déclare obligatoirement en contrainte de table : écrire PRIMARY KEY derrière deux colonnes déclarerait deux clés primaires, ce qui est interdit. De même, une clé étrangère qui référence une clé composite reprend toutes ses colonnes, dans le même ordre. Avec ces tables, la ligne (1, 11, 3) est refusée dans order_items tant que la commande (1, 11) n'existe pas dans orders.

Un exemple : du modèle entité-association au modèle relationnel diapos 23–24

Sa traduction en modèle relationnel, avec les règles du cours 1 :

Personne(id_pers, nom, prenom)

Résidence(#id_pers, #id_adresse)

Acteur(#id_pers, #id_film)

Réalisateur(#id_pers, #id_film)

Film(id_film, titre, année, duree)

Projection(#id_film, #id_salle)

Salle(#id_cinema, id_salle, nom_salle, capacité)

Adresse(id_adresse, numero, voie, code_postal, ville)

Cinema(id_cinema, nom_cinema, #id_adresse)

À vérifier La clé primaire de Salle est (id_cinema, id_salle) : la salle est identifiée relativement à son cinéma. La clé étrangère de Projection vers Salle doit donc comprendre les deux colonnes, soit Projection(#id_film, #id_cinema, #id_salle). Écrite avec id_salle seul, comme sur la diapo, PostgreSQL la refuse (there is no unique constraint matching given keys for referenced table "salle").

Exercice 1 Créer les premières tables diapo 24

On veut créer les quatre premières tables : Personne(id_pers, nom, prenom), Acteur(#id_pers, #id_film), Réalisateur(#id_pers, #id_film) et Film(id_film, titre, année, duree).

  1. Peut-on créer les tables dans cet ordre ?
  2. A-t-on vraiment besoin des contraintes ?
  3. Et si l'on change des noms d'attributs, cela dérange-t-il ?
  4. Et si l'on change l'ordre des attributs ?
  5. Et si l'on se trompe sur le nom ou le type d'un attribut, ou si l'on en oublie un ?
Indice

Une clé étrangère référence une table : que se passe-t-il si cette table n'existe pas encore ?

Solution proposée
  1. Non. Acteur référence Film, qui n'existe pas encore : CREATE TABLE acteur échoue avec relation "film" does not exist. On crée d'abord les tables référencées : Personne et Film, puis Acteur et Réalisateur.
  2. Oui. Sans PRIMARY KEY, rien n'empêche deux personnes d'avoir le même id_pers ; sans REFERENCES, on peut déclarer acteur une personne qui n'existe pas. Les contraintes traduisent le modèle ; sans elles, la base accepte n'importe quoi.
  3. Pas pour le SGBD, tant que les noms restent cohérents entre les tables et les requêtes. Mais une clé étrangère qui porte le même nom que la clé qu'elle référence (id_pers) rend le schéma lisible.
  4. Peu importe pour les requêtes qui nomment les colonnes. Cela compte pour un INSERT sans liste de colonnes, qui suit l'ordre de la table (section 5).
  5. On corrige la table avec ALTER TABLE (ci-dessous), sans la recréer ni perdre ses données.
CREATE TABLE personne (
    id_pers integer PRIMARY KEY,
    nom     varchar(50) NOT NULL,
    prenom  varchar(50)
);
CREATE TABLE film (
    id_film integer PRIMARY KEY,
    titre   varchar(100) NOT NULL,
    annee   integer,
    duree   integer
);
CREATE TABLE acteur (
    id_pers integer REFERENCES personne (id_pers),
    id_film integer REFERENCES film (id_film),
    PRIMARY KEY (id_pers, id_film)
);
CREATE TABLE realisateur (
    id_pers integer REFERENCES personne (id_pers),
    id_film integer REFERENCES film (id_film),
    PRIMARY KEY (id_pers, id_film)
);

Ce script s'exécute sans erreur ; il se complète de la même façon pour Adresse, Résidence, Cinema, Salle et Projection, en créant toujours une table après celles qu'elle référence.

La référence circulaire diapo 25

Deux tables peuvent se référencer l'une l'autre : un employé appartient à un département, et un département a un employé pour responsable.

CREATE TABLE Employees (
    EmployeeID INT PRIMARY KEY,
    Name VARCHAR(255),
    DepartmentID INT,
    FOREIGN KEY (DepartmentID) REFERENCES Departments(DepartmentID)
);
CREATE TABLE Departments (
    DepartmentID INT PRIMARY KEY,
    DepartmentName VARCHAR(255),
    ManagerID INT,
    FOREIGN KEY (ManagerID) REFERENCES Employees(EmployeeID)
);

Complément Casser le cercle

Quel que soit l'ordre, la première table créée référence une table qui n'existe pas encore : ici, relation "departments" does not exist. La solution : créer la première table sans sa clé étrangère, créer la seconde, puis ajouter la clé étrangère manquante avec ALTER TABLE.

CREATE TABLE Employees (
    EmployeeID INT PRIMARY KEY,
    Name VARCHAR(255),
    DepartmentID INT
);
CREATE TABLE Departments (
    DepartmentID INT PRIMARY KEY,
    DepartmentName VARCHAR(255),
    ManagerID INT,
    FOREIGN KEY (ManagerID) REFERENCES Employees(EmployeeID)
);
ALTER TABLE Employees
    ADD FOREIGN KEY (DepartmentID) REFERENCES Departments(DepartmentID);

C'est ce que fait le TP 1 avec la clé réflexive id_chef de emp (question 6), ajoutée après la création de la table.

Modifier une table diapos 26–28

ALTER TABLE modifie la structure d'une table après sa création, même quand elle contient déjà des données : colonnes, contraintes, propriétaire… Les usages courants sont l'ajout ou la suppression d'une colonne, le changement de type d'une colonne, le changement de nom d'une table ou d'une colonne, et l'ajout, la suppression ou la modification d'une contrainte (documentation PostgreSQL, chapitre 5.6).

-- Ajout d'une colonne
ALTER TABLE emp ADD COLUMN grade int;
-- Suppression d'une colonne
ALTER TABLE emp DROP COLUMN grade;
-- Ajout d'une valeur par défaut
ALTER TABLE emp ALTER COLUMN comm SET DEFAULT 0;
-- Ajout d'une contrainte NOT NULL
ALTER TABLE emp ALTER COLUMN comm SET NOT NULL;
-- Modification du nom d'une colonne
ALTER TABLE emp RENAME COLUMN comm TO com;
-- Modification du nom d'une table
ALTER TABLE emp RENAME TO employes;
-- Ajout d'une contrainte de table
ALTER TABLE emp ADD CHECK (sal < 100000);
-- Suppression d'une contrainte de table
ALTER TABLE emp DROP CONSTRAINT earn_too_much;

La diapo 27 le rappelle : du code facile à lire, une commande par ligne !

Attention Ces commandes ne passent pas toutes, ni dans cet ordre

Ajout Exécutées l'une après l'autre sur la table emp de la diapo 20, avec des employés sans commission :

  • SET NOT NULL échoue (column "comm" contains null values) : SET DEFAULT ne vaut que pour les futures insertions et ne remplit pas les champs existants. Il faut d'abord UPDATE emp SET comm = 0 WHERE comm IS NULL; (diapo 34).
  • Après RENAME TO employes, la table emp n'existe plus : les deux dernières commandes doivent viser employes.
  • DROP CONSTRAINT earn_too_much échoue, car aucune contrainte ne porte ce nom : PostgreSQL a nommé la contrainte ajoutée employes_sal_check. Pour pouvoir la supprimer par son nom, on la nomme en la créant : ALTER TABLE employes ADD CONSTRAINT earn_too_much CHECK (sal < 100000);

Supprimer une table diapo 29

DROP TABLE détruit une table, sa structure et son contenu, de façon irréversible. Seul son propriétaire peut le faire. Pour ne supprimer que le contenu, on utilise DELETE (section 5).

DROP TABLE employees [RESTRICT | CASCADE];
  • RESTRICT (par défaut) : la suppression est impossible si un autre objet en dépend, par exemple une clé étrangère d'une autre table.
  • CASCADE : supprime aussi les vues et les contraintes de clé étrangère qui dépendent de la table.

Si la table est référencée par une clé étrangère d'une autre table, il faut donc d'abord supprimer ou modifier ces liens, sauf avec l'option CASCADE.

Complément Ce que supprime CASCADE

Sur l'exemple de la référence circulaire, DROP TABLE Employees RESTRICT est refusé (other objects depend on it). DROP TABLE Employees CASCADE supprime Employees et la contrainte de clé étrangère de Departments, mais pas la table Departments ni ses lignes : sa colonne ManagerID reste, sans contrôle.

Modifier les données : INSERT, UPDATE, DELETE diapos 30–37

Une fois les tables créées, le DML (Data Manipulation Language) les remplit et les fait évoluer. Trois commandes de base suffisent : INSERT ajoute des enregistrements, UPDATE les met à jour, DELETE les supprime. La quatrième, SELECT, consulte la base : associée à ses mots-clés et à ses clauses, elle permet de trouver et d'afficher quasiment toutes les informations possibles. C'est l'instruction la plus puissante et la plus complexe (section 6).

Insérer : INSERT INTO diapo 32

INSERT INTO table_name (column1, column2, column3, ...)
VALUES (value1.1, value2.1, value3.1, ...)
     [, (value1.2, value2.2, value3.2, ...)];
  • La déclaration des colonnes peut être explicite (liste des colonnes) ou implicite : sans liste, les valeurs suivent l'ordre des colonnes de la table.
  • Les colonnes non citées prennent leur valeur par défaut.
  • Les valeurs peuvent aussi venir du résultat d'une requête (documentation PostgreSQL, chapitre 6.1).
-- Colonnes explicites : comm, absente de la liste, vaut NULL
INSERT INTO emp (id_emp, nom_emp, metier, id_chef, date_emb, sal, id_dep)
VALUES (8350, 'BETTY', 'Analyste', 7566, '2025-09-15', 3056.33, 20);

-- Colonnes implicites (ordre de la table), deux lignes à la fois
INSERT INTO dep VALUES (50, 'Innovation', 'Le Mans'),
                       (60, 'Commerce', 'Nantes');

Complément L'ordre des insertions compte

Une clé étrangère doit désigner une ligne qui existe déjà. Dans le script du TP 1, chaque chef est inséré avant ses subordonnés, et les départements avant les employés ; sinon PostgreSQL refuse l'insertion (violates foreign key constraint).

Mettre à jour : UPDATE diapos 33–34

UPDATE modifie les données existantes d'une table, à ne pas confondre avec ALTER, qui modifie sa structure. Pour chaque enregistrement qui satisfait la condition, chaque colonne citée reçoit sa nouvelle valeur (documentation PostgreSQL, chapitre 6.2).

UPDATE table_name
SET column1 = value1, column2 = value2, ...
[FROM table_name2, ...]
WHERE condition;

Attention Sans WHERE, toutes les lignes diapo 33

La clause WHERE spécifie les lignes à modifier. Sans elle, toutes les lignes de la table sont mises à jour.

-- Modification simple, à partir des valeurs existantes
UPDATE emp SET id_emp = id_emp + 1;
-- Restriction des lignes avec WHERE
UPDATE emp SET comm = 0 WHERE comm IS NULL;
-- Modification de plusieurs colonnes
UPDATE emp SET comm = 0, id_emp = id_emp + 1 WHERE comm IS NULL;

Ajout Sur la base du TP, la deuxième commande met à jour 10 lignes. La première est refusée : id_emp est référencé par la clé étrangère id_chef, et changer le numéro d'un chef laisserait ses subordonnés pointer vers un employé inexistant. Sur une table sans clé étrangère mais aux numéros consécutifs (1, 2…), elle échoue aussi : le 1 devient 2 alors que 2 existe encore (duplicate key value violates unique constraint). Modifier une clé primaire est rarement une bonne idée.

Exercice 2 INSERT ou UPDATE ? diapo 35

Pour chaque événement, quelle commande faut-il utiliser sur les tables emp et dep ?

  1. John Doe vient d'être embauché !
  2. Jane Weber vient d'être promue !
  3. Aaron Dwight change de département.
  4. Le département Innovation vient d'ouvrir, et Gwen va y être mutée.
  5. Le département Commerce a fait faillite…
Indice

Une nouvelle ligne, ou une ligne qui existe déjà et dont une valeur change ? Pour le dernier cas, penser aux employés du département.

Solution proposée

On suppose que les employés cités existent, et que Commerce a le numéro 60.

-- 1. Nouvel employé : INSERT
INSERT INTO emp (id_emp, nom_emp, metier, id_chef, date_emb, sal, comm, id_dep)
VALUES (8001, 'DOE', 'Vendeur', 7698, CURRENT_DATE, 1300.00, 0, 30);

-- 2. Promotion : UPDATE du métier et du salaire
UPDATE emp SET metier = 'Manager', sal = 2900.00 WHERE nom_emp = 'WEBER';

-- 3. Mutation : UPDATE du département
UPDATE emp SET id_dep = 10 WHERE nom_emp = 'DWIGHT';

-- 4. Nouveau département (INSERT), puis mutation (UPDATE)
INSERT INTO dep VALUES (50, 'Innovation', 'Le Mans');
UPDATE emp SET id_dep = 50 WHERE nom_emp = 'GWEN';

-- 5. Faillite : DELETE, les employés d'abord
DELETE FROM emp WHERE id_dep = 60;
DELETE FROM dep WHERE id_dep = 60;

Pour le cas 5, supprimer directement le département est refusé (violates foreign key constraint "emp_id_dep_fkey") tant que des employés y sont rattachés. Plutôt que de les supprimer, on pourrait aussi les muter ailleurs par un UPDATE. Le cas 4 montre qu'un même événement demande parfois plusieurs commandes, dans le bon ordre.

Supprimer : DELETE diapos 36–37

DELETE supprime des enregistrements d'une table, à ne pas confondre avec DROP, qui supprime sa structure. La suppression est définitive, sauf dans une transaction (documentation PostgreSQL, chapitre 6.3).

DELETE FROM nom_table
WHERE condition;

La clause WHERE spécifie les lignes à supprimer. Sans condition, tous les enregistrements sont supprimés.

-- Suppression selon une condition
DELETE FROM emp WHERE date_emb >= '2001-01-01';
-- Suppression de tous les enregistrements : la table emp est vide, mais existe encore
DELETE FROM emp;

À vérifier La diapo 37 encadre la date d'apostrophes typographiques (‘2001-01-01’), que PostgreSQL ne reconnaît pas : en SQL, une chaîne s'écrit entre apostrophes droites '…'. Sur la base du TP, où tout le monde a été embauché avant 1984, la première commande ne supprime aucune ligne.

Interroger les données : SELECT diapos 38–47

SELECT est la commande que l'on écrit le plus. Elle compte neuf clauses, dont sept facultatives ; ce cours se limite aux requêtes « simples » sur une table : projection et sélection, filtrage avec les opérateurs, et quelques fonctions. Les jointures, qui combinent plusieurs tables, viendront ensuite.

Exemple Étendue : BETWEEN diapo 44

Qui a été embauché entre août 1981 et août 1982 ?

SELECT nom_emp, date_emb FROM emp
WHERE date_emb BETWEEN '1981-08-01' AND '1982-08-01';

Six employés : KING (1981-11-17), FORD (1981-12-03), MARTIN (1981-09-28), TURNER (1981-09-08), JAMES (1981-12-03) et MILLER (1982-01-23). BETWEEN inclut ses deux bornes.

Exemple Appartenance : IN diapo 45

Qui est vendeur ou employé de bureau ?

SELECT nom_emp, metier FROM emp
WHERE metier IN ('Vendeur', 'Secretaire');

Huit employés : les quatre vendeurs (ALLEN, WARD, MARTIN, TURNER) et les quatre secrétaires (SMITH, ADAMS, JAMES, MILLER).

Complément Les modèles de LIKE

La diapo cite LIKE sans détailler ses modèles. Deux caractères y sont spéciaux :

  • % remplace n'importe quelle suite de caractères, même vide : nom_emp LIKE '%A%' garde les noms qui contiennent un A (BLAKE, ALLEN, WARD, MARTIN, CLARK, ADAMS, JAMES) ;
  • _ remplace exactement un caractère : nom_emp LIKE '_A%' garde les noms dont la deuxième lettre est un A (WARD, MARTIN, JAMES).

LIKE distingue les majuscules des minuscules ; PostgreSQL propose ILIKE pour ne pas les distinguer. Ce sont les questions 13, 14 et 23 du TP 1.

Négation et conjonction diapo 46

  • Négation d'une condition, pour exclure des enregistrements d'un résultat : NOT. On l'emploie aussi sous la forme NOT BETWEEN, NOT IN, NOT LIKE, IS NOT NULL.
  • Conditions multiples : expression1 AND expression2 est vraie si les deux expressions sont vraies ; expression1 OR expression2 est vraie si l'une au moins l'est.
  • On peut chaîner plusieurs opérateurs : l'ordre d'écriture a de l'importance !

Attention AND passe avant OR

Ajout Comme la multiplication avant l'addition, AND est évalué avant OR. Pour « les vendeurs et les managers qui gagnent plus de 2 800 » :

-- 6 lignes : tous les vendeurs, plus JONES et BLAKE
SELECT nom_emp FROM emp
WHERE metier = 'Vendeur' OR metier = 'Manager' AND sal > 2800;

-- 2 lignes : JONES et BLAKE
SELECT nom_emp FROM emp
WHERE (metier = 'Vendeur' OR metier = 'Manager') AND sal > 2800;

La première requête se lit « vendeur, ou (manager et plus de 2 800) » : elle renvoie les quatre vendeurs, quel que soit leur salaire. Dans le doute, on met des parenthèses.

Complément Pourquoi 4 lignes, et comment compter une commission absente

Tous les employés gagnent plus de 500. Mais pour les dix qui n'ont pas de commission, sal + comm vaut NULL, et NULL > 500 n'est pas vrai : ils disparaissent du résultat. Pour traiter une commission absente comme 0, on utilise COALESCE(comm, 0), qui renvoie comm s'il est renseigné et 0 sinon :

SELECT nom_emp, sal + COALESCE(comm, 0) AS revenu FROM emp WHERE id_dep = 30;

BLAKE a alors un revenu de 2852.56, et JAMES de 1253.65, au lieu d'une case vide.

À retenir

L'essentiel

  • Une table implémente une relation : ses lignes sont des enregistrements, ses colonnes des attributs, chaque case un champ. La clé primaire assure l'unicité ; une clé étrangère renvoie à une valeur qui existe dans une autre table.
  • On se connecte avec psql -U user -d base -h host. Les commandes PostgreSQL commencent par un antislash (\l, \c, \dt, \d, \i) ; les commandes SQL finissent par un point-virgule.
  • SQL est déclaratif : on décrit le résultat, le SGBD choisit comment l'obtenir. Il est normalisé, mais chaque SGBD a ses variantes.
  • NULL signifie « pas de valeur » : ni 0, ni chaîne vide, ni faux. On le teste avec IS NULL ; tout calcul qui le contient vaut NULL.
  • DDL : CREATE TABLE (nom, type et contraintes de chaque colonne), ALTER TABLE (structure), DROP TABLE (structure et contenu, RESTRICT ou CASCADE).
  • Contraintes : NOT NULL, UNIQUE, DEFAULT, CHECK, PRIMARY KEY, FOREIGN KEY … REFERENCES ; sur plusieurs colonnes, on les écrit en contraintes de table.
  • Une table se crée après celles qu'elle référence ; une référence circulaire se règle par ALTER TABLE … ADD FOREIGN KEY.
  • DML : INSERT INTO … VALUES, UPDATE … SET … WHERE, DELETE FROM … WHERE. Sans WHERE, UPDATE et DELETE touchent toutes les lignes.
  • SELECT choisit les colonnes (projection), WHERE les lignes (sélection) avec =, <>, BETWEEN, IN, LIKE, IS NULL, NOT, AND et OR (AND d'abord).

Auto-évaluation

Quelle différence entre ALTER et UPDATE ? Entre DROP et DELETE ?

ALTER et DROP agissent sur la structure (DDL) ; UPDATE et DELETE sur les données (DML). Après DELETE FROM emp;, la table existe encore, vide ; après DROP TABLE emp;, elle n'existe plus.

Pourquoi WHERE comm = NULL ne renvoie-t-il rien ?

Une comparaison avec NULL n'est jamais vraie : NULL n'est pas une valeur mais son absence. On écrit WHERE comm IS NULL.

Dans quel ordre créer Personne, Film et Acteur(#id_pers, #id_film) ?

Personne et Film d'abord, dans n'importe quel ordre, puis Acteur, qui les référence. Sinon, CREATE TABLE acteur échoue : relation "film" does not exist.

Comment déclarer la clé primaire (order_id, product_id) ?

En contrainte de table, après les colonnes : PRIMARY KEY (order_id, product_id). Écrire PRIMARY KEY derrière chacune des deux colonnes déclarerait deux clés primaires, ce qui est interdit.

Que fait UPDATE emp SET sal = sal * 1.1; ?

Elle augmente de 10 % le salaire de tous les employés, faute de clause WHERE.

Que renvoie WHERE metier = 'Vendeur' OR metier = 'Manager' AND sal > 2800 ?

Tous les vendeurs, plus les managers qui gagnent plus de 2 800 : AND est évalué avant OR. Avec des parenthèses autour du OR, on n'obtient que les vendeurs et managers au-delà de 2 800.

Quels noms garde nom_emp LIKE '%ER' ?

Ceux qui finissent par ER : TURNER et MILLER. % remplace une suite quelconque de caractères, même vide.
