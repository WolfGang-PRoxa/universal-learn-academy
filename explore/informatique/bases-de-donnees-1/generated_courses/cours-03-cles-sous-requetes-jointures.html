Clés, sous-requêtes et jointures

Ce cours part du retour sur le TP 1 pour aller plus loin en SQL. Il précise le rôle des clés et de l'auto-incrémentation, fait évoluer une base existante sans perdre ses données, puis donne les deux outils qui permettent d'interroger plusieurs tables : les sous-requêtes et les jointures.

Rappels sur les instructions SQL diapos 1–6, 22–24

Le cours s'ouvre sur le retour du TP 1 (diapo 2, sans autre contenu), puis rappelle ce qu'est une instruction SQL.

L'instruction SQL diapo 4

L'instruction SQL est la base de la communication avec le serveur SGBD, selon un modèle client-serveur. C'est du code dit « facile à lire », puisque le langage est déclaratif. Sa syntaxe comprend :

  • une commande SQL : CREATE, SELECT… ;
  • un ensemble de clauses : RENAME, WHERE… ;
  • un point-virgule, qui déclenche l'exécution.

Les diapos 5 et 23 reprennent les cinq catégories de commandes (DDL, DML, DQL, DCL, SQL intégré), et la diapo 24 les commandes du DML : voir le cours 2, où la correspondance entre DQL, DCL et leurs rôles est discutée.

Les clés et l'auto-incrémentation diapos 7–12

Les clés relient les tables et garantissent l'unicité des lignes. Encore faut-il choisir leurs valeurs : c'est le rôle de l'auto-incrémentation, et dire ce qui se passe quand une ligne référencée disparaît : c'est le rôle des actions des clés étrangères.

La clé primaire diapo 7

Définition Clé primaire (PRIMARY KEY) diapo 7

La clé primaire identifie de manière unique chaque ligne d'une table. Ses propriétés :

  • unique : deux lignes ne peuvent pas avoir la même clé primaire ;
  • non nulle : aucun champ de la clé primaire ne peut être NULL ;
  • une seule par table ;
  • composée si besoin : elle peut porter sur plusieurs colonnes.

Astuce Les bonnes pratiques diapo 7

  • Nommer le champ de clé primaire id_<table>.
  • Utiliser un type entier et la propriété d'auto-incrémentation.
  • Ne jamais réutiliser ni modifier une clé primaire existante.
CREATE TABLE Employees (
    EmployeeID INT PRIMARY KEY,
    Name VARCHAR(100)
);

À vérifier La diapo ajoute « Pas de clé = pas 4 NF ». La quatrième forme normale n'est pas définie dans ce module, qui s'arrête à la 3NF (cours 1). L'idée à retenir : sans clé primaire, une table peut contenir deux lignes identiques, et les formes normales, qui s'énoncent par rapport à la clé, ne peuvent même pas être vérifiées.

La clé étrangère diapo 8

Définition Clé étrangère (FOREIGN KEY) diapo 8

La clé étrangère relie une colonne d'une table à la clé primaire d'une autre table. Ses propriétés :

  • référence : elle pointe vers une clé primaire (ou UNIQUE) existante ;
  • intégrité référentielle : on ne peut pas supprimer un enregistrement parent tant qu'il est encore référencé ;
  • nullable possible : elle peut être NULL si la relation est facultative.
CREATE TABLE Employees (
    EmployeeID INT PRIMARY KEY,
    Name VARCHAR(100),
    DepartmentID INT,
    FOREIGN KEY (DepartmentID) REFERENCES Departments(DepartmentID)
);

Les clauses ON DELETE et ON UPDATE de FOREIGN KEY disent quoi faire des lignes « enfants » quand la ligne « parent » référencée est supprimée ou que sa clé change :

  • CASCADE : supprime, ou met à jour, aussi les lignes enfants ;
  • SET NULL ou SET DEFAULT : remplace la valeur de la clé étrangère par NULL ou par sa valeur par défaut.
FOREIGN KEY (DepartmentID)
    REFERENCES Departments(DepartmentID)
    ON DELETE SET NULL
    ON UPDATE CASCADE

Complément L'action par défaut

Sans clause, l'action est NO ACTION : la suppression ou la modification du parent est refusée tant qu'un enfant le référence. C'est la propriété « intégrité référentielle » ci-dessus. RESTRICT se comporte presque de même. Sur la diapo, la clause FOREIGN KEY … ON UPDATE CASCADE se termine par un point-virgule : elle ne s'écrit pas seule, mais dans un CREATE TABLE ou un ALTER TABLE.

Le type SERIAL diapo 9

Le type SERIAL correspond à :

  • le type INT ;
  • la création d'une séquence (sequence), un ensemble de valeurs entières obtenues automatiquement : la valeur par défaut de la colonne est la suivante de la séquence.

On l'associe généralement à une clé primaire : il permet de ne pas gérer les valeurs du champ. Mais il ne faut pas l'associer à une clé étrangère.

À vérifier La diapo donne les valeurs « 0, 1, 2, … » ; la séquence commence en fait à 1 (voir l'exemple ci-dessous).

Complément Pourquoi pas de SERIAL sur une clé étrangère

Une clé étrangère doit reprendre une valeur qui existe dans l'autre table, choisie par celui qui insère. Avec SERIAL, la colonne recevrait un numéro de séquence sans rapport avec la ligne visée. La clé primaire est SERIAL, la clé étrangère qui la référence est un simple INT.

GENERATED AS IDENTITY diapo 10

SERIAL est propre à PostgreSQL : il n'est pas reconnu par la norme SQL:1999 (« SQL 99 »). La forme normalisée est la propriété de colonne GENERATED AS IDENTITY, qui s'associe elle aussi généralement à une clé primaire et évite de gérer les valeurs du champ.

CREATE TABLE emp (
    id_emp INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nom_emp VARCHAR(50)
);
GENERATED { ALWAYS | BY DEFAULT } AS IDENTITY
    [ ( [ START WITH start ]
        [ INCREMENT BY increment ]
        [ MINVALUE minvalue | NO MINVALUE ]
        [ MAXVALUE maxvalue | NO MAXVALUE ]
        [ CYCLE | NO CYCLE ]
        [ CACHE cache ] ) ]

Complément ALWAYS ou BY DEFAULT

  • ALWAYS : la base choisit toujours la valeur. Insérer un identifiant explicite est refusé (cannot insert a non-DEFAULT value into column "id_emp").
  • BY DEFAULT : la base propose une valeur, mais on peut en donner une. Attention, la séquence n'en tient pas compte : après avoir inséré l'identifiant 10 à la main, la ligne suivante reçoit 2, et un conflit surviendra quand la séquence atteindra 10.

Questions sur les clés diapo 12

Une clé primaire peut-elle être composée de plusieurs attributs ?

Oui ! Elle s'écrit alors obligatoirement en contrainte de table : PRIMARY KEY (a, b).

Une table peut-elle ne pas avoir de clé primaire ?

Non ! (La diapo : « ce n'est pas 4NF ».) SQL l'accepte techniquement, mais la table peut alors contenir des lignes en double.

Un attribut peut-il être clé étrangère et faire partie de la clé primaire ?

Oui : c'est le cas d'une table d'association, ou d'un identifiant relatif (cours 1). On l'écrit avec des contraintes de table, et éventuellement une contrainte d'attribut.

Un cas complet : le directeur de chaque département diapos 13–21, 25–27

Une base en service évolue : il faut parfois ajouter une information sans recréer les tables ni perdre les données. La partie « avancée » du TP 1 en donne un exemple complet, du diagramme de classes aux données.

Exemple L'énoncé diapo 13

On souhaite enregistrer le directeur de chaque département. Ce directeur est un employé déjà enregistré, qui a en charge le bon fonctionnement d'un département donné. Un employé n'est en aucun cas obligé de diriger un département, mais s'il l'accepte, il ne peut en prendre qu'un seul en charge.

Il faut d'abord modifier le diagramme de classes, puis le modèle relationnel. (La diapo écrit « puis le modèle de classe », pour le modèle relationnel.)

Le point de départ diapo 14

emp(id_emp, nom_emp, metier, #id_chef, date_emb, sal, comm, #id_dep)

dep(id_dep, nom_dep, loc)

grade(id_grade, min_sal, max_sal)

CREATE TABLE dep (
    id_dep SERIAL PRIMARY KEY,
    nom_dep VARCHAR(50) NOT NULL,
    loc VARCHAR(50)
);

CREATE TABLE emp (
    id_emp SERIAL PRIMARY KEY,
    nom_emp VARCHAR(50) NOT NULL,
    metier VARCHAR(50),
    id_chef INT REFERENCES emp(id_emp),
    date_emb DATE,
    sal DECIMAL(10,2),
    comm DECIMAL(10,2),
    id_dep INT REFERENCES dep(id_dep)
);

On retrouve la règle de la diapo 9 : les clés primaires sont SERIAL, les clés étrangères id_chef et id_dep de simples INT.

Le diagramme de classes diapos 15, 18

L'information « est directeur de » relie un employé à un département : on ajoute une association entre Emp et Dep, distincte de « est rattaché à ».

À vérifier Sur la diapo 15, l'association porte 1..1 côté Emp : tout département a exactement un directeur. Sur les diapos 18 à 20, elle porte 0..1 des deux côtés, cohérent avec l'ON DELETE SET NULL qui suit : quand un directeur part, son département reste un temps sans directeur. Côté Dep, 0..1 traduit l'énoncé : un employé dirige au plus un département.

Le modèle relationnel et les ALTER TABLE diapos 16–20

L'association est du type 0..1 — 0..1 : règle 4 du cours 1, une clé étrangère d'un côté ou de l'autre. On l'ajoute à dep, sous le nom id_dir :

emp(id_emp, nom_emp, metier, #id_chef, date_emb, sal, comm, #id_dep)

dep(id_dep, nom_dep, loc, #id_dir)

grade(id_grade, min_sal, max_sal)

La table existe et contient des données : on la modifie en deux étapes (diapo 17).

-- Étape 1 : la colonne
ALTER TABLE dep ADD COLUMN id_dir INT;
-- Étape 2 : la clé étrangère
ALTER TABLE dep ADD FOREIGN KEY (id_dir) REFERENCES emp(id_emp);

Puis on affine, question après question.

  1. Un directeur ne peut diriger qu'un seul département (diapo 18) : la colonne devient UNIQUE. Désigner KING pour un second département est alors refusé (duplicate key value violates unique constraint "dep_id_dir_key"). 
    ALTER TABLE dep ADD COLUMN id_dir INT UNIQUE;
  2. Et si le directeur d'un département quitte l'entreprise ? (diapo 19) On supprime l'enregistrement de l'employé, et il faut mettre à jour dep : ON DELETE SET NULL le fait automatiquement. 
    ALTER TABLE dep ADD FOREIGN KEY (id_dir) REFERENCES emp(id_emp)
    ON DELETE SET NULL;
  3. Et si l'on renumérote les employés ? (diapo 20) Il faut encore mettre à jour dep : ON UPDATE CASCADE reporte le nouveau numéro. 
    ALTER TABLE dep ADD FOREIGN KEY (id_dir) REFERENCES emp(id_emp)
    ON DELETE SET NULL
    ON UPDATE CASCADE;

Attention Les autres clés étrangères ont leur mot à dire

Ajout Sur la base du TP, supprimer KING, ou changer son numéro, reste refusé malgré ces clauses : emp.id_chef référence aussi id_emp, sans action, et KING est le chef de JONES, BLAKE et CLARK (violates foreign key constraint "emp_id_chef_fkey"). L'ON DELETE SET NULL de id_dir ne joue que si rien d'autre ne retient la ligne : un directeur sans subordonné qui part laisse bien son département avec id_dir à NULL.

Enregistrer les directeurs : UPDATE avec une sous-requête diapos 21, 25–27

Il faut maintenant enregistrer que KING dirige le département Comptable, FORD le département Recherche et BLAKE le département Ventes. Est-ce une modification de structure ? Non : la colonne existe déjà (elle est vide), il s'agit de modifier des données, donc d'un UPDATE (diapo 25).

nath=# select * from dep;
 id_dep |  nom_dep   |   loc    | id_dir
--------+------------+----------+--------
     40 | Operations | Boston   |
     10 | Comptable  | New York |
     30 | Ventes     | Chicago  |
     20 | Recherche  | Dallas   |
(4 lignes)

Il ne faut surtout pas toucher aux données existantes : on ne remplit que id_dir, en y mettant l'id_emp de KING, de FORD et de BLAKE (diapo 26). Mais le numéro de KING n'est pas connu : une requête SELECT, placée entre parenthèses, va le donner (diapo 27).

UPDATE dep SET id_dir = (SELECT id_emp FROM emp WHERE nom_emp = 'KING')
WHERE nom_dep = 'Comptable';
UPDATE 1
nath=# select * from dep where nom_dep='Comptable';
 id_dep |  nom_dep  |   loc    | id_dir
--------+-----------+----------+--------
     10 | Comptable | New York |   7839
(1 ligne)

Attention Une seule valeur diapo 27

Une sous-requête utilisée à la place d'une valeur ne doit renvoyer qu'une seule valeur : une ligne, une colonne. S'il y avait deux employés nommés KING, PostgreSQL refuserait la commande (more than one row returned by a subquery used as an expression). La diapo écrit SELECT dep set id_dir = … pour UPDATE dep SET id_dir = ….

La diapo 29 montre une autre écriture, propre à PostgreSQL, qui joint emp dans l'UPDATE :

UPDATE dep SET id_dir = id_emp FROM emp
WHERE nom_dep = 'Recherche' AND nom_emp = 'FORD';

Exercice 1 Enregistrer les directeurs diapos 17–27

Écrire le script qui, sur la base du TP 1, ajoute à dep la colonne id_dir avec toutes ses contraintes (unicité, clé étrangère, actions en cas de suppression et de renumérotation), puis enregistre KING, FORD et BLAKE comme directeurs de Comptable, Recherche et Ventes. Operations reste sans directeur.

Guillemets, casse et INSERT à partir d'un SELECT diapos 28–33

En écrivant ces UPDATE, on bute vite sur deux questions de détail qui font perdre du temps : apostrophe ou guillemet, majuscule ou minuscule ? Puis on voit comment une sous-requête peut aussi fournir les valeurs d'un INSERT.

Apostrophes et guillemets diapos 28–30

Apostrophes ' (simples quotes)

Elles définissent la valeur d'une donnée : 'KING'. Les majuscules y sont prises en compte : 'King' n'est pas 'KING'.

Guillemets " (doubles quotes)

Ils définissent un nom d'objet interprété par le SGBD : nom d'une table, d'une colonne, d'une base… Les majuscules y sont prises en compte aussi !

CREATE TABLE "Mes Employés" (
    "ID Employé" INT PRIMARY KEY,
    "Nom Employé" VARCHAR(50)
);

Quand on a compris, on peut « presque » tout faire… mais il faut privilégier la simplicité et la lisibilité (diapo 29). Les essais de la diapo le montrent :

Attention Abandonner les " dans les CREATE diapo 30

Une table créée par CREATE TABLE "Test" (id int primary key); garde sa majuscule. Ensuite, select * from test; et même select * from Test; échouent (la relation « test » n'existe pas), car un nom sans guillemets est ramené en minuscules. Seul select * from "Test"; fonctionne. D'où la règle : pas de guillemets dans les CREATE, des noms en minuscules.

Un SELECT dans les valeurs d'un INSERT diapo 31

La question 12 de la partie 2 du TP 1 : un nouvel analyste vient d'être embauché aujourd'hui ! Il travaille dans le département Recherche. Son nom est BETTY et son numéro d'employé 8350. Il a pour chef M. Jones et touche le même salaire que M. Ford.

INSERT INTO emp VALUES (
    8350, 'BETTY', 'Analyste',
    (SELECT id_emp FROM emp WHERE nom_emp = 'JONES'),
    current_date,
    (SELECT sal FROM emp WHERE nom_emp = 'FORD'),
    NULL,
    (SELECT id_dep FROM dep WHERE nom_dep = 'Recherche')
);

Chaque SELECT se met entre parenthèses, et son résultat prend la place de la valeur : il ne doit renvoyer qu'une seule ligne. BETTY reçoit ainsi le chef 7566, le salaire 3056.33 et le département 20.

À vérifier La diapo ferme plusieurs chaînes par une apostrophe typographique ('Analyste’), que PostgreSQL ne reconnaît pas ; elles sont corrigées ici.

INSERT … SELECT diapos 32–33

On peut aussi insérer des enregistrements issus d'une autre table : une requête SELECT, aussi complexe que nécessaire, prend la place de VALUES.

INSERT INTO emp2 SELECT * FROM emp WHERE sal > 2000;

Attention Redondance et incohérence diapo 32

Recopier des données, c'est créer de la redondance : si un salaire change dans emp, la copie de emp2 devient fausse. À n'utiliser que dans des cas particuliers (archives, table de travail). Ajout La table emp2 doit exister avant l'insertion, par exemple créée par CREATE TABLE emp2 (LIKE emp); ; elle reçoit ici 6 employés.

Exemple Remplir batiment à partir des analystes diapo 33

nath=# INSERT into batiment (nom_bat,loc) select nom_emp,loc from emp natural join dep where metier='Analyste';
INSERT 0 2
nath=# select * from batiment;

--------+---------+--------------------

      2 | Leia    |
      3 | Han     |
      4 | Anakin  | très très lointain
      5 | FORD    | Dallas
      6 | SCOTT   | Dallas
(6 lignes)
  • Le SELECT est aussi complexe que besoin : ici, une jointure naturelle (section 7).
  • id_bat reçoit une valeur par défaut grâce au SERIAL.
  • DEFAULT ne peut pas être écrit dans le SELECT : on liste donc les colonnes remplies, (nom_bat, loc), avant la requête.

SELECT : choisir le bon opérateur diapos 34–44

Les diapos 35 à 38 rappellent la syntaxe de SELECT et ses opérateurs, vus au cours 2. Les suivantes montrent, sur des exemples du TP 1, les erreurs les plus fréquentes : un opérateur mal choisi, ou mal combiné.

La syntaxe complète diapo 35

Neuf clauses, dont sept (voire huit) optionnelles, dans cet ordre (version simplifiée) :

SELECT [ALL | DISTINCT] {* | expression [AS nom_affiché]} [, ...]
FROM nom_table [[AS] alias] [, ...]
[WHERE prédicat]
[GROUP BY expression [, ...]]
[HAVING condition [, ...]]
[{UNION | INTERSECT | EXCEPT} [ALL] requête]
[ORDER BY expression [ASC | DESC] [, ...]]
[LIMIT {ALL | nombre}]
[OFFSET début]
  • La clause SELECT gère l'affichage des données (diapo 36) : *, ALL (toutes les lignes, par défaut), DISTINCT, + - * /, ||, AS.
  • La clause WHERE gère les lignes à considérer (diapo 37) : une ligne est acceptée si elle respecte la condition expression1 opérateur expression2, avec les opérateurs de comparaison, BETWEEN, IN, LIKE et IS NULL, combinés par NOT, AND et OR (diapo 38).

Deux exemples du TP 1 diapos 39–40

Question 9 : la liste des employés qui sont secrétaires, vendeurs ou analystes. IN évite trois conditions reliées par OR (10 employés) :

SELECT * FROM emp WHERE metier IN ('Secretaire', 'Vendeur', 'Analyste');

Question 19 : la liste des vendeurs qui n'ont pas de commission (valeur 0 ou NULL). On décompose : les vendeurs, metier = 'Vendeur' ; commission nulle, comm IS NULL ; commission égale à 0, comm = 0.

SELECT nom_emp FROM emp
WHERE (metier = 'Vendeur') AND ((comm IS NULL) OR (comm = 0));

Attention Deux pièges diapo 40

  • AND est évalué avant OR : les parenthèses autour du OR sont obligatoires.
  • comm IN (0, NULL) ne fonctionne pas : il équivaut à comm = 0 OR comm = NULL, et la seconde comparaison n'est jamais vraie. Seul TURNER (commission 0) est trouvé, aucun des employés sans commission.

La diapo, qui numérote cette question 12, écrit aussi ‘Vendeur’ avec des apostrophes typographiques, à remplacer par 'Vendeur'.

Complément Ce que dit PostgreSQL

  • À vérifier La diapo 41 dit que loc IN 'Avignon' « fonctionne techniquement ». PostgreSQL le refuse (syntax error at or near "'Dallas'" avec Dallas) : IN exige des parenthèses, loc IN ('Avignon'). La conclusion reste la même : pour une seule valeur, on écrit =.
  • Le format '01-JAN-2021' est accepté par PostgreSQL, mais le format ISO '2021-01-01' est plus sûr. La version BETWEEN de la diapo 42 se termine par une parenthèse de trop, qui provoque une erreur de syntaxe.
  • Sur la base du TP, comm = 0 OR comm IS NULL trouve 11 employés : TURNER et les dix sans commission.

L'ordre d'évaluation dans WHERE diapo 44

Du plus prioritaire au moins prioritaire :

  1. les parenthèses ( … ) ;
  2. les opérateurs arithmétiques *, /, puis +, - ;
  3. les opérateurs de comparaison =, <, >, <=, >=, <>, !=, IS [NOT] NULL, LIKE, BETWEEN, IN ;
  4. NOT ;
  5. AND ;
  6. OR.

Les sous-requêtes dans WHERE diapos 45–48

Une condition peut dépendre du contenu de la base elle-même : « les employés dont le chef travaille au département 20 ». On utilise alors le résultat d'une requête comme élément de comparaison dans la clause WHERE.

Combien de résultats ? diapos 45–46

Tout dépend du nombre de résultats renvoyés par la sous-requête :

  • un résultat : pas de souci, on compare avec =, <… ;
  • deux résultats ou plus : un opérateur spécifique est obligatoire devant la sous-requête.
Opérateurs devant une sous-requête (diapos 45–46)
ÉcritureVraie si…
expression IN (sous-requête)l'expression est égale à au moins une valeur
expression opérateur ALL (sous-requête)la comparaison est vraie pour tous les résultats
expression opérateur ANY (sous-requête)la comparaison est vraie pour au moins un résultat

L'expression est une valeur ou une colonne, et l'opérateur l'un de =, <>, <, <=, >, >=.

Exemple Les employés dont le chef est au département 20 diapo 47

Il faut afficher les employés qui ont pour chef une personne du département 20. Qui sont les personnes du département 20 ?

SELECT id_emp FROM emp WHERE id_dep = 20;

Les chefs doivent faire partie de ces personnes : on utilise cette requête comme sous-requête dans le WHERE.

SELECT id_emp FROM emp
WHERE id_chef = (SELECT id_emp FROM emp WHERE id_dep = 20);

Erreur : on compare un id_chef avec plusieurs id_emp (more than one row returned by a subquery used as an expression). Avec ANY :

SELECT id_emp FROM emp
WHERE id_chef = ANY (SELECT id_emp FROM emp WHERE id_dep = 20);

Quatre employés : FORD et SCOTT (chef JONES), SMITH (chef FORD) et ADAMS (chef SCOTT).

La diapo écrit l'énoncé avec le « département n° 2 » et la requête avec id_dep = 2 ; dans la base du TP, le numéro est 20, comme dans sa capture d'écran.

IN, NOT IN, ANY et ALL diapo 48

  • IN équivaut à = ANY : les deux requêtes suivantes donnent les mêmes 4 employés.
SELECT id_emp FROM emp WHERE id_chef IN    (SELECT id_emp FROM emp WHERE id_dep = 20);
SELECT id_emp FROM emp WHERE id_chef = ANY (SELECT id_emp FROM emp WHERE id_dep = 20);
  • NOT IN équivaut à <> ALL : « différent de tous », ou « pas dedans ». Pour la liste des employés qui n'ont pas leur chef dans le département 20 :
SELECT id_emp FROM emp WHERE id_chef <> ALL (SELECT id_emp FROM emp WHERE id_dep = 20);
SELECT id_emp FROM emp WHERE id_chef NOT IN (SELECT id_emp FROM emp WHERE id_dep = 20);

Attention NOT IN et NULL

Ajout Ces deux requêtes renvoient 9 employés, et pas 10 : KING n'a pas de chef, et NULL <> ALL (…) n'est pas vrai. Plus grave : si la sous-requête renvoie un NULL, NOT IN ne renvoie plus aucune ligne, car « différent d'une valeur inconnue » n'est jamais vrai. On l'évite en excluant les NULL de la sous-requête (WHERE … IS NOT NULL), ou avec une jointure externe (section 7).

Exemple ALL et ANY avec une inégalité

Ajout Les employés qui gagnent plus que tous ceux du département 30 : KING, JONES, FORD et SCOTT (le plus haut salaire des Ventes est celui de BLAKE, 2852.56). Avec ANY, plus qu'au moins un d'entre eux, on en trouve 12.

SELECT nom_emp, sal FROM emp
WHERE sal > ALL (SELECT sal FROM emp WHERE id_dep = 30);

Les jointures diapos 49–61

Une sous-requête permet de filtrer une table d'après une autre, mais pas d'afficher les colonnes des deux : pour avoir le nom d'un employé à côté du nom de son département, il faut combiner les lignes des deux tables. C'est la jointure.

La clause FROM diapo 49

La clause FROM est indispensable : elle sélectionne l'ensemble des données sur lesquelles travailler. Sans jointure, on accède aux données d'une table. Avec une jointure (join), on combine les lignes de deux tables ou plus selon une condition commune, typiquement fondée sur une clé primaire et une clé étrangère, et l'on travaille sur plusieurs tables à la fois.

La jointure interne diapo 50

INNER JOIN (ou simplement JOIN) : seules les lignes qui ont une correspondance dans les deux tables sont conservées ; une ligne sans correspondance est exclue.

SELECT emp.nom_emp, dep.nom_dep
FROM emp INNER JOIN dep ON emp.id_dep = dep.id_dep;

Seules les lignes où emp.id_dep = dep.id_dep apparaissent : les 14 employés avec leur département. Les employés sans département et les départements sans employés (ici Operations) ne sont pas inclus.

Attention Préfixer les colonnes communes

À vérifier La diapo donne d'abord … INNER JOIN dep ON id_dep = id_dep;. PostgreSQL la refuse : id_dep existe dans les deux tables, et le nom seul est ambigu (column reference "id_dep" is ambiguous). D'où la seconde écriture, préfixée par le nom de la table.

Les jointures externes diapos 51–53

  • LEFT OUTER JOIN (ou LEFT JOIN) : toutes les lignes de la table de gauche sont conservées. Sans correspondance à droite, les colonnes de droite valent NULL.
SELECT e.nom_emp, d.nom_dep FROM emp AS e LEFT JOIN dep AS d ON e.id_dep = d.id_dep;

La table de gauche est emp : tous les employés apparaissent, même ceux sans département, pour lesquels d.nom_dep vaut NULL. AS est optionnel : emp e suffit.

  • RIGHT OUTER JOIN (ou RIGHT JOIN) : le symétrique, toutes les lignes de la table de droite sont conservées.
SELECT e.nom_emp, d.nom_dep FROM emp AS e RIGHT JOIN dep AS d ON e.id_dep = d.id_dep;

La table de droite est dep : tous les départements apparaissent, même sans employé. Ici, 15 lignes : les 14 employés, et une ligne Operations dont e.nom_emp vaut NULL.

  • FULL OUTER JOIN : toutes les lignes des deux tables sont conservées, les colonnes manquantes valent NULL. Il combine les comportements de LEFT et RIGHT JOIN, et il est rarement utilisé.
SELECT e.nom_emp, d.nom_dep
FROM emp AS e FULL OUTER JOIN dep AS d ON e.id_dep = d.id_dep;

La diapo 53 commence par « Symétrique du LEFT JOIN : toutes les lignes de la table de droite sont conservées », phrase recopiée de la diapo 52.

Complément Lire le schéma

Les trois diagrammes avec WHERE … IS NULL gardent les lignes sans correspondance : après une jointure externe, une ligne sans partenaire a des colonnes NULL de l'autre côté, et le WHERE ne garde qu'elles. C'est la façon la plus sûre de chercher « les départements sans employé » ou « les pilotes sans vol ».

Le produit cartésien et la jointure naturelle diapos 55–56

  • CROSS JOIN produit toutes les combinaisons possibles des lignes des deux tables : c'est le produit cartésien. Si emp a 5 lignes et dep 3, le résultat en a \(5 \times 3 = 15\) ; sur la base du TP, \(14 \times 4 = 56\). À utiliser avec précaution, car le résultat peut être énorme ; rarement utilisé.
SELECT e.nom_emp, d.nom_dep FROM emp AS e CROSS JOIN dep AS d;
  • NATURAL JOIN est une jointure interne dont la condition est implicite : elle fait correspondre tous les attributs qui portent le même nom dans les deux tables, et leurs valeurs doivent toutes être égales. Elle est peu recommandée : à utiliser quand on a compris les autres jointures, et encore !

Complément Le danger de NATURAL JOIN

emp NATURAL JOIN dep joint aujourd'hui sur id_dep, la seule colonne commune, et donne les 14 employés. Mais qu'on ajoute un jour une colonne loc à emp, ou une colonne nom aux deux tables, et la condition change en silence : la requête renvoie d'autres lignes, sans aucune erreur. Une condition écrite avec ON ne bouge pas.

Autres points importants diapos 57–60

La condition de jointure s'écrit généralement ON table1.col = table2.col, et l'on peut y ajouter d'autres conditions :

SELECT * FROM emp AS e JOIN dep AS d ON e.id_dep = d.id_dep AND e.sal > 3000;

La condition e.sal > 3000 peut aussi aller dans le WHERE : pour une jointure interne, le résultat est le même (KING, FORD et SCOTT). Et la performance ? L'optimiseur de PostgreSQL traite en général les deux écritures de la même façon.

Attention ON ou WHERE, avec une jointure externe

Ajout Avec un LEFT JOIN, les deux écritures ne sont plus équivalentes. Dans le ON, la condition dit quelles lignes de droite peuvent s'associer : les lignes de gauche restent toutes. Dans le WHERE, elle filtre le résultat final, et élimine les lignes de gauche sans correspondance, dont les colonnes valent NULL.

Les jointures multiples se lisent de gauche à droite :

SELECT e.nom_emp, d.nom_dep, m.nom_emp AS chef
FROM emp AS e
JOIN dep AS d ON e.id_dep = d.id_dep
LEFT JOIN emp AS m ON e.id_chef = m.id_emp;

On obtient les 14 employés avec leur département et le nom de leur chef ; KING, sans chef, garde une case chef vide grâce au LEFT JOIN. Avec un JOIN simple, il disparaîtrait (13 lignes).

Une jointure peut porter sur le résultat d'un SELECT : la sous-requête, placée dans le FROM et nommée, devient une table temporaire.

SELECT t1.col1, t2.col2
FROM table1 AS t1
JOIN (
    SELECT colX, colY
    FROM table2
    WHERE condition
) AS t2 ON t1.col1 = t2.colX;

La jointure réflexive joint une table avec elle-même. Il faut alors renommer au moins une des deux copies avec AS, et désigner chaque attribut en notation préfixée, alias_table.nom_attribut.

SELECT
    e.nom_emp AS employe,
    c.nom_emp AS chef
FROM emp AS e
JOIN emp AS c
    ON e.id_chef = c.id_emp;

13 lignes, de JONES (chef KING) à MILLER (chef CLARK) : c'est l'association réflexive « est supervisé par » du diagramme, parcourue en SQL.

Écrire une requête diapos 62–63

Face à une question en français, il faut une démarche plutôt qu'une inspiration. Et une même question admet presque toujours plusieurs requêtes justes.

Méthode Implémenter une requête SELECT diapo 62

  1. De quels attributs ai-je besoin ? Pour la sélection des données, et pour l'affichage.
  2. Quelles tables vais-je interroger ? Faut-il une ou plusieurs jointures ?
  3. Le déroulement : comment, moi, humain, je réponds à la question ? Je la découpe en sous-problèmes, puis je transpose chacun en SQL.

Toujours plusieurs possibilités diapo 63

À chacun sa préférence. Par exemple : quels sont les employés de grade 4 qui travaillent à Dallas ? Le grade d'un employé est la tranche de grade qui contient son salaire, d'où une jointure sur BETWEEN.

-- J'ai accès à tous les attributs de toutes les tables !
SELECT e.nom_emp, g.id_grade, d.loc
FROM emp AS e
JOIN grade AS g ON e.sal BETWEEN g.min_sal AND g.max_sal
JOIN dep AS d ON e.id_dep = d.id_dep
WHERE d.loc = 'Dallas' AND g.id_grade = 4;

-- Je n'ai plus accès aux attributs de dep !
SELECT nom_emp, id_grade
FROM emp JOIN grade ON sal BETWEEN min_sal AND max_sal
WHERE id_dep IN (SELECT id_dep FROM dep WHERE loc = 'Dallas') AND id_grade = 4;

-- Je n'ai plus accès qu'aux attributs de emp !
SELECT nom_emp FROM emp
WHERE sal BETWEEN (SELECT min_sal FROM grade WHERE id_grade = 4)
              AND (SELECT max_sal FROM grade WHERE id_grade = 4)
  AND id_dep IN (SELECT id_dep FROM dep WHERE loc = 'Dallas');

Les trois requêtes renvoient les mêmes employés : JONES, FORD et SCOTT. Elles diffèrent par ce qu'elles peuvent afficher : une colonne n'est affichable que si sa table est dans le FROM, pas seulement dans une sous-requête.

Complément Trois façons de trouver « ceux qui n'ont pas »

Les notes de la diapo 63 donnent, sur la base des avions du TP 2, trois requêtes pour les pilotes qui n'ont aucun vol :

SELECT numpil FROM pilote EXCEPT SELECT numpil FROM vol;
SELECT * FROM pilote WHERE numpil NOT IN (SELECT numpil FROM vol);
SELECT * FROM pilote LEFT OUTER JOIN vol ON pilote.numpil = vol.numpil WHERE numvol IS NULL;

La première est une différence d'ensembles (EXCEPT, clause de la syntaxe complète) ; la deuxième une sous-requête ; la troisième une jointure externe filtrée. Essayées sur trois pilotes dont un sans vol, elles trouvent toutes ce pilote. Mais s'il existe un vol sans pilote (numpil à NULL), la version NOT IN ne renvoie plus rien (section 6) : les deux autres restent justes.

À retenir

L'essentiel

  • Clé primaire : unique, non nulle, une seule par table, éventuellement composée ; de préférence un entier auto-incrémenté nommé id_table, jamais modifié.
  • Clé étrangère : référence une clé existante ; sans clause, supprimer ou modifier le parent est refusé. ON DELETE / ON UPDATE CASCADE, SET NULL ou SET DEFAULT changent ce comportement.
  • SERIAL (PostgreSQL) et GENERATED {ALWAYS | BY DEFAULT} AS IDENTITY (norme) numérotent automatiquement une clé primaire ; la clé étrangère qui la référence reste un INT.
  • Ajouter une association à une base existante : ALTER TABLE … ADD COLUMN, puis ADD FOREIGN KEY (et UNIQUE pour un « au plus un ») ; les données se remplissent ensuite par UPDATE, pas par une nouvelle structure.
  • Une sous-requête entre parenthèses peut fournir une valeur (UPDATE … SET, INSERT … VALUES) si elle renvoie une seule ligne ; INSERT … SELECT insère plusieurs lignes.
  • '…' encadre une valeur, "…" un nom d'objet ; les deux respectent la casse. Pas de guillemets dans les CREATE.
  • = pour une valeur, LIKE pour un motif, IN pour une liste, BETWEEN pour un intervalle, IS NULL pour l'absence ; AND avant OR.
  • Sous-requête à plusieurs résultats : IN (= ANY), NOT IN (<> ALL), op ANY, op ALL. NOT IN échoue en silence si la sous-requête contient NULL.
  • Jointures : JOIN … ON garde les correspondances ; LEFT, RIGHT, FULL OUTER JOIN gardent aussi les lignes sans partenaire (colonnes à NULL) ; CROSS JOIN fait toutes les combinaisons ; une jointure réflexive exige des alias.

Auto-évaluation

Que se passe-t-il si l'on supprime un département référencé par des employés, sans clause ON DELETE ?

La suppression est refusée : c'est l'intégrité référentielle (action par défaut NO ACTION). Avec ON DELETE CASCADE, les employés seraient supprimés ; avec ON DELETE SET NULL, leur id_dep passerait à NULL.

Pourquoi id_dir est-il déclaré UNIQUE dans dep ?

Parce qu'un employé dirige au plus un département : son numéro ne peut apparaître que dans une ligne de dep. Sans UNIQUE, la clé étrangère seule autoriserait un directeur pour plusieurs départements.

Pourquoi select * from Test; échoue-t-il sur une table créée par CREATE TABLE "Test" ?

Un nom sans guillemets est ramené en minuscules : on cherche test, alors que la table s'appelle Test. Il faudrait écrire "Test", d'où la règle de ne jamais mettre de guillemets à la création.

Quand faut-il ANY, ALL ou IN devant une sous-requête ?

Dès qu'elle peut renvoyer plusieurs lignes. Avec un simple =, PostgreSQL refuse : « more than one row returned by a subquery used as an expression ».

Pourquoi comm IN (0, NULL) ne trouve-t-il pas les employés sans commission ?

Il équivaut à comm = 0 OR comm = NULL, et une comparaison avec NULL n'est jamais vraie. Il faut comm = 0 OR comm IS NULL.

Combien de lignes donne emp RIGHT JOIN dep sur la base du TP, et pourquoi ?

15 : les 14 employés avec leur département, plus Operations, qui n'a pas d'employé et apparaît avec nom_emp à NULL. Un INNER JOIN en donne 14.

Comment trouver les départements sans employé avec une jointure ?

SELECT d.nom_dep FROM dep d LEFT JOIN emp e ON e.id_dep = d.id_dep WHERE e.id_emp IS NULL; : la jointure externe garde tous les départements, le WHERE ne garde que ceux sans correspondance.
