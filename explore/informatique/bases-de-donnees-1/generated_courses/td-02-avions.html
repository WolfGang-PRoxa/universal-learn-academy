Première version TD, p. 1

Une base volontairement minuscule : trois sortes d'informations, sur les avions, les vols du jour et leurs pilotes.

Exercice 1 Les avions, première version

Un ensemble d'aéroports souhaite sauvegarder un tout petit ensemble d'informations concernant le trafic aérien. Il faut donc mettre en place une base de données très petite qui ne permet pas de modéliser réellement le trafic aérien.

Pour les avions, par exemple, ce qui intéresse le client c'est de connaître le type et la capacité de chaque avion. On voudra par exemple savoir qu'un avion numéro X est de type A310 et qu'il contient 280 places tandis que l'avion Y est de type B747 et qu'il contient 348 places. On voudra également connaître l'aéroport de rattachement de l'avion.

On désire également conserver les informations concernant les vols sur la journée uniquement : d'où un avion est parti, à quelle heure, pour aller où à quelle heure. Finalement, on aimerait également enregistrer le pilote principal de l'avion sur ce vol, en conservant son nom et sa ville de résidence.

Deuxième version TD, p. 2

La base de la version 1 a été mise en service, et l'usage révèle trois défauts. Il faut corriger le modèle, puis la base elle-même.

Exercice 1 Les avions, deuxième version

La base « aéroport » a été implémentée dans sa première version.

Après réflexion, oh horreur, oh malheur, vous vous rendez compte que vous n'êtes pas en 3NF !! En effet, la capacité de l'avion est « théorique », c'est-à-dire qu'elle est liée au type de l'avion et pas à l'avion lui-même. Par exemple l'avion identifié 2, un B747, a 2 fauteuils cassés, sa capacité n'est plus de 348 places.

Après discussion avec l'aéroport, vous vous rendez compte que c'est bien la capacité théorique du type d'avion qu'ils souhaitent sauvegarder et non pas le nombre maximum possible de passagers de chaque avion. C'est donc bien le type général des avions qu'il faut sauvegarder. Le type est caractérisé par un nom de type (A310 ou B747 par ex.) et sa capacité. Nous modifions donc le modèle conceptuel afin de modéliser que : un avion est d'un seul type donné. En revanche, il existe plusieurs avions d'un même type.

Il y a eu des erreurs dans la saisie des noms d'aéroport. Ainsi on retrouve dans la base les valeurs Orly, orly mais aussi Orli… Il faut donc mettre à part l'information concernant l'aéroport. On souhaitera en plus du nom de l'aéroport conserver sa ville. Tous les attributs qui contenaient un nom d'aéroport devront donc maintenant être supprimés pour associer directement les identifiants d'aéroport. On se rend compte par l'usage également que ce qui est saisi dans la ville de résidence du pilote est en fait son aéroport de rattachement…

Pour finir, on souhaite s'assurer que chaque pilote principal possède la licence adéquate pour piloter l'avion sur lequel il est affecté pour un vol. Une liste des licences est donc sauvegardée dans la base (identifiant et nom). Chaque licence peut donner l'autorisation de piloter un ou plusieurs types d'avion. Chaque pilote peut avoir plusieurs licences. L'autorisation de piloter un type d'avions peut se faire via différentes licences.

À retenir

Les méthodes

  • Une base se crée dans l'ordre des références : d'abord les tables que l'on cite dans un REFERENCES.
  • Un vol 1..1 avion devient une clé étrangère NOT NULL dans vol.
  • Les heures et les dates ont leur type (time, date) : ainsi seulement les comparaisons sont justes.
  • Un attribut qui dépend d'un autre attribut non clé (la capacité, du type) viole la 3NF : on en fait une entité, reliée à l'ancienne.
  • Une valeur saisie librement et répétée (un nom d'aéroport) gagne à devenir une entité, désignée par son identifiant : plus de fautes de frappe.
  • Plusieurs associations entre les deux mêmes classes (départ, arrivée) donnent plusieurs clés étrangères, nommées d'après leur rôle.
  • ALTER TABLE ajoute ou supprime une colonne ; avec des données, on ajoute, on remplit, puis on supprime.

Auto-évaluation

Avion(id_avion, nom_type, nb_place) : quelle dépendance pose problème ?

nom_type → nb_place : un attribut non clé dépend d'un autre attribut non clé. La relation n'est pas en 3NF.

Pourquoi créer pilote et avion avant vol ?

Parce que vol les référence : une clé étrangère ne peut citer qu'une table qui existe.

Combien de clés étrangères vers Aeroport dans Vol, version 2 ?

Deux : l'aéroport de départ et celui d'arrivée, deux associations distinctes.

Licence — Type est * — * : que devient-elle ?

Une relation Licence_Type(#id_licence, #id_type), de clé le couple (règle 2).
