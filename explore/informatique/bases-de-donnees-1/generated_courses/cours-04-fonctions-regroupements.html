Bases de données Cours 4 · L2

Fonctions, regroupements et évolution d'une base

Jusqu'ici, une requête renvoyait des lignes de la base. Ce dernier cours apprend à les transformer (fonctions), à les résumer (agrégats, GROUP BY, HAVING) et à les trier ou les paginer. Il termine par la modification d'une base en service : mettre à jour des données à partir d'autres tables, et corriger un modèle mal conçu sans perdre de données.

Les fonctions prédéfinies diapos 6–11

Une colonne n'est pas toujours affichable telle quelle : on veut un nom en minuscules, les trois premières lettres d'un métier, une date décalée de trente ans. Les fonctions transforment les valeurs ligne par ligne.

Trois catégories diapos 6–7

  • Les fonctions prédéfinies classiques : voir la documentation, docs.postgresql.fr/14/functions.html.
  • Les fonctions d'agrégation, très pratiques dans les SELECT avec GROUP BY (section 3).
  • Les fonctions définies par l'utilisateur, qui sont des objets du SGBD : elles seront vues en L3.

PostgreSQL offre un grand nombre de fonctions, dont beaucoup hors du standard SQL, ce qui pose un problème de compatibilité avec les autres SGBD. Ces fonctions sont « typées » : chacune attend des arguments d'un certain type, et renvoie une valeur d'un certain type.

Fonctions mathématiques et de caractères diapos 8–10

  • Mathématiques : valeur absolue ABS, arrondi ROUND, racine carrée SQRT, puissance POWER, SIN(x), COS(x), TAN(x), EXP(x), LOG(x)…
  • Sur les caractères, et aussi de formatage des types, de dates, de géométrie…

Complément TRANSLATE ou REPLACE

TRANSLATE travaille caractère par caractère : chaque caractère de val1 est remplacé par le caractère de même rang dans val2, et supprimé si val2 est plus courte. REPLACE remplace une sous-chaîne entière. Ainsi translate('abcabc', 'bc', 'X') donne aXaX (b devient X, c disparaît), comme replace('abcabc', 'bc', 'X'), mais pour une autre raison.

Bien choisir son type diapo 11

Le type d'une colonne décide des fonctions qu'on pourra lui appliquer. Exemple du TP 1 :

  • date_emb est de type date : on accède aux intervalles (INTERVAL). La question 10 du TP 1 (« donner un coup de jeune » en ajoutant 30 ans aux dates d'embauche) s'écrit date_emb + INTERVAL '30 years' : KING passe du 17 novembre 1981 au 17 novembre 2011.
  • Type numeric ou float ?

numeric

  • ++ exactitude (attention aux arrondis) ;
  • bien pour les calculs en euros, dont la plus petite unité est le centime ;
  • -- calcul lent.

float ou real

  • -- exactitude variable ;
  • ++ calcul plus rapide.

Pour en savoir plus : docs.postgresql.fr/14/datatype-numeric.html.

Complément L'exactitude, concrètement

Un float stocke les nombres en binaire, où 0,1 n'a pas d'écriture exacte. Sous PostgreSQL, 0.1::float8 + 0.2::float8 vaut 0.30000000000000004, et le test = 0.3 est faux ; avec numeric, il est vrai. Pour des salaires, un centime perdu à chaque calcul finit par se voir : d'où numeric(7,2) dans la table emp.

Les fonctions d'agrégation diapos 12–16

Combien d'employés ? Quel salaire moyen ? Ces questions ne portent pas sur une ligne, mais sur un ensemble de lignes. Les fonctions d'agrégation calculent une seule valeur à partir d'un ensemble de valeurs.

Définition Fonction d'agrégation diapo 12

Une fonction d'agrégation (aggregate function) calcule une seule valeur à partir d'un ensemble de valeurs en entrée. Elle s'écrit nom_agrégat(expression), nom_agrégat(ALL expression), nom_agrégat(DISTINCT expression) ou nom_agrégat(*), et s'utilise dans la clause SELECT et dans la clause HAVING.

Attention Le choix de l'expression à agréger diapo 14

  • agrégation(*) représente le tuple complet : les lignes qui contiennent des NULL sont comptées.
  • agrégation(colonne) porte sur un attribut : elle ignore les NULL.
  • DISTINCT est appliqué avant la fonction.
  • La fonction d'agrégation ne renvoie qu'une seule valeur, donc une seule ligne de résultat.

Exemple Compter avec COUNT diapos 15–16

       count(DISTINCT id_chef) AS nombre_manager,
       count(*)                AS toutes_lignes
FROM emp;

De même, SELECT count(DISTINCT metier) FROM emp; donne 5, et SELECT avg(comm) FROM emp; donne 550 : la moyenne ne porte que sur les quatre commissions renseignées, \((300 + 500 + 1400 + 0) / 4\), et pas sur les 14 employés.

Trier et regrouper : ORDER BY, GROUP BY, HAVING diapos 17–33

Des neuf clauses de SELECT, on connaît SELECT, FROM, WHERE et les opérations ensemblistes. Restent le tri, les regroupements et la restriction des groupes.

La clause ORDER BY diapos 18–20

Sans ORDER BY, l'ordre des lignes est aléatoire et non garanti. La clause trie les lignes du résultat :

ORDER BY expression [ASC | DESC] [, ...]
  • expression : un champ, un ordinal (numéro de colonne du résultat) ou une opération mathématique de base ;
  • ASC : ordre ascendant, tri croissant (par défaut) ; DESC : ordre descendant, tri décroissant ;
  • on peut trier selon plusieurs champs, dans l'ordre précisé.

SELECT * FROM emp ORDER BY nom_emp; range les 14 employés par ordre alphabétique : ADAMS, ALLEN, BLAKE, CLARK, FORD, JAMES, JONES, KING, MARTIN, MILLER, SCOTT, SMITH, TURNER, WARD (diapo 19).

Exemple Trier selon deux colonnes diapo 20

SELECT sal, comm FROM emp ORDER BY 2, 1;

Tri par commission (colonne 2), puis, à commission égale, par salaire (colonne 1). La valeur NULL est considérée comme supérieure à toute autre valeur : les dix employés sans commission viennent en dernier, triés par salaire.

La clause GROUP BY diapos 21–26

Définition GROUP BY diapo 21

GROUP BY expression [, ...] classe les données par groupes. Un groupe est le sous-ensemble des lignes qui ont la même valeur pour les attributs précisés. L'expression est un nom de colonne en entrée, un nom ou un numéro de colonne en sortie, ou une expression sur les champs en entrée. La clause se place après WHERE et avant ORDER BY.

  • Chaque attribut de la clause SELECT doit se trouver dans la clause GROUP BY, ou être dans une fonction d'agrégation.
  • Une seule ligne est produite par groupe.

Les diapos 22 à 26 construisent l'idée pas à pas. SELECT avg(sal) FROM emp; calcule le salaire moyen de toute l'entreprise : une seule valeur, 2227.11. Avec GROUP BY metier, la moyenne est calculée au sein de chaque groupe :

SELECT avg(sal) FROM emp GROUP BY metier;

Note Remarques de la diapo 24

  • Une seule ligne est retournée par groupe, et la fonction est appliquée au sein de chaque groupe.
  • La colonne calculée ne porte que le nom de la fonction (avg), sans indication d'attribut.
  • Si l'attribut groupé n'est pas indiqué dans le SELECT, on ne comprend pas forcément l'affichage : cinq moyennes, mais de quels métiers ? D'où SELECT metier, avg(sal) … GROUP BY metier.

À vérifier Les diapos 30 à 32 affichent 3145,46 pour les analystes ; le calcul donne \((3056{,}33 + 3234{,}62) / 2 = 3145{,}475\), soit 3145,48 en arrondissant.

Même démarche pour compter (diapos 25–26) : SELECT count(*) FROM emp; compte toutes les lignes, et avec GROUP BY id_dep, les lignes de chaque département.

SELECT count(*), id_dep FROM emp GROUP BY id_dep;

GROUP BY avec WHERE, et les sous-groupes diapos 27–28

On combine GROUP BY avec un WHERE, à placer avant : le WHERE choisit d'abord les lignes, qui sont ensuite regroupées.

SELECT metier, avg(sal) FROM emp
WHERE nom_emp LIKE '%A%'
GROUP BY metier;

Attention Aux attributs utilisés dans quelle clause diapo 27

SELECT nom_emp, metier, avg(sal) FROM emp
WHERE nom_emp LIKE '%A%'
GROUP BY metier;

Cette requête ne fonctionne pas : il existe plusieurs valeurs de nom_emp par métier, et une ligne par groupe ne peut en afficher qu'une. PostgreSQL : column "emp.nom_emp" must appear in the GROUP BY clause or be used in an aggregate function. Sur la diapo, les apostrophes de ‘%A%’ sont typographiques ; il faut '%A%'.

On peut former des sous-groupes en regroupant selon plusieurs colonnes, et l'ordre des colonnes du GROUP BY n'a pas d'importance (diapo 28) : GROUP BY metier, id_chef et GROUP BY id_chef, metier donnent les mêmes quatre groupes, aux mêmes moyennes.

SELECT id_chef, metier, avg(sal) FROM emp
WHERE nom_emp LIKE '%A%'
GROUP BY metier, id_chef;

La clause HAVING diapos 29–33

Définition HAVING diapo 29

HAVING applique une restriction sur les groupes : HAVING est à GROUP BY ce que WHERE est à SELECT.

  • WHERE restreint les enregistrements ; HAVING restreint les groupes.
  • Même syntaxe que WHERE, mais on n'y trouve que des fonctions d'agrégation et des expressions qui figurent dans la clause GROUP BY.
SELECT avg(sal) FROM emp GROUP BY metier HAVING avg(sal) > 1500;

Parmi les cinq moyennes par métier, HAVING ne garde que celles qui dépassent 1 500 : les secrétaires (1319.00) disparaissent, il reste Vendeur, Manager, Analyste et President (diapos 30–31).

Exercice 1 Problème ? diapo 32

Parmi ces quatre requêtes, lesquelles provoquent une erreur, et pourquoi ? Que renvoient les autres ?

SELECT metier, avg(sal) FROM emp GROUP BY metier HAVING avg(sal) > 1500;
SELECT avg(sal) FROM emp HAVING nom_emp LIKE '%A%';
SELECT nom_emp FROM emp GROUP BY metier HAVING nom_emp LIKE '%A%';
SELECT metier, avg(sal) FROM emp GROUP BY metier HAVING metier LIKE '%A%';
Indice

Dans le HAVING et le SELECT d'une requête groupée, une colonne doit être groupée ou agrégée. Sans GROUP BY mais avec un agrégat, toute la table forme un seul groupe.

Solution proposée
  • 1 : correcte. Quatre lignes : Vendeur 1532.22, Manager 2827.91, Analyste 3145.48, President 5000.00 (le tableau de la diapo).
  • 2 : erreur. Sans GROUP BY, toute la table forme un seul groupe, et nom_emp n'y a pas une valeur unique. Pour ne moyenner que les employés dont le nom contient un A, la condition porte sur les lignes : elle va dans un WHERE.
  • 3 : erreur, pour la même raison : nom_emp n'est ni groupé ni agrégé, ni dans le SELECT, ni dans le HAVING.
  • 4 : correcte, car metier est groupé. Mais LIKE distingue les majuscules : seul « Analyste » contient un A majuscule, et le résultat n'a qu'une ligne. Avec ILIKE, on obtient Manager, Analyste et Secretaire. Une condition sur une colonne groupée pourrait d'ailleurs aller dans le WHERE.

Exemple Le métier au salaire moyen le plus élevé diapo 33

Quel est le métier qui a en moyenne le salaire le plus élevé ? La requête groupée donne les cinq moyennes, et c'est la plus forte que l'on veut. On copie-colle cette requête comme sous-requête dans le HAVING :

SELECT metier, avg(sal) FROM emp GROUP BY metier
HAVING avg(sal) >= ALL (SELECT avg(sal) FROM emp GROUP BY metier);

La sous-requête renvoie la colonne des cinq moyennes. On compare la moyenne de chaque groupe à celles de tous les groupes, et la plus forte l'emporte : President, 5000.

LIMIT, OFFSET et l'ordre d'exécution diapos 34–37

Il reste deux clauses pour limiter l'affichage, puis une vue d'ensemble : dans quel ordre PostgreSQL exécute-t-il réellement toutes ces clauses ?

Les clauses LIMIT et OFFSET diapos 34–35

LIMIT {ALL | nombre}
OFFSET début

Elles restreignent le nombre de lignes renvoyées : ALL (par défaut) les garde toutes ; nombre est le nombre total de lignes à afficher ; début est le nombre de lignes à sauter avant d'afficher.

SELECT * FROM emp ORDER BY nom_emp LIMIT 4 OFFSET 2;

Dans l'ordre alphabétique, on saute ADAMS et ALLEN, puis on affiche quatre employés : BLAKE, CLARK, FORD et JAMES.

Attention Pas à la place d'un MAX diapo 34

Il ne faut pas utiliser LIMIT à la place d'un MAX : risque d'incohérence. Ajout Exemple : le dernier embauché de 1981. … ORDER BY date_emb DESC LIMIT 1 renvoie FORD seul, alors que FORD et JAMES ont été embauchés le même jour, le 3 décembre 1981. La version avec WHERE date_emb = (SELECT max(date_emb) FROM emp WHERE …) renvoie les deux.

L'ordre d'exécution diapo 37

Les clauses ne s'exécutent pas dans l'ordre où on les écrit. D'après la diapo :

  1. FROM : les données de départ, jointures comprises ;
  2. WHERE : le filtre des lignes ;
  3. les fonctions de groupe et GROUP BY ;
  4. HAVING : le filtre des groupes ;
  5. SELECT : le calcul des colonnes affichées ;
  6. UNION, INTERSECT, EXCEPT ;
  7. ORDER BY ;
  8. DISTINCT ;
  9. OFFSET ;
  10. LIMIT.

Complément Ce que cet ordre explique

  • Un alias défini dans le SELECT (étape 5) n'existe pas encore dans le WHERE (étape 2) : WHERE tot > 2000 échoue. Il est en revanche utilisable dans ORDER BY.
  • Un agrégat ne peut pas figurer dans le WHERE, exécuté avant le regroupement : c'est le rôle du HAVING.
  • À vérifier La documentation de PostgreSQL (commande SELECT) place l'élimination des doublons par DISTINCT avec le calcul du SELECT, donc avant les opérations ensemblistes et ORDER BY, et non après comme sur la diapo. Le résultat est le même dans les cas courants.

UPDATE et DELETE à partir d'autres tables diapos 38–42

UPDATE et DELETE ont accès à tous les attributs de la table qu'ils modifient. Mais comment tenir compte d'une information rangée dans une autre table ?

  • Norme SQL : faire une sous-requête.
  • PostgreSQL : FROM … WHERE … pour UPDATE, USING … WHERE … pour DELETE. C'est une jointure écrite dans la commande de modification.

Exemple Enregistrer un directeur diapos 39, 41

Au lieu d'une sous-requête par directeur (cours 3), on peut utiliser le FROM pour prendre l'information dans emp :

-- SQL99 : sous-requête
UPDATE dep SET id_dir = (SELECT id_emp FROM emp WHERE nom_emp = 'KING')
WHERE nom_dep = 'Comptable';

-- PostgreSQL : FROM
UPDATE dep SET id_dir = id_emp FROM emp
WHERE nom_dep = 'Comptable' AND nom_emp = 'KING'
  AND dep.id_dep = emp.id_dep;

Il faut faire de même avec les autres directeurs. À vérifier Sur la diapo 41, la sous-requête s'écrit (SELECT id_emp FROM emp nom_emp='KING’), sans WHERE et avec une apostrophe typographique : corrigée ici.

Ajout La condition dep.id_dep = emp.id_dep ajoute une exigence que la sous-requête n'a pas : le directeur doit appartenir au département qu'il dirige. C'est vrai pour KING, FORD et BLAKE ; pour un directeur venu d'un autre département, cet UPDATE ne modifierait aucune ligne.

Exemple Doubler des salaires selon la ville diapo 40

Objectif : doubler le salaire des personnes qui travaillent dans une ville dont le nom comporte un C.

-- SQL99
UPDATE emp SET sal = sal * 2
WHERE id_dep IN (SELECT id_dep FROM dep WHERE loc LIKE '%C%');

-- Version PostgreSQL (pas dans la norme)
UPDATE emp SET sal = sal * 2 FROM dep
WHERE loc LIKE '%C%' AND emp.id_dep = dep.id_dep;

Les deux commandes modifient les 6 employés de Chicago, seule ville avec un C majuscule. Dans la seconde, la condition de jointure emp.id_dep = dep.id_dep est indispensable ; sans préfixe, id_dep = id_dep est refusé comme ambigu.

Exemple Les DELETE diapo 42

-- Suppression de tous les enregistrements
DELETE FROM emp;
-- Suppression selon une condition
DELETE FROM emp WHERE date_emb >= '2001-01-01';
-- Suppression selon un attribut issu d'une autre table, SQL99
DELETE FROM emp WHERE id_dep IN (SELECT id_dep FROM dep WHERE loc = 'CHICAGO');
-- La même, PostgreSQL
DELETE FROM emp USING dep
WHERE dep.id_dep = emp.id_dep AND loc = 'CHICAGO';

À vérifier Dans la base du TP, la ville s'écrit 'Chicago' : avec 'CHICAGO', ces deux commandes ne suppriment aucune ligne, puisque la comparaison respecte la casse (cours 3). Avec 'Chicago', elles suppriment les 6 employés du département 30. Les apostrophes typographiques de la diapo sont aussi à remplacer.

Modifier une relation sans perdre de données diapos 43–49

Une erreur de modélisation découverte après coup ne se corrige pas en supprimant la table : elle contient des données. On la corrige par étapes, en respectant deux règles.

Le principe diapos 43–45

La relation implémentée est R1(a:int, b1:varchar, b2:varchar, c:varchar). C'est une mauvaise modélisation : b1 et b2 doivent être dans une relation à part. On veut obtenir R1(a:int, #b:int, c:varchar) et R2(b:int, b1:varchar, b2:varchar).

Méthode Restructurer une relation en cinq étapes diapos 43–45

Deux règles : on ne perd pas les données ; on assure les contraintes de clé étrangère.

  1. Création de la nouvelle table R2 (structure), avec une clé primaire de type entier : GENERATED ALWAYS AS IDENTITY.
  2. Insertion des enregistrements dans R2 : on liste les insertions si l'on connaît les données a priori, ou on les extrait de R1 par un INSERT INTO … SELECT, grâce au GENERATED ALWAYS AS IDENTITY qui numérote seul.
  3. Insertion d'une nouvelle colonne dans R1, de type INTEGER, avec une clé étrangère vers R2.
  4. Mise à jour des enregistrements : on remplit la nouvelle colonne avec les bonnes informations.
  5. Suppression des colonnes redondantes de R1, après s'être assuré que l'étape 4 est correcte.

Exemple avec les avions diapos 46–49

Dans la première version de la base Avions (TP 2), il y a des aéroports partout.

Ce n'est pas possible : cela va forcément entraîner des erreurs lors de la saisie, avec ou sans majuscules, avec ou sans accents… Il faut créer une entité Aéroport pour uniformiser les noms. On applique les cinq étapes.

  1. Création de la table aéroport (diapo 47). 
    CREATE TABLE aeroport (
    nom_aero  varchar(30),
    nom_ville varchar(30),
    id_aero   INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY
);
  2. Insertion des aéroports existants : la liste de tous les aéroports trouvés dans la base (diapo 47). 
    INSERT INTO aeroport
    SELECT nom_aero FROM pilote
    UNION SELECT nom_aero_ratt FROM avion
    UNION SELECT nom_aero_dep FROM vol
    UNION SELECT nom_aero_arr FROM vol;
  3. Modification des tables concernées, par exemple Pilote : on ajoute une autre colonne pour l'id_aero (diapo 48). 
    ALTER TABLE pilote ADD COLUMN id_aero int REFERENCES aeroport;
  4. Mise à jour des données de Pilote (diapo 48). 
    UPDATE pilote SET id_aero = (SELECT aeroport.id_aero FROM aeroport
                             WHERE pilote.nom_aero = aeroport.nom_aero);
  5. Finalisation de la structure de Pilote : suppression de la colonne nom_aero (diapo 49). Il faut faire de même avec toutes les autres tables qui utilisent des noms d'aéroports. 
    ALTER TABLE pilote DROP COLUMN nom_aero;

Complément Pourquoi cela marche, et ce qu'il faut vérifier

  • L'identifiant est placé en dernière colonne : l'INSERT … SELECT d'une seule colonne remplit nom_aero, et id_aero est généré. UNION élimine les doublons : sur les données du TP 2, on obtient 9 aéroports.
  • L'UPDATE contient une sous-requête corrélée : elle fait référence à pilote.nom_aero, la ligne en cours de mise à jour, et elle est donc évaluée pour chaque pilote.
  • Avant l'étape 5, on vérifie : SELECT * FROM pilote WHERE id_aero IS NULL; ne doit rien renvoyer. Un pilote resté à NULL aurait un nom d'aéroport absent de la table, et le supprimer effacerait cette information.
  • La table Vol a deux aéroports : elle reçoit deux clés étrangères, id_aero_dep et id_aero_arr, vers la même table. C'est ce que demande la deuxième version du TP 2.
  • À vérifier La diapo 48 écrit REFERNCES, que PostgreSQL refuse (syntax error at or near "REFERNCES") : il faut REFERENCES. Il manque aussi le point-virgule après le CREATE TABLE de la diapo 47.

Exercice 3 Migrer les aéroports des pilotes diapos 46–49

Sur la première version de la base Avions, écrire le script complet qui crée la table aeroport (identifiant généré), y insère tous les aéroports cités dans la base, relie chaque pilote à son aéroport par une clé étrangère id_aero, puis supprime la colonne nom_aero de pilote.

Indice

Les cinq étapes, dans l'ordre. Les noms d'aéroports sont dans pilote.nom_aero, avion.nom_aero_ratt, vol.nom_aero_dep et vol.nom_aero_arr.

À retenir

L'essentiel

  • Les fonctions transforment chaque valeur : UPPER, LOWER, SUBSTRING, REPLACE, TRANSLATE, LENGTH, ROUND… Le type d'une colonne décide des fonctions utilisables : date donne accès à INTERVAL, numeric est exact, float rapide mais approché.
  • Un agrégat (COUNT, SUM, AVG, MIN, MAX) réduit un ensemble de lignes à une valeur. count(*) compte les lignes ; count(colonne) et les autres agrégats ignorent les NULL ; DISTINCT s'applique avant.
  • ORDER BY est le seul moyen d'obtenir un ordre garanti ; NULL est trié après toutes les valeurs en ordre croissant.
  • GROUP BY produit une ligne par groupe ; toute colonne du SELECT est groupée ou agrégée.
  • WHERE filtre les lignes avant le regroupement, HAVING filtre les groupes après ; un agrégat ne va jamais dans le WHERE.
  • LIMIT n OFFSET k saute k lignes puis en garde n ; il ne remplace pas un MAX, qui garde les ex æquo.
  • Ordre d'exécution : FROM, WHERE, GROUP BY, HAVING, SELECT, opérations ensemblistes, ORDER BY, OFFSET, LIMIT.
  • Pour modifier selon une autre table : une sous-requête (norme), ou UPDATE … FROM et DELETE … USING (PostgreSQL), sans oublier la condition de jointure.
  • Restructurer une relation : créer la table, la remplir à partir des données existantes, ajouter la clé étrangère, la remplir, vérifier, puis supprimer les anciennes colonnes.

Auto-évaluation

Sur emp, que valent count(*), count(comm) et count(DISTINCT id_dep) ?

14 lignes ; 4 commissions renseignées ; 3 départements différents (10, 20 et 30). count(colonne) ignore les NULL, DISTINCT retire les doublons avant de compter.

Pourquoi avg(comm) vaut-il 550 et pas \(2200 / 14\) ?

Parce que AVG ignore les NULL : la moyenne porte sur les 4 commissions renseignées, \(2200 / 4 = 550\). Pour la moyenne sur tous les employés, on écrit avg(COALESCE(comm, 0)).

Pourquoi SELECT nom_emp, avg(sal) FROM emp GROUP BY metier; échoue-t-il ?

Un groupe (un métier) contient plusieurs noms, et la ligne du groupe ne peut en afficher qu'un. Toute colonne du SELECT doit être dans le GROUP BY ou dans un agrégat.

WHERE ou HAVING pour « les métiers dont le salaire moyen dépasse 2 000 » ?

HAVING avg(sal) > 2000 : la condition porte sur un groupe et contient un agrégat, calculé après le WHERE.

Que renvoie ORDER BY nom_emp LIMIT 3 OFFSET 3 ?

Les 4e, 5e et 6e employés par ordre alphabétique : CLARK, FORD, JAMES (après ADAMS, ALLEN et BLAKE).

Dans quel ordre créer la colonne id_aero et supprimer nom_aero ?

Créer id_aero (avec sa clé étrangère), la remplir par un UPDATE, vérifier qu'aucun pilote n'est resté à NULL, et seulement ensuite supprimer nom_aero : sinon l'information est perdue.

Pourquoi DELETE … WHERE loc = 'CHICAGO' ne supprime-t-il rien sur la base du TP ?

La ville est enregistrée 'Chicago', et la comparaison de chaînes respecte la casse. Une condition qui ne correspond à aucune ligne n'est pas une erreur : la commande répond DELETE 0.
