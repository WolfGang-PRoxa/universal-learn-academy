TP 2 : plateforme de jeux en ligne (suite)

On reprend la base de la plateforme de jeux créée au TP 1 : schémas, fonctions SQL, séquence, CTE et fonctions de fenêtrage, modification de tables, rôles et privilèges entre binômes, puis premiers pas en PL/pgSQL. Pour travailler chez soi, une console SQL rejoue la base du TP 1 et le compte rendu sur une base PostgreSQL neuve.

Objectifs

  • Gérer les schémas d'une base et son search_path.
  • Écrire des fonctions SQL, et les appeler dans des requêtes.
  • Créer une séquence et l'associer à une colonne.
  • Écrire des requêtes avec des CTE et des fonctions de fenêtrage.
  • Modifier des tables et leurs contraintes, gérer des rôles et des privilèges, écrire ses premières fonctions PL/pgSQL.

À rendre

  • Comme au TP 1, un compte rendu TP2_Monnom.txt (pas d'odt, de rtf ou autre format, et pas de .zip), avec les requêtes de chaque question.
  • Le TP se termine d'une semaine sur l'autre.
  • Cours à revoir : les fonctions SQL, puis, dans le cours 3, les séquences, les rôles, les CTE, le fenêtrage et PL/pgSQL.

Consignes p. 1

Les TP doivent être finis d'une semaine sur l'autre. Lors d'une nouvelle séance, vous commencez le nouveau sujet et n'hésitez pas à poser des questions sur l'ancien TP si vous avez besoin d'aide MAIS le TP réalisé pendant la séance est bien le nouveau sujet.

Compte rendu de TP : afin de garder une trace de votre travail, vous devez écrire dans un fichier TPX_Monnom.txt (pas d'odt, de rtf ou autre format… et pas de .zip !) les requêtes associées à chaque question.

Pour commencer ce TP, vous devez être connecté sur votre base de données jeu (créée lors du TP précédent).

Rappel du modèle relationnel p. 1

Fonctions SQL

  1. Créer la fonction SQL f_nb_avat() qui renvoie le nombre d'avatars d'un visiteur (login) donné jouant un rôle donné dans une de ses parties. Par exemple, on veut savoir combien le visiteur « Visit » a d'avatars qui jouent le rôle « gentil », quel que soit le jeu.
  2. Créer la fonction SQL f_topscore() qui renvoie pour un jeu donné le meilleur score et le login du visiteur auquel appartient l'avatar détenant ce score sous la forme d'une seule chaîne de caractères : « login 372000 ». Attention : pour cela la définition de la fonction doit être dans un autre séparateur que ' '. Par exemple, CREATE FUNCTION … AS $$ select blabla ; $$ LANGUAGE SQL ; Conseil : n'hésitez pas à vous servir de la vue du TP précédent.
  3. Créer la fonction SQL f_gentillesse() qui renvoie un booléen : vrai (valeur = t) si le visiteur passé en paramètre joue plus souvent en tant que gentil qu'en tant que méchant ; faux (valeur = f) sinon. Note : cette fonction peut faire doublement appel à la fonction f_nb_avat()…

SELECT de fonction…

  1. Combien Dominic a-t-il d'avatars qui ont un rôle de gentil ? et de méchant ?

Séquences

  1. On souhaite que chacun des objets créés soit de puissance plus importante que les précédents. Note : la puissance est un attribut de la table objet.
    1. Quelle est la valeur maximale actuelle de puissance des objets ?
    2. Créer une séquence seq_puiss initialisée à cette valeur (donner le chiffre) et s'incrémentant de 10 en 10.
    3. Associez seq_puiss à l'attribut puissance de la table objet afin que ce soit la valeur par défaut de tout nouvel objet créé.

Rôles (30 minutes maximum)

  1. Modifiez votre mot de passe (notez-le pour ne pas l'oublier !).
  2. Quelles sont les commandes qui permettent de :
    1. savoir avec quel rôle je me suis connecté(e) au SGBD ;
    2. savoir quel est le rôle que j'ai actuellement ;
    3. changer de rôle ;
    4. réinitialiser mon rôle.
  3. Votre rôle a été modifié afin que vous ayez les droits pour créer vous-même un rôle. Quelle commande a été appliquée ? (Attention, elle ne fonctionnera pas pour vous qui n'êtes pas super-utilisateur.)

Chez soi : la console SQL du TP

Le serveur de la fac n'est pas accessible de chez soi. La console ci-dessous exécute le compte rendu entier sur une base PostgreSQL neuve (PGlite), par le serveur local des quiz : studies/lancer.bat, puis cette page ouverte depuis le portail. Sans le serveur, on peut écrire, mais pas exécuter.

  1. Le TP 2 part de la base du TP 1. En tête de la console, on colle donc le compte rendu du TP 1 : le menu ⋯ de la console du TP 1 en copie le texte, ou bien on reprend TP1_Monnom.txt. Il doit au moins contenir le script complété (tables jeu, partie et save), les schémas jeu, toto1 et toto2, le search_path, les modifications des questions 14 à 16 et les vues.
  2. Les réponses du TP 2 s'écrivent à la suite, dans l'ordre des questions. Exécuter (ou Ctrl + Entrée) rejoue tout, depuis le début, sur une base neuve, et affiche le résultat de la dernière requête qui renvoie des lignes, ou la première erreur.
  3. Le travail s'enregistre tout seul : dans le navigateur, et, avec le serveur, dans le dossier td_results/ de ce cours, dans ton espace. Le menu ⋯ copie le texte, à coller dans TP2_Monnom.txt.

Attention Ce qui ne se fait qu'à la fac

  • Les commandes du client psql (\dn, \dt, \du, \c) ne sont pas du SQL : la console les refuse. On les garde en commentaire (-- \du) ; les requêtes sur les catalogues (information_schema.schemata, pg_roles), elles, fonctionnent.
  • Rôles et privilèges : CREATE ROLE, GRANT, SET ROLE, RESET ROLE, current_user et session_user s'exécutent, mais la console travaille en super-utilisateur, sur une base nommée postgres : aucun droit n'y est refusé. Les questions 21, 25 et 26, qui portent sur ce qu'un rôle a le droit de faire, et le travail en binôme ne se vérifient qu'à la fac.
  • Un RAISE NOTICE (questions 28 et suivantes) n'apparaît pas dans les résultats de la console : il se voit dans psql.

À retenir

L'essentiel

  • Le TP 2 travaille sur la base du TP 1 : si aucune table ne s'affiche, c'est le search_path qui ne parcourt plus le schéma jeu.
  • Le corps d'une fonction s'écrit entre $$ … $$ plutôt qu'entre apostrophes, pour ne pas avoir à doubler celles du code.
  • Le compte rendu TP2_Monnom.txt garde chaque requête, dans l'ordre des questions ; le TP se termine d'une semaine sur l'autre.
  • Les questions 11 à 15 reprennent les CTE et les fonctions de fenêtrage du cours 3 : moyenne de moyennes, rang dans un groupe, total sans fusionner les lignes, top 2 par jeu.
  • Chez soi, la console rejoue la base du TP 1 puis le compte rendu du TP 2 ; les commandes psql et les refus de droits ne s'y voient pas.

Auto-évaluation

Les tables du TP 1 ont disparu à la reconnexion. Que s'est-il passé ?

Elles sont toujours dans le schéma jeu, mais le search_path est revenu à sa valeur par défaut, qui ne le parcourt pas. On liste les schémas, puis on remet jeu dans le search_path.

Pourquoi le sujet demande-t-il $$ … $$ plutôt que ' … ' pour le corps de f_topscore ?

Le corps contient lui-même des chaînes entre apostrophes (l'espace entre le login et le score) : entre apostrophes, il faudrait toutes les doubler. Les dollars délimitent le corps sans conflit.

Pourquoi faut-il coller le compte rendu du TP 1 en tête de la console du TP 2 ?

Chaque exécution part d'une base neuve : rien ne reste d'une exécution à l'autre, ni d'une page à l'autre. Pour que les tables, les modifications et les vues du TP 1 existent quand arrivent les questions du TP 2, il faut les recréer à chaque fois, avant elles.

Pourquoi la console ne montre-t-elle pas le message de bonjour() ?

Un RAISE NOTICE n'est pas un résultat de requête : psql l'affiche à part, mais la console n'affiche que les lignes renvoyées.
