TP 1 : plateforme de jeux en ligne

Une plateforme de jeux en ligne : des visiteurs, leurs avatars, les objets qu'ils achètent, les jeux auxquels ils participent et leurs sauvegardes. On se connecte au serveur PostgreSQL de la fac, on crée des schémas, on complète et on exécute le script de la base, on la modifie, puis on l'interroge et on crée des vues. Pour travailler chez soi, une console SQL rejoue tout le compte rendu sur une base PostgreSQL neuve.

Objectifs

  • Se connecter au serveur PostgreSQL de la fac et interroger ses catalogues.
  • Créer des schémas et régler le search_path.
  • Compléter et exécuter un script de création : tables, types, contraintes.
  • Modifier une base existante sans perdre de données, puis l'interroger et créer des vues.

À rendre

  • Rien : le compte rendu TP1_Monnom.txt ou .sql n'est pas à rendre. Il garde la trace du travail, le chargé de TP s'en sert pour vérifier en séance, et il est autorisé au TP noté.
  • Cours à revoir : le langage SQL.

Consignes p. 1

Compte rendu
On écrit dans un fichier TPX_Monnom.txt ou TPX_Monnom.sql (pas d'odt, de rtf ni d'autre format, et pas de zip) les requêtes de chaque question. Ce compte rendu n'est pas à rendre : il sert à garder une trace du travail, et au chargé de TP pour le vérifier et le corriger pendant la séance. On a le droit de le consulter pendant le TP noté.
Suivi
On communique avec son chargé de TP tout au long de la séance. Chaque fois que l'on passe à la question suivante, la précédente est notée dans le compte rendu.
Aide
Beaucoup de solutions se trouvent dans les supports de cours. Ce TP applique les notions vues au premier semestre et lors du premier cours de SQL de ce semestre.

Le modèle de la base p. 1

Des visiteurs créent des avatars, chacun d'une race ; ils achètent des objets ; leurs avatars participent à des jeux, avec un rôle et un meilleur score, et y font des sauvegardes.

Connexion à PostgreSQL p. 1–2

On se connecte d'abord à sa base de données, sous son propre utilisateur. Le serveur PostgreSQL est hébergé sur le serveur de l'IC2 nommé erebor, et le nom d'utilisateur Unix, le nom d'utilisateur PostgreSQL et le nom de la base sont les mêmes : le numéro étudiant.

$ psql -h erebor -U num_etu

Le mot de passe est formé des deux premières lettres du nom, des deux premières lettres du prénom et des deux premiers caractères du numéro étudiant, le tout en minuscules : pour John Doe, s245681, c'est dojos2.

Remarque Rester dans psql

Pour se connecter à une autre base de données, on reste dans l'environnement de PostgreSQL : la commande Unix psql ne sert plus.

Les questions p. 2–3

Les questions du sujet, dans son ordre et avec ses intitulés de parties.

Database

  1. Listez l'ensemble des bases de données disponibles par une commande PostgreSQL, puis par une commande SQL (il faut pour cela interroger le bon catalogue).
  2. Listez toutes les tables de votre base de données. Rien ne s'affiche ? N'oubliez pas de faire la liste de toutes les tables qui appartiennent à tous les schémas.
  3. Connectez-vous à la base de données template1. Listez toutes les tables. Vous devriez retrouver exactement le même résultat qu'à la requête précédente.
  4. Reconnectez-vous à votre base de données afin de pouvoir travailler.

Schéma

  1. Utilisez une commande PostgreSQL pour lister les schémas, puis une commande DML pour écrire le nombre exact de schémas (interroger un catalogue… la mauvaise réponse est 1, la bonne réponse est 4).
  2. Quel est le nom des schémas qui ne contiennent aucune table ?
  3. Créez les schémas toto1, toto2 et jeu.
  4. Modifiez votre search_path pour travailler dans le schéma jeu en priorité, puis dans le schéma toto1.

Conception : tables

Récupérez le fichier Script_PlateformeJeux.txt sur la plateforme UMTICE (il est dans le Drive : script.sql).

  1. Complétez le script avec la création des tables jeu, partie et save. Pour cela, basez-vous sur la modélisation donnée (MEA et MR) et sur les informations complémentaires suivantes :
    1. jeu : id_jeu de type serial et clé primaire, nom_jeu de type varchar(20), unique et non nul, type, qui peut prendre uniquement les valeurs « role », « plateau », « tower defense », « MMORPG » ou « Autre », nb_joueur de type integer ;
    2. pas d'informations supplémentaires pour partie ;
    3. save : id_avatar de type bigint, qui fait référence à id_avatar de la table avatar et fait partie de la clé primaire, id_jeu de type bigint, qui fait référence à id_jeu de la table jeu et fait partie de la clé primaire, date_s de type date, qui fait partie de la clé primaire, nb_pv de type integer et fichier de type varchar(50), qui doit être unique et n'admet pas de valeur nulle.
    Attention : pensez également à regarder les enregistrements qui vont être saisis dans ces tables, afin qu'il y ait correspondance entre les valeurs des INSERT et l'ordre des attributs dans la création de chaque table.
  2. Modifiez la table visiteur dans le script afin qu'une vérification mineure soit faite sur le mail : un caractère @ doit être dans la valeur de mail.
  3. Créez une table localisation : id_loc de type serial et clé primaire, nom_loc de type varchar(50) et code_postal de type integer.

Implémentation

  1. Exécutez le script pour générer la base de données.

Normalement, toutes vos tables ont été créées dans le schéma jeu sans que vous ayez spécifié le nom du schéma lors de la création des tables. Vous pouvez le vérifier en listant les tables. Si ce n'est pas le cas, vous avez mal configuré votre search_path…

Après la création de la base

  1. Insérez les tuples suivants dans la table localisation : 13100 Aix en Provence, 72250 Brette les Pins, 09000 Foix, 54000 Nancy, 59640 Dunkerque, 38000 Grenoble et 74000 Annecy.
  2. Modifiez la table visiteur afin que les villes ne soient plus des varchar, mais que cette information soit obtenue grâce à la table localisation. Pour cela, vous devrez créer une clé étrangère dans la table visiteur pointant vers la table localisation. Attention, vous ne devez pas perdre les informations permettant de savoir quel visiteur habite dans quelle ville !
  3. Mettez à jour les données afin de sauvegarder que Ian habite à Aix en Provence et que Sean habite à Brette les Pins.
  4. Renommez le champ nb_joueur de la table jeu en nb_joueur_max.

Vues

  1. Créez une vue v_qui_joue comprenant les champs id_visiteur, login, nom_avatar, nom_race, nom_jeu, highscore.
  2. Créez une vue v_stock comprenant les champs login, nom_objet, nb_dispo, sum_tot, avec sum_tot la valeur totale qu'a dépensée login pour l'achat de l'objet nom_objet. Exemple : Elijah a acheté 10 baguettes magiques à 5 € chacune, et il ne lui en reste actuellement que 3 disponibles. Le n-uplet affiché dans v_stock pour Elijah sur baguette magique est : Elijah, baguette magique, 3, 50.

Chez soi : la console SQL du TP

Le serveur de la fac n'est pas accessible de chez soi. La console ci-dessous exécute le compte rendu entier sur une base PostgreSQL neuve (PGlite), par le serveur local des quiz : studies/lancer.bat, puis cette page ouverte depuis le portail. Sans le serveur, on peut écrire, mais pas exécuter.

  1. La console contient au départ le script fourni. Les réponses aux questions 5 à 8 (schémas, search_path) se placent au-dessus du script, les questions 9 à 11 se font dans le script lui-même, et les suivantes s'écrivent à la suite, dans l'ordre.
  2. Exécuter (ou Ctrl + Entrée) rejoue tout le texte, depuis le début, sur une base neuve : les tables, les modifications et les vues des questions précédentes sont donc là quand arrive la dernière requête.
  3. La console affiche le résultat de la dernière requête qui renvoie des lignes, ou la première erreur. On travaille donc en fin de texte ; pour revoir une requête plus ancienne, on la recopie à la fin.
  4. Le travail s'enregistre tout seul : dans le navigateur, et, avec le serveur, dans le dossier td_results/ de ce cours, dans ton espace. Pour en faire le fichier de compte rendu, le menu ⋯ de la console copie le texte, à coller dans TP1_Monnom.sql.

Attention Ce qui ne se fait qu'à la fac

Les commandes qui commencent par une barre oblique inverse (\l, \dt, \dn, \c) appartiennent au client psql, pas au langage SQL : la console les refuse (syntax error). On les garde en commentaire (-- \dt) dans le compte rendu. De même, on ne peut pas s'y connecter à une autre base (questions 3 et 4). Les requêtes SQL sur les catalogues, elles, fonctionnent.

À retenir

L'essentiel

  • À la fac : psql -h erebor -U num_etu ; base, utilisateur Unix et utilisateur PostgreSQL portent le numéro étudiant.
  • Le compte rendu TP1_Monnom.txt ou .sql garde chaque requête ; il n'est pas à rendre, mais il est autorisé au TP noté.
  • Le script fourni ne s'exécute qu'une fois complété : les tables jeu, partie et save sont à écrire (question 9).
  • Chez soi, la console rejoue tout le compte rendu sur une base neuve et affiche le résultat de la dernière requête ; les commandes psql (\dt…) n'y existent pas.
  • Les dates du script s'écrivent jour/mois/année : la console règle DateStyle comme le serveur de la fac.

Auto-évaluation

Le script fourni, exécuté tel quel, s'arrête sur relation "jeu" does not exist. Pourquoi ?

Il insère des lignes dans jeu, partie et save, mais ne crée pas ces tables : leur création est laissée aux emplacements prévus du script, c'est la question 9.

Pourquoi un PostgreSQL réglé par défaut refuse-t-il la date '24/01/16' ?

Par défaut, DateStyle lit les dates dans l'ordre mois/jour/année, et il n'y a pas de 24e mois. Le serveur de la fac, comme la console, lit jour/mois/année.

Pourquoi \dt provoque-t-il une erreur dans la console, alors qu'il marche à la fac ?

C'est une commande du client psql, qui la traduit en requête sur les catalogues : ce n'est pas du SQL, et la console n'exécute que du SQL.

Comment voir, dans la console, le résultat d'une requête écrite plus haut ?

La console n'affiche que la dernière requête qui renvoie des lignes : on recopie la requête à la fin du texte, ou l'on met en commentaire celles qui la suivent.
