Les séquences diapos 4–5

Définition Séquence

Une séquence (sequence) est un objet de la base qui génère des entiers, les uns après les autres. On s'en sert surtout pour fabriquer des identifiants.

CREATE SEQUENCE nom_seq [ INCREMENT BY increment ]
    [ MINVALUE valeurmin | NO MINVALUE ]
    [ MAXVALUE valeurmax | NO MAXVALUE ]
    [ START [ WITH ] début ]
    [ CACHE cache ]
    [ [ NO ] CYCLE ]
    [ OWNED BY { table.colonne | NONE } ]

On utilise les valeurs de la séquence avec trois fonctions :

  • nextval() : valeur suivante ;
  • currval() : valeur courante ;
  • setval() : initialisation de la valeur courante.

Complément Les options de CREATE SEQUENCE

  • INCREMENT BY : le pas, 1 par défaut ; un pas négatif fait une séquence décroissante.
  • MINVALUE, MAXVALUE : les bornes. Par défaut, de 1 à 263 − 1 pour une séquence croissante.
  • START WITH : la première valeur renvoyée, MINVALUE par défaut.
  • CACHE : nombre de valeurs réservées d'avance en mémoire, pour aller plus vite (1 par défaut).
  • CYCLE : une fois la borne atteinte, la séquence repart de l'autre borne. Avec NO CYCLE (par défaut), nextval() échoue.
  • OWNED BY : rattache la séquence à une colonne ; supprimer la colonne supprime la séquence (voir SERIAL plus bas).

Exemple Une séquence qui part de 3, de 2 en 2 diapo 5

CREATE SEQUENCE mon_num START 3 INCREMENT BY 2;

SELECT nextval('mon_num');
    -- retourne 3

SELECT nextval('mon_num');
    -- retourne 5

INSERT INTO ma_table VALUES (nextval('mon_num'));   -- insère 7

ALTER SEQUENCE mon_num RESTART WITH 3;
    -- réinitialisation à 3 ;

SELECT setval('mon_num', 3, false);
    -- idem

Complément currval, setval et les bornes, en pratique

currval() renvoie la dernière valeur obtenue par nextval() dans la session en cours. Avant le premier nextval(), elle échoue :

SELECT currval('mon_num');
-- ERROR:  currval of sequence "mon_num" is not yet defined in this session

Le troisième argument de setval() indique si la valeur donnée a déjà été utilisée :

SELECT setval('mon_num', 3, false);  SELECT nextval('mon_num');   -- 3 : la valeur donnée sert au prochain appel
SELECT setval('mon_num', 3);         SELECT nextval('mon_num');   -- 5 : true par défaut, on repart de 3 + 2

Enfin, une séquence bornée sans CYCLE s'arrête ; avec CYCLE, elle recommence :

CREATE SEQUENCE petite MAXVALUE 3;
SELECT nextval('petite'), nextval('petite'), nextval('petite');   -- 1 | 2 | 3
SELECT nextval('petite');
-- ERROR:  nextval: reached maximum value of sequence "petite" (3)

CREATE SEQUENCE ronde MAXVALUE 3 CYCLE;
SELECT nextval('ronde'), nextval('ronde'), nextval('ronde'), nextval('ronde');   -- 1 | 2 | 3 | 1

Attention Jamais de SERIAL pour une clé étrangère

Une clé étrangère doit contenir l'identifiant d'une ligne qui existe déjà dans la table référencée. Or une colonne SERIAL invente sa propre valeur à chaque insertion.

Ajout Avec id_s SERIAL REFERENCES t_serial (id), une insertion qui ne précise pas id_s le remplit tout seul avec 1, puis 2, etc. : chaque ligne pointe vers une ligne arbitraire. Une clé étrangère se déclare avec le type entier correspondant : integer pour référencer un serial, bigint pour un bigserial.

SERIAL n'est pas un vrai type : c'est un raccourci pour créer une séquence et l'associer à une colonne.

CREATE TABLE ma_table ( ma_col SERIAL );
CREATE SEQUENCE ma_seq AS integer;
CREATE TABLE ma_table
    ( ma_col integer NOT NULL DEFAULT nextval('ma_seq') );
ALTER SEQUENCE ma_seq OWNED BY ma_table.ma_col;

La dernière ligne crée une dépendance :

  • si ma_col est supprimée, alors ma_seq est aussi supprimée ;
  • mais si ma_seq est supprimée, ma_col subsiste, sans valeur par défaut.

Ajout Précision sur le second point : un simple DROP SEQUENCE est refusé, car la valeur par défaut de la colonne dépend de la séquence. Il faut CASCADE, qui supprime la valeur par défaut et garde la colonne :

DROP SEQUENCE t_serial_id_seq;
-- ERROR:  cannot drop sequence t_serial_id_seq because other objects depend on it
-- DETAIL:  default value for column id of table t_serial depends on sequence t_serial_id_seq
-- HINT:  Use DROP ... CASCADE to drop the dependent objects too.

La séquence créée par SERIAL s'appelle table_colonne_seq ; la fonction pg_get_serial_sequence(table, colonne) renvoie son nom.

Remarque Des « trous » dans les valeurs

Il peut y avoir des trous dans les valeurs : si une transaction ne fonctionne pas, la valeur est perdue.

Ajout nextval() n'est jamais annulé, même par un ROLLBACK. Une insertion refusée consomme donc quand même une valeur :

CREATE TABLE t_serial (id SERIAL PRIMARY KEY, nom varchar(10) NOT NULL);
INSERT INTO t_serial (nom) VALUES ('a');     -- id 1
INSERT INTO t_serial (nom) VALUES ('b');     -- id 2
INSERT INTO t_serial (nom) VALUES (NULL);
-- ERROR:  null value in column "nom" of relation "t_serial" violates not-null constraint
-- DETAIL:  Failing row contains (3, null).  ← la valeur 3 est consommée
INSERT INTO t_serial (nom) VALUES ('c');     -- id 4 : le 3 n'existera jamais

Un identifiant ne sert qu'à identifier : on ne compte pas sur lui pour numéroter sans trou.

Attention Insérer un identifiant à la main Ajout

Donner explicitement une valeur à une colonne SERIAL ne fait pas avancer la séquence. Le conflit apparaît plus tard :

INSERT INTO t_serial (nom) VALUES ('a'), ('b');   -- id 1 et 2, la séquence est à 2
INSERT INTO t_serial VALUES (3, 'c');              -- id donné à la main
INSERT INTO t_serial (nom) VALUES ('d');           -- nextval() renvoie 3…
-- ERROR:  duplicate key value violates unique constraint "t_serial_pkey"
-- DETAIL:  Key (id)=(3) already exists.

-- On recale la séquence sur le plus grand identifiant :
SELECT setval('t_serial_id_seq', (SELECT max(id) FROM t_serial));
INSERT INTO t_serial (nom) VALUES ('d');           -- id 4

Complément Les colonnes IDENTITY Hors programme

La norme SQL propose une syntaxe équivalente, préférée dans les versions récentes de PostgreSQL :

CREATE TABLE t (id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY, nom text);

La séquence est gérée de la même façon, mais une valeur donnée à la main est refusée, ce qui évite le piège ci-dessus.

Les index diapos 9–10

Définition Index

Un index (index) est une structure de données auxiliaire, construite à partir d'une ou plusieurs colonnes d'une table, qui permet au SGBD de retrouver des lignes sans parcourir toute la table. C'est une notion non standard : la norme SQL ne la définit pas, mais tous les SGBD la proposent.

L'intérêt est une recherche plus rapide, nécessaire pour les grandes bases de données. Mais un index a un coût :

Avantage

  • Retrouver une ligne spécifique plus rapidement.

Inconvénient

  • Une surcharge pour le SGBD : la structure de données est mise à jour à chaque modification de la table.

Un index est donc à utiliser à bon escient. PostgreSQL crée automatiquement un index sur chaque clé primaire Ajout et sur chaque contrainte UNIQUE :

SELECT indexname, indexdef FROM pg_indexes WHERE tablename IN ('articles', 'vendeurs');
--  vendeurs_pkey | CREATE UNIQUE INDEX vendeurs_pkey ON public.vendeurs USING btree (id)
--  articles_pkey | CREATE UNIQUE INDEX articles_pkey ON public.articles USING btree (id)

Création, suppression et modification d'un index :

CREATE INDEX nom_index
    ON nom_table [ USING methode ] ( nom_colonne [, ...] )
    [ WHERE expression ];

DROP INDEX nom_index [, ...] [ RESTRICT | CASCADE ];

ALTER INDEX nom_index ...

La clause WHERE crée un index partiel : seules les lignes qui vérifient l'expression sont indexées.

Exemple Index sur la table articles Ajout

CREATE INDEX idx_articles_categorie ON articles (categorie);
-- index partiel : seules les ventes de vêtements
CREATE INDEX idx_vetements_date ON articles (date_vente) WHERE categorie = 'Vêtements';
-- index de hachage : ne sert que pour l'égalité
CREATE INDEX idx_articles_nom_hash ON articles USING hash (nom);

ALTER INDEX idx_articles_categorie RENAME TO idx_cat;
DROP INDEX idx_cat, idx_articles_nom_hash;

Complément Voir si un index sert : EXPLAIN

EXPLAIN affiche le plan choisi par PostgreSQL pour exécuter une requête, sans l'exécuter. Sur une table de 200 000 lignes :

CREATE TABLE grosse AS SELECT n, md5(n::text) AS code FROM generate_series(1, 200000) AS n;

EXPLAIN SELECT * FROM grosse WHERE n = 4242;
--  Seq Scan on grosse  (cost=0.00..4228.00 rows=1 width=37)      ← parcours de toute la table
--    Filter: (n = 4242)

CREATE INDEX idx_grosse_n ON grosse (n);
EXPLAIN SELECT * FROM grosse WHERE n = 4242;
--  Index Scan using idx_grosse_n on grosse  (cost=0.42..8.44 rows=1 width=37)   ← 500 fois moins cher
--    Index Cond: (n = 4242)

EXPLAIN SELECT * FROM grosse WHERE n > 1000;
--  Seq Scan on grosse  (cost=0.00..4228.00 rows=199043 width=37) ← l'index est ignoré

La dernière requête garde presque toutes les lignes : passer par l'index coûterait plus cher que lire la table. Un index sert quand la condition est sélective ; sur une petite table comme articles, PostgreSQL ne l'utilise même pas.

Par exemple, une table de hachage ne sert que pour l'opérateur =. Plus d'informations dans la documentation de PostgreSQL.

Rôles et privilèges diapos 12–23

Une base de données sert à plusieurs personnes, qui n'ont pas toutes besoin des mêmes droits : une comptable doit pouvoir lire les ventes sans pouvoir les modifier. PostgreSQL gère ces droits avec des rôles, auxquels on accorde ou retire des privilèges sur les objets.

Les rôles diapo 12

Définition Rôle

Un rôle (role, mot-clé ROLE, non standard SQL) est une entité qui peut posséder des objets et avoir des droits.

  • Un rôle de la base n'est pas un utilisateur du système d'exploitation.
  • Il est global aux bases de données : un rôle existe pour tout le serveur, pas pour une seule base.
  • Il affecte les droits d'accès sur ses objets pour les autres rôles.

Les rôles sont enregistrés dans le catalogue pg_roles. On les liste par une requête, ou par la méta-commande \du de psql :

SELECT rolname FROM pg_roles;

Ajout Sur un serveur neuf, la requête renvoie postgres et une quinzaine de rôles prédéfinis dont le nom commence par pg_ (pg_read_all_data, pg_monitor…), qui regroupent des droits d'administration.

Utilisateur et super-utilisateur diapo 13

Un « user » est un rôle qui a le droit de connexion. Les droits sont déterminés par le rôle indiqué lors de la connexion :

$ psql -U nom_user

Pendant la session, session_user vaut alors nom_user.

L'utilisateur initial est postgres : c'est le rôle par défaut d'un SGBD PostgreSQL nouvellement installé. Il a les droits d'un super-utilisateur : aucune vérification de droits n'est faite avant l'exécution d'une action.

Rôles et groupes diapo 14

Un rôle peut être à la fois une personne ou un groupe de personnes. L'intérêt d'un groupe est le partage commun de droits : on accorde les droits une fois au groupe, et tous ses membres en profitent.

Il est possible de changer de rôle, si nom_user fait partie du groupe group_user :

SET ROLE to group_user;          -- current_user prend alors la valeur group_user
SELECT current_user, session_user;   -- quel rôle ?
RESET ROLE;                      -- retour au rôle de connexion

Complément session_user ou current_user ?

session_user est le rôle qui s'est connecté ; il ne change pas pendant la session. current_user est le rôle dont les droits sont vérifiés à cet instant ; SET ROLE le modifie. Connecté en postgres :

SET ROLE nora;
SELECT current_user, session_user;
--  current_user | session_user
--  nora         | postgres

La liste de contrôle d'accès diapos 16–17

Définition Liste de contrôle d'accès

La liste de contrôle d'accès (access control list, ACL) indique quels rôles possèdent quels droits sur quels objets. Elle est consultée avant toute action. Pour chaque objet, elle contient un ensemble de privilèges et un ensemble de restrictions.

Les droits sur un objet peuvent être modifiés par le super-utilisateur ou par le propriétaire de l'objet : octroi de privilèges avec GRANT, restriction avec REVOKE.

Complément Lire une ACL

Dans psql, \dp nom_table affiche l'ACL d'une table. Elle est aussi stockée dans le catalogue, sous une forme abrégée :

SELECT relname, relacl FROM pg_class WHERE relname = 'stock';
--  stock | {postgres=arwdDxtm/postgres,lecteur=r/postgres}

Chaque élément se lit bénéficiaire=droits/auteur : lecteur=r/postgres signifie que postgres a accordé à lecteur le droit r. Les lettres : r SELECT, a INSERT, w UPDATE, d DELETE, D TRUNCATE, x REFERENCES, t TRIGGER, m MAINTAIN. Un bénéficiaire vide (=r/…) désigne PUBLIC.

Accorder des privilèges : GRANT diapos 18–20

GRANT privilege [, ...] ON objet [, ...]
    TO { username | GROUP groupname | PUBLIC } [, ...];

Exemples de valeurs pour privilege :

  • SELECT : lecture ;
  • INSERT : insertion de lignes ;
  • UPDATE : modification de colonnes ;
  • DELETE : suppression de lignes ;
  • ALL : tous les privilèges.

Exemples de valeurs pour objet :

  • base de données : ON DATABASE nom_bd ;
  • table : ON [TABLE] nom_table ;
  • schéma : ON SCHEMA nom_schema ;
  • langage : ON LANGUAGE nom_langage ;
  • fonction : ON FUNCTION nom_fonction.

Le bénéficiaire, après TO, est un utilisateur particulier (username), un groupe d'utilisateurs (GROUP groupname) ou tous les utilisateurs (PUBLIC).

Attention Les droits dépendent des objets

Ajout Chaque type d'objet a ses propres privilèges. Accorder SELECT sur une base de données, par exemple, n'a pas de sens.

Exemple Des droits à la colonne près Ajout

Pour UPDATE (et SELECT, INSERT), on peut restreindre le droit à certaines colonnes :

GRANT SELECT ON articles TO compta;
GRANT UPDATE (prix) ON articles TO compta;

SET ROLE compta;
UPDATE articles SET prix = prix WHERE id = 1;    -- UPDATE 1 : autorisé
UPDATE articles SET nom = 'x' WHERE id = 1;
-- ERROR:  permission denied for table articles
SELECT * FROM vendeurs;
-- ERROR:  permission denied for table vendeurs   ← aucun droit par défaut
RESET ROLE;

Retirer des privilèges : REVOKE diapo 21

REVOKE privilege [, ...] ON objet [, ...]
    FROM { username | GROUP groupname | PUBLIC } [, ...];

Remarque

Le fait de supprimer des droits à PUBLIC n'affecte pas ceux à qui l'on a octroyé spécifiquement les droits.

GRANT SELECT ON articles TO PUBLIC;
GRANT SELECT ON articles TO compta;
REVOKE SELECT ON articles FROM PUBLIC;
SET ROLE compta;
SELECT count(*) FROM articles;    -- 12 : compta garde son droit

Accès aux schémas diapo 22

-- Donner les droits d'accès à son schéma
GRANT usage ON schema mon_schema TO nom_utilisateur;

-- Révoquer les droits : interdiction de créer des objets dans le schéma public
REVOKE create ON schema public FROM public;

Attention Droits sur un schéma ≠ droits sur ses objets

L'octroi de droits sur le schéma n'octroie pas de droits sur les objets de ce schéma !

Ajout Il faut les deux : USAGE sur le schéma pour y entrer, et un privilège sur la table pour s'en servir.

CREATE SCHEMA boutique;
CREATE TABLE boutique.stock (id int, qte int);

GRANT USAGE ON SCHEMA boutique TO lecteur;        -- le schéma seul
SET ROLE lecteur; SELECT * FROM boutique.stock;
-- ERROR:  permission denied for table stock

REVOKE USAGE ON SCHEMA boutique FROM lecteur;
GRANT SELECT ON boutique.stock TO lecteur;        -- la table seule
SET ROLE lecteur; SELECT * FROM boutique.stock;
-- ERROR:  permission denied for schema boutique

GRANT USAGE ON SCHEMA boutique TO lecteur;        -- les deux
SET ROLE lecteur; SELECT * FROM boutique.stock;   -- 1 | 10 : enfin

Pour donner un droit sur toutes les tables existantes d'un schéma en une commande :

GRANT SELECT ON ALL TABLES IN SCHEMA boutique TO lecteur;

Ajout Depuis PostgreSQL 15, PUBLIC n'a plus le droit CREATE sur le schéma public : le REVOKE de la diapo n'est plus nécessaire que sur les versions antérieures. Un rôle ordinaire qui tente CREATE TABLE public.essai (x int); obtient permission denied for schema public.

-- Création des rôles
CREATE ROLE group_test;
CREATE ROLE toto;

-- Ajout d'utilisateurs au sein d'un groupe

GRANT SELECT, INSERT ON articles TO group_test;
SET ROLE titi;  SELECT count(*) FROM articles;    -- 12 : titi est membre
SET ROLE toto;  SELECT count(*) FROM articles;    -- toto a été retiré du groupe
-- ERROR:  permission denied for table articles

La base Dingo Fringo diapos 25–29

Dingo Fringo vend des articles (vêtements, chaussures, accessoires) par l'intermédiaire de vendeur·ses. Chaque vendeur·se peut avoir été parrainé·e par un·e autre. Le cours déroule les quatre étapes de la conception :

  1. Diagramme de classes : c'est fait (figure ci-dessous).
  2. Modèle relationnel associé.
  3. Création des tables de la base de données.

Attention NATURAL JOIN joint sur toutes les colonnes de même nom Ajout

Une requête difficile à lire diapos 33–38

Quelles catégories ont un chiffre d'affaires supérieur au chiffre d'affaires moyen par catégorie ? La requête suivante fonctionne :

SELECT categorie, SUM(prix) AS ca_total
FROM articles
GROUP BY categorie
HAVING SUM(prix) > (
    SELECT AVG(ca) FROM (
        SELECT SUM(prix) AS ca
        FROM articles
        GROUP BY categorie
    ) AS sous_requete );

Que fait-elle ? Il faut la lire de l'intérieur vers l'extérieur :

  1. La sous-requête la plus interne calcule le chiffre d'affaires de chaque catégorie : 85,00, 118,00 et 54,00 (3 lignes).
  2. La sous-requête intermédiaire en fait la moyenne : 85,666…, soit environ 85,7.
  3. La requête principale calcule le chiffre d'affaires de chaque catégorie (Chaussures 85,00, Vêtements 118,00, Accessoires 54,00), et HAVING ne garde que les groupes au-dessus de 85,7.
--  categorie | ca_total
-- -----------+----------
--  Vêtements |   118.00

Le résultat est juste : la seule catégorie dont le chiffre d'affaires dépasse le chiffre d'affaires moyen par catégorie est Vêtements. Le problème ? La requête est illisible. Trois niveaux d'imbrication, un calcul (SUM(prix) … GROUP BY categorie) écrit deux fois, et une lecture de l'intérieur vers l'extérieur : difficile à comprendre, et à corriger en cas d'erreur.

Les CTE : WITH diapos 39–40

Définition Expression de table commune

Une expression de table commune (Common Table Expression, CTE) est une requête nommée, définie avant la requête principale, qui se comporte comme une table temporaire, mais n'existe que le temps de l'exécution de la requête : pas de stockage, à la différence d'une vue (VIEW). Mot-clé : WITH.

WITH nom_cte AS (SELECT ...) SELECT ... FROM nom_cte

Une CTE permet de lire les requêtes de haut en bas, plutôt que de l'intérieur vers l'extérieur. Réécriture de la requête précédente :

WITH ca_par_categorie AS (
    SELECT categorie, SUM(prix) AS ca_total FROM articles
    GROUP BY categorie )
SELECT categorie, ca_total
FROM ca_par_categorie
WHERE ca_total > (SELECT AVG(ca_total) FROM ca_par_categorie);
-- Vêtements | 118.00

Ajout On lit d'abord « on calcule le chiffre d'affaires par catégorie », puis « on garde celles au-dessus de la moyenne ». Le calcul n'est écrit qu'une fois, et la CTE est utilisée deux fois. Comme le résultat de la CTE est une table, la condition passe du HAVING au WHERE.

Chaîner des CTE diapo 41

Il est possible de chaîner des CTE les unes à la suite des autres, séparées par des virgules, derrière un seul WITH. Elles agissent alors comme des variables intermédiaires, utilisables dans la suite de la requête ; chacune peut utiliser les précédentes.

WITH etape1 AS (...), etape2 AS (SELECT * FROM etape1 ...) SELECT ...

    SELECT categorie, SUM(prix) AS ca_total

Ajout moyenne_globale ne contient qu'une ligne : le produit cartésien ca_par_categorie c, moyenne_globale m ajoute simplement la moyenne en face de chaque catégorie.

Les CTE récursives diapo 42

Définition CTE récursive

Une CTE récursive (WITH RECURSIVE) permet de parcourir plusieurs fois une table de travail. Elle est formée de deux requêtes reliées par UNION ALL (ou UNION) :

  • le terme ancre initialise la table de travail. Il est exécuté une seule fois et ne référence pas nom_cte ;
  • le terme récursif est répété en boucle. Il référence obligatoirement nom_cte, et la boucle s'arrête quand il renvoie 0 ligne.
WITH RECURSIVE nom_cte (colonne1, colonne2, ...) AS (
    -- terme ancre : initialisation de la table de travail
    SELECT <colonnes>
    FROM <table_source>
    WHERE <condition_de_depart>

    UNION ALL                  -- obligatoire entre les deux termes

    -- terme récursif : répété en boucle
    SELECT <colonnes>
    FROM <table_source> t
    JOIN nom_cte c ON <condition_de_liaison>
    WHERE <condition_d_arret_optionnelle> )
SELECT * FROM nom_cte ORDER BY <colonne>;

Attention Rien à voir avec une fonction récursive

Une CTE récursive n'a rien à voir avec les fonctions récursives en programmation. Ajout Rien ne s'appelle soi-même et il n'y a pas de pile d'appels : c'est une boucle, qui recalcule une table de travail à partir de la précédente tant qu'elle produit des lignes.

Méthode Comment PostgreSQL évalue une CTE récursive diapos 48–51

  1. Exécuter le terme ancre. Son résultat forme la première table de travail, et entre dans le résultat.
  2. Exécuter le terme récursif, où nom_cte désigne la table de travail courante (seulement les lignes produites au tour précédent).
  3. Si ce tour produit des lignes, elles deviennent la nouvelle table de travail et sont ajoutées au résultat (UNION ALL) ; reprendre à l'étape 2.
  4. Si ce tour ne produit aucune ligne, s'arrêter. La CTE vaut l'union de toutes les tables produites.

Exemple Compter de 1 à 5 Ajout

Le plus petit exemple possible, sans table : l'ancre produit 1, chaque tour ajoute 1, et la condition du terme récursif arrête la boucle.

WITH RECURSIVE compteur (n) AS (
    SELECT 1                                  -- ancre
    UNION ALL
    SELECT n + 1 FROM compteur WHERE n < 5    -- terme récursif
)
SELECT n FROM compteur;    -- 1, 2, 3, 4, 5

Au cinquième tour, la table de travail ne contient que 5 : WHERE n < 5 ne laisse rien passer, le tour renvoie 0 ligne et la boucle s'arrête.

Exemple : le réseau de parrainage diapos 43–51

OK, mais à quoi ça sert ? Dans la table vendeurs, chaque vendeur·se a un parrain ou une marraine (association réflexive), et chaque parrain ou marraine peut avoir été parrainé·e par une autre personne : on a donc des filleuls de filleuls. La taille de cet organigramme est inconnue ! Comment retrouver cette hiérarchie à partir des données ?

Une jointure réflexive donne un niveau ; deux jointures, deux niveaux. Mais sans connaître la profondeur, on ne sait pas combien en écrire. La CTE récursive, elle, ajoute un niveau à chaque tour jusqu'à épuisement :

WITH RECURSIVE reseau AS (
    -- table de travail initiale : le sommet de la hiérarchie (pas de parrain)
    SELECT id, nom, id_parrain, 1 AS niveau
    FROM vendeurs
    WHERE id_parrain IS NULL

    UNION ALL

    -- terme récursif : les personnes parrainées par celles du tour précédent
    SELECT v.id, v.nom, v.id_parrain, r.niveau + 1
    FROM vendeurs v
    JOIN reseau r ON v.id_parrain = r.id
)
SELECT * FROM reseau ORDER BY niveau;    -- affichage : tri par niveau hiérarchique

Décomposons les résultats intermédiaires.

  1. Ancre (diapo 48). Le terme ancre (WHERE id_parrain IS NULL) ne renvoie que Julie, car elle n'a pas de parrain : c'est la table de travail initiale, (1, Julie, NULL, 1).
  2. Première itération (diapo 49). Le terme récursif cherche les personnes dont le parrain a l'identifiant de Julie. Comme la table de travail ne contient que Julie, au niveau 1, il s'exécute comme si r.niveau + 1 valait 1 + 1, et renvoie Marc et Sophie, au niveau 2. Puis on fait UNION ALL avec la table de travail pour les mettre dans reseau.
  3. Deuxième itération (diapo 50). La table de travail ne contient plus que les lignes de niveau 2. Le terme récursif calcule cette fois 2 + 1, et renvoie 3 lignes : Karim, Lea et Nadia, au niveau 3.
  4. Troisième itération Ajout. La table de travail contient Karim, Lea et Nadia, qui ne parrainent personne : 0 ligne, fin de la boucle.

À chaque itération, le JOIN garantit de ne voir que les « nouveaux » filleuls : pas de redondance. Au final, reseau contient l'union de la table de travail initiale (l'ancre) et des tables produites par la récursion ; il reste à trier selon le niveau pour obtenir l'organigramme (diapo 51) :

Bilan et pièges diapo 52

Les CTE récursives permettent de parcourir les données itérativement. Elles sont composées de deux parties, un terme « ancre » (initialisation) et un terme récursif. Ce type de requête est très pratique pour parcourir des données structurées en arbre, comme un organigramme.

  • UNION ou UNION ALL ? UNION supprime les doublons, UNION ALL non. Quand on travaille sur des identifiants uniques, il n'y a pas de doublon, et UNION ALL est plus rapide.
  • Condition d'arrêt ? Il n'est pas possible de préciser une condition d'arrêt dans la récursion : la boucle s'arrête seulement quand un tour ne renvoie rien. S'il y a un cycle (A est parrain de B et B est parrain de A), ça tourne à l'infini ! À vous de vérifier les données, ou d'ajouter un WHERE dans le terme récursif pour éviter les cycles.

À vérifier La diapo 42 annote UNION ALL comme « obligatoire entre les deux termes », la diapo 52 laisse le choix entre UNION et UNION ALL. Les deux sont acceptés : ce qui est obligatoire, c'est la présence de l'un des deux.

Complément Se protéger d'un cycle

Avec une table où A et B se parrainent mutuellement, la CTE récursive ne s'arrête jamais. Trois parades, testées sur cette table :

CREATE TABLE boucle (id int PRIMARY KEY, nom text, id_parrain int);
INSERT INTO boucle VALUES (1, 'A', 2), (2, 'B', 1);

-- 1. Limiter la profondeur par un WHERE dans le terme récursif
WITH RECURSIVE r AS (
    SELECT id, nom, id_parrain, 1 AS niveau FROM boucle WHERE id = 1
    UNION ALL
    SELECT b.id, b.nom, b.id_parrain, r.niveau + 1
    FROM boucle b JOIN r ON b.id_parrain = r.id
    WHERE r.niveau < 6 )
SELECT * FROM r;    -- A, B, A, B, A, B (niveaux 1 à 6), puis arrêt

-- 2. UNION : une ligne déjà produite est éliminée, le tour suivant est vide
WITH RECURSIVE r AS (
    SELECT id, nom, id_parrain FROM boucle WHERE id = 1
    UNION
    SELECT b.id, b.nom, b.id_parrain FROM boucle b JOIN r ON b.id_parrain = r.id )
SELECT * FROM r;    -- A, B

La parade 2 ne marche que si les lignes se répètent à l'identique : avec une colonne niveau, qui change à chaque tour, UNION ne voit jamais de doublon. Hors programme Depuis la version 14, PostgreSQL propose une clause dédiée : ) CYCLE id SET est_cycle USING chemin, placée après la parenthèse de la CTE, arrête la branche dès qu'un id revient.

Les fonctions de fenêtrage diapos 53–69

La clause GROUP BY agrège les lignes qui ont la même valeur d'attribut sur une colonne. Son problème principal : on perd des informations, puisque le résultat contient moins de lignes. Heureusement, il existe les fonctions de fenêtrage (window functions).

La limite de GROUP BY diapos 53–54

Revenons à Dingo Fringo : on veut connaître le prix moyen de chaque catégorie d'article.

SELECT categorie, AVG(prix) AS prix_moyen

-- -------------+---------------------

--  Vêtements   | 23.6000000000000000
--  Accessoires | 13.5000000000000000

Impossible, avec GROUP BY, d'avoir cette information en face de chaque article vendu : il ne reste qu'une ligne par catégorie.

Définition Fonction de fenêtrage

Une fonction de fenêtrage (window function, fonction() OVER (…)) applique une fonction sur une fenêtre, c'est-à-dire un ensemble de lignes liées à la ligne courante. C'est une alternative à GROUP BY qui évite de perdre des lignes : chaque ligne reste dans le résultat, avec la valeur calculée sur sa fenêtre.

SELECT att1, att2,
    function_name() OVER (
        [PARTITION BY partition_expression]
        [ORDER BY sort_expression [ASC | DESC] [NULLS {FIRST | LAST}]]
        [frame_clause]
    );
  • PARTITION BY découpe les lignes en partitions, comme GROUP BY découpe en groupes ; sans elle, la fenêtre est tout le résultat.
  • ORDER BY ordonne les lignes à l'intérieur de chaque partition (voir la section 4.3).
  • frame_clause, le cadre, précise quelles lignes de la partition entrent dans le calcul (même section).

Attention Une fonction de fenêtrage s'exécute toujours après le WHERE

Le WHERE a déjà filtré les lignes quand la fonction de fenêtrage est calculée. Conséquence : on ne peut pas filtrer sur son résultat dans le même WHERE (section 4.5).

Règle ORDER BY dans OVER diapo 60

  • Dans une requête classique, ORDER BY modifie uniquement l'affichage, sans impact sur les valeurs retournées.
  • Dans la clause OVER, ORDER BY agit différemment : il modifie la fenêtre de calcul de la fonction, qui est calculée de la première ligne de la partition jusqu'à la ligne courante. Cela permet notamment de faire des sommes cumulées d'un attribut.
  • Sans ORDER BY, le calcul s'applique à toute la partition.

Complément Le cadre, et le piège des ex-aequo

« De la première ligne jusqu'à la ligne courante » est le cadre par défaut, la frame_clause de la syntaxe :

RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW

Avec RANGE, les lignes qui ont la même valeur de tri que la ligne courante (ses ex-aequo) entrent toutes dans le calcul. Avec ROWS, on compte ligne par ligne :

ROW_NUMBER, RANK et DENSE_RANK diapos 61–62

Trois fonctions très utiles avec le fenêtrage :

  • ROW_NUMBER() assigne un numéro à chaque ligne d'une partition, selon le tri choisi ;

SELECT nom, categorie, prix,

Top-N par groupe diapos 63–65

Utilisation courante : on veut savoir quels sont les 2 articles vendus les plus chers dans chaque catégorie (pour faire un max de thunes). On procède en deux étapes.

Étape 1 : calculer le rang de chaque article dans sa catégorie à l'aide d'une fonction de fenêtrage.

SELECT nom, categorie, prix,
    RANK() OVER (PARTITION BY categorie ORDER BY prix DESC) AS rang
FROM articles;
-- Accessoires : Sac à main vintage 1, Chapeau feutre 2, Ceinture cuir 3, Écharpe laine 3
-- Chaussures  : Bottines cuir 1, Baskets Adidas 2, Sandales été 3
-- Vêtements   : Manteau laine 1, Jean Levis 2, Pull col roulé 3, Robe fleurie 3, T-shirt Nike 5

Étape 2 : intégrer ce résultat dans une requête qui ne retourne que le top 2. Premier essai :

SELECT nom, categorie, prix,
    RANK() OVER (PARTITION BY categorie ORDER BY prix DESC) AS rang
FROM articles
WHERE rang >= 2;
-- ERROR:  column "rang" does not exist

La fonction de fenêtrage s'applique après le WHERE : au moment du filtrage, la colonne rang n'existe pas encore.

À vérifier La diapo 64 écrit rang >= 2 ; pour garder le top 2, la condition voulue est rang <= 2, comme sur la diapo 65. L'erreur est la même dans les deux cas.

Complément Et sans l'alias ?

Écrire l'expression entière dans le WHERE ne marche pas davantage : PostgreSQL l'interdit explicitement.

SELECT nom, categorie, prix FROM articles
WHERE RANK() OVER (PARTITION BY categorie ORDER BY prix DESC) <= 2;
-- ERROR:  window functions are not allowed in WHERE

C'est la même règle que pour les agrégats, qui ne peuvent pas figurer dans un WHERE (d'où le HAVING). Mais il n'existe pas de « HAVING des fonctions de fenêtrage » : il faut une requête englobante.

Étape 2, et les CTE alors ? On calcule le rang dans une CTE, puis on filtre sur son résultat, qui est une table comme une autre :

WITH classement AS (
    SELECT nom, categorie, prix,
    RANK() OVER (
        PARTITION BY categorie
        ORDER BY prix DESC) AS rang
    FROM articles )
SELECT * FROM classement WHERE rang <= 2;

Attention RANK ou ROW_NUMBER pour un top-N ? Ajout

Avec RANK, les ex-aequo sont gardés ensemble : un « top 1 » peut renvoyer plusieurs lignes. Pour l'article le moins cher de chaque catégorie, RANK() … ORDER BY prix donne le rang 1 à l'Écharpe laine et à la Ceinture cuir (9,00 toutes les deux), alors que ROW_NUMBER() numérote 1 et 2, et n'en garde qu'une, choisie arbitrairement. On prend ROW_NUMBER pour exactement N lignes, RANK ou DENSE_RANK pour ne pas écarter un ex-aequo.

LAG et LEAD diapos 66–68

LAG() et LEAD() donnent accès à la donnée précédente (lag) ou suivante (lead) dans une partition. Elles permettent de comparer des valeurs dans un voisinage proche.

Exemple : quelle est l'évolution mensuelle du chiffre d'affaires de Dingo Fringo pour une catégorie ? Le chiffre d'affaires par mois pour la catégorie Vêtements s'obtient par regroupement :

SELECT DATE_TRUNC('month', date_vente) AS mois, SUM(prix) AS ca
FROM articles
WHERE categorie = 'Vêtements'
GROUP BY DATE_TRUNC('month', date_vente);
-- 2024-01-01 00:00:00+01 | 43.00
-- 2024-02-01 00:00:00+01 | 57.00
-- 2024-03-01 00:00:00+01 | 18.00

Comment exploiter ce résultat pour comparer chaque mois au précédent ? Les ingrédients : une CTE (continuité pédagogique !) et une fonction de fenêtrage.

WITH ca_mensuel AS (
    SELECT DATE_TRUNC('month', date_vente) AS mois, SUM(prix) AS ca
    FROM articles
    WHERE categorie = 'Vêtements'
    GROUP BY DATE_TRUNC('month', date_vente) )
SELECT mois, ca, LAG(ca) OVER (ORDER BY mois) AS ca_mois_precedent,
    ca - LAG(ca) OVER (ORDER BY mois) AS evolution
FROM ca_mensuel;

Il est où, le PARTITION BY ? Ajout Il n'est pas nécessaire ici : la CTE ne garde qu'une catégorie, donc tout son résultat forme une seule partition. Sans PARTITION BY, la fenêtre est l'ensemble des lignes, ordonnées par ORDER BY mois.

Complément Toutes les catégories à la fois

    LAG(ca)  OVER (PARTITION BY categorie ORDER BY mois) AS ca_precedent,
    LEAD(ca) OVER (PARTITION BY categorie ORDER BY mois) AS ca_suivant
FROM ca_mensuel

Bilan : CTE et fenêtrage diapo 69

  • Les CTE (WITH … AS ( )) permettent de créer une table temporaire sur laquelle on applique une requête. Elles évitent les sous-requêtes imbriquées, et facilitent la lecture, donc le débogage.
  • Les CTE récursives (WITH RECURSIVE … AS ( )) sont un cas particulier de CTE qui permet de parcourir une table itérativement. Elles se composent toujours d'une table ancre (initialisation), de UNION [ALL] et d'une requête récursive. On les utilise principalement pour retrouver des structures hiérarchiques dans les données, comme un organigramme.
  • Les fonctions de fenêtrage (func() OVER (…)) appliquent une fonction sur une fenêtre. C'est une alternative à GROUP BY qui évite de perdre des lignes, très pratique pour analyser un top-N par catégorie (RANK) ou une évolution entre groupes (LAG, LEAD). Elles se combinent aisément avec les CTE, puisqu'on ne peut pas tester directement le résultat de la fonction dans la requête.

Q2 Le parrain d'origine

En utilisant la table vendeurs (colonne id_parrain), écrivez une CTE récursive qui affiche, pour chaque vendeur, son nom et le nom de son parrain d'origine (le vendeur historique tout en haut de la chaîne, celui dont id_parrain IS NULL).

Indice

L'ancre sélectionne la racine et mémorise son nom dans une colonne ; le terme récursif recopie cette colonne sans la modifier.

Correction 
WITH RECURSIVE reseau AS (
    SELECT id, nom, nom AS vendeur_racine      -- la racine est sa propre racine
    FROM vendeurs
    WHERE id_parrain IS NULL

    UNION ALL

    SELECT v.id, v.nom, r.vendeur_racine       -- jamais mis à jour : on le recopie
    FROM vendeurs v
    JOIN reseau r ON v.id_parrain = r.id
)
SELECT nom, vendeur_racine FROM reseau;

La colonne vendeur_racine reçoit une valeur dans l'ancre, puis n'est jamais mise à jour : chaque filleul hérite de celle de son parrain, donc de la racine. Ici, tout le réseau descend de Julie.

Le langage PL/pgSQL diapos 76–87

Jusqu'ici, chaque requête SQL est une instruction isolée : elle décrit un résultat, pas une suite d'étapes. Un langage procédural ajoute à SQL des variables, des conditions et des boucles, exécutées directement dans le serveur. Cette partie s'appuie aussi sur le supplément de cours PL/pgSQL, noté « supplément » dans les références.

Pourquoi un langage procédural ? diapos 77–79

Un langage procédural dans un SGBD comprend les commandes du DML : l'interrogation avec SELECT, la manipulation avec INSERT, UPDATE et DELETE. On évite en revanche d'y mettre des commandes DDL. S'y ajoute la partie procédurale : boucles, conditions, variables, affectation…

Ses avantages :

  • il permet de spécifier une suite d'étapes, donc de créer des blocs d'instructions ;
  • dans une architecture client/serveur, il améliore la qualité de l'application : le traitement est centralisé au niveau du serveur, ce qui réduit le nombre d'allers-retours, et seuls les résultats nécessaires sont renvoyés.

Ajout Par exemple, pour calculer le chiffre d'affaires de chaque vendeur, une application sans fonction envoie une requête pour obtenir la liste des vendeurs, puis une requête par vendeur. Avec une fonction stockée dans le serveur, un seul appel suffit (section 6.3).

La structure en blocs diapos 80–81

Le code PL/pgSQL est organisé en blocs. Un bloc compte quatre parties :

  • DECLARE : partie déclarative (facultative) ;
  • BEGIN : corps principal (obligatoire) ;
  • EXCEPTION : traitement des « erreurs » (facultatif) ;
  • END; : fin de bloc (obligatoire).

Toute instruction se termine par un ;. Les blocs peuvent être nommés par une étiquette, <<label>>, et imbriqués : un bloc peut figurer parmi les instructions d'un autre.

[<<label>>]
[DECLARE
    déclarations]
BEGIN
    instructions            -- peuvent contenir un sous-bloc complet
[EXCEPTION
    traitements]
END [label];

Complément Tester un bloc sans créer de fonction : DO

La commande DO exécute un bloc anonyme, une seule fois. C'est pratique pour essayer du PL/pgSQL. L'exemple montre aussi à quoi servent les étiquettes : dans le sous-bloc, x désigne la variable locale, qui masque celle du bloc englobant ; externe.x désigne cette dernière.

DO $$
<<externe>>
DECLARE
    x integer := 1;
BEGIN
    DECLARE
        x integer := 2;
    BEGIN
        RAISE NOTICE 'x interne = %, x externe = %', x, externe.x;
    END;
    RAISE NOTICE 'après le sous-bloc : x = %', x;
END externe $$;
-- NOTICE:  x interne = 2, x externe = 1
-- NOTICE:  après le sous-bloc : x = 1

Attention : le BEGIN d'un bloc PL/pgSQL n'a rien à voir avec le BEGIN qui ouvre une transaction en SQL.

Écrire une fonction PL/pgSQL diapos 82–84

Les blocs se placent dans une fonction, créée avec CREATE [OR REPLACE] FUNCTION, comme les fonctions SQL du cours 2. Cette commande crée et nomme la fonction, définit ses paramètres d'entrée et son type de retour. Le corps est encadré par le délimiteur $$, qui marque le début et la fin de la définition, et la commande se termine par LANGUAGE plpgsql;.

CREATE OR REPLACE FUNCTION nom_fonction (paramètres)
RETURNS type AS $$
    DECLARE
      -- déclarations
    BEGIN
      -- sous-bloc
      DECLARE
          -- déclarations
      BEGIN
          -- corps
      END; -- fin du sous-bloc
    END; -- fin du bloc principal
$$ LANGUAGE plpgsql;

On retrouve les éléments de base : une variable déclarée dans DECLARE (nom type [:= valeur_initiale];), l'affectation avec :=, et RETURN pour renvoyer le résultat.

Ranger le résultat d'une requête dans une variable : INTO supplément § 2.3

La commande SELECT … INTO attribue le résultat d'une requête à une ou plusieurs variables. C'est ainsi qu'une fonction utilise les données de la base :

CREATE FUNCTION f_ca_vendeur (p_id integer) RETURNS numeric AS $$
DECLARE
    total numeric;
BEGIN
    SELECT SUM(prix) INTO total FROM articles WHERE id_vendeur = p_id;
    RETURN total;
END;
$$ LANGUAGE plpgsql;

SELECT nom, f_ca_vendeur(id) AS ca FROM vendeurs;
-- Julie 69.00 ; Marc 58.00 ; Sophie 60.00 ; Karim 34.00 ; Lea 27.00 ; Nadia 9.00

Attention Un SELECT sans destination Ajout

Dans une fonction PL/pgSQL, un SELECT doit ranger son résultat quelque part. Sinon, l'erreur n'apparaît qu'à l'appel :

CREATE FUNCTION f_sans_into () RETURNS integer AS $$
BEGIN
    SELECT count(*) FROM articles;
    RETURN 0;
END;
$$ LANGUAGE plpgsql;

SELECT f_sans_into();
-- ERROR:  query has no destination for result data
-- HINT:  If you want to discard the results of a SELECT, use PERFORM instead.

PERFORM et la variable FOUND diapo 85, supplément § 3

SELECT ma_fonction() ou PERFORM ma_fonction() ? Dans du PL/pgSQL :

  • on utilise PERFORM quand on souhaite exécuter une requête sans récupérer le résultat, par exemple pour appeler une fonction qui effectue des modifications dans la base (un UPDATE, un INSERT, un DELETE…) ;
  • on l'utilise aussi pour tester le succès d'une requête, en combinaison avec la variable FOUND ;
  • on ne l'utilise pas quand on veut récupérer le résultat. Comment le récupérer, alors ? Avec SELECT … INTO (section 6.3).

Définition FOUND supplément § 3

FOUND est une variable spéciale, fournie automatiquement par PL/pgSQL. Elle contient un booléen qui indique si la dernière instruction SQL exécutée dans le bloc a affecté au moins une ligne : TRUE si la dernière commande a retourné ou modifié une ou plusieurs lignes, FALSE sinon. On la teste souvent après un SELECT INTO, un UPDATE, un DELETE, un INSERT ou un PERFORM, pour décider de la suite du traitement.

Les deux exemples du supplément, appliqués à la base Dingo Fringo :

-- FOUND après un UPDATE
DO $$
BEGIN
    UPDATE articles SET prix = prix WHERE id = 99;
    IF NOT FOUND THEN
        RAISE NOTICE 'Aucune ligne modifiee.';
    END IF;
END $$;
-- NOTICE:  Aucune ligne modifiee.

-- FOUND après un PERFORM : la requête est exécutée sans stocker de valeur
CREATE FUNCTION verifie_presence (id_recherche INTEGER) RETURNS BOOLEAN AS $$
BEGIN
    PERFORM * FROM articles WHERE id = id_recherche;
    -- FOUND indique si la requête précédente a affecté au moins une ligne
    IF FOUND THEN
        RETURN TRUE;
    ELSE
        RETURN FALSE;
    END IF;
END;
$$ LANGUAGE plpgsql;

SELECT verifie_presence(3), verifie_presence(42);   -- t | f

Remarque PERFORM n'existe qu'en PL/pgSQL Ajout

Soit une fonction qui ne renvoie rien (type void) et applique une remise à une catégorie :

CREATE FUNCTION f_solde (p_cat varchar, p_taux numeric) RETURNS void AS $$
BEGIN
    UPDATE articles SET prix = prix * (1 - p_taux) WHERE categorie = p_cat;
    IF NOT FOUND THEN
        RAISE NOTICE 'Aucun article dans la catégorie %', p_cat;
    END IF;
END;
$$ LANGUAGE plpgsql;

SELECT f_solde('Bijoux', 0.1);      -- dans psql : NOTICE, puis une cellule vide
PERFORM f_solde('Bijoux', 0.1);     -- dans psql :
-- ERROR:  syntax error at or near "PERFORM"
DO $$ BEGIN PERFORM f_solde('Accessoires', 0.5); END $$;   -- dans un bloc : correct

Dans psql, on appelle toujours une fonction avec SELECT, même si elle ne renvoie rien. PERFORM ne s'écrit qu'à l'intérieur d'un bloc, dans une fonction ou un DO.

Attention Colonnes de sortie et colonnes de table homonymes Ajout

Les colonnes déclarées dans RETURNS TABLE (ou les paramètres OUT) deviennent des variables de la fonction. Si une table a une colonne du même nom, la requête devient ambiguë. Sans l'alias a., la fonction ci-dessus échoue à l'appel :

-- corps : RETURN QUERY SELECT categorie, count(*), SUM(prix) FROM articles GROUP BY categorie;
SELECT * FROM f_stats();
-- ERROR:  column reference "categorie" is ambiguous
-- DETAIL:  It could refer to either a PL/pgSQL variable or a table column.

On préfixe les colonnes par un alias de table, ou l'on donne aux colonnes de sortie des noms différents.

Exemple RETURN NEXT : construire le résultat ligne à ligne Ajout

Avec RETURN NEXT, on remplit les colonnes de sortie, puis on ajoute la ligne au résultat ; la fonction continue ensuite.

CREATE FUNCTION f_prix_ttc () RETURNS TABLE (article varchar, ttc numeric) AS $$
DECLARE
    r record;
BEGIN
    FOR r IN SELECT nom, prix FROM articles WHERE categorie = 'Accessoires' LOOP
        article := r.nom;
        ttc := ROUND(r.prix * 1.2, 2);
        RETURN NEXT;              -- ajoute (article, ttc) au résultat
    END LOOP;
END;
$$ LANGUAGE plpgsql;

-- Sac à main vintage 26.40 ; Écharpe laine 10.80 ; Ceinture cuir 10.80 ; Chapeau feutre 16.80

Commentaires et messages diapo 87

On commente une ligne par --, plusieurs lignes par /* bloc commenté */. Le mot-clé RAISE envoie des messages, avec différents niveaux : DEBUG, LOG, INFO, NOTICE, WARNING, EXCEPTION. Chaque % du message est remplacé par la valeur de la variable correspondante :

RAISE NOTICE 'Hello world to %', var_prenom;

Complément Ce que l'on voit selon le niveau

DO $$
DECLARE var_prenom text := 'Julie';
BEGIN
    RAISE DEBUG 'debug';
    RAISE LOG 'log';
    RAISE INFO 'info';
    RAISE NOTICE 'Hello world to %', var_prenom;
    RAISE WARNING 'warning';
    RAISE EXCEPTION 'Arrêt : % n''a pas le droit', var_prenom;

-- NOTICE:  Hello world to Julie
-- WARNING:  warning
-- ERROR:  Arrêt : Julie n'a pas le droit

Par défaut, DEBUG et LOG ne sont pas envoyés au client : LOG va dans le journal du serveur. RAISE EXCEPTION est différent des autres niveaux : il lève une erreur, qui arrête l'exécution et annule ce que l'instruction en cours avait modifié. C'est ainsi qu'un trigger refuse une opération (section 7).

Gérer les erreurs : EXCEPTION supplément § 4

PL/pgSQL gère les erreurs grâce à la partie EXCEPTION d'un bloc. Lorsqu'une erreur survient dans la partie principale, l'exécution bascule vers le bloc EXCEPTION, qui peut intercepter plusieurs types d'erreurs. Ces types sont des noms prédéfinis, comme division_by_zero ou unique_violation, ou others pour capter toutes les erreurs non gérées spécifiquement.

BEGIN
    instruction;
EXCEPTION
    WHEN type_erreur THEN
        action;
END;
DO $$
DECLARE resultat numeric; valeur integer := 0;
BEGIN
    resultat := 10 / valeur;
EXCEPTION
    WHEN division_by_zero THEN
        RAISE NOTICE 'Division par zero detectee.';
        resultat := NULL;
END $$;
-- NOTICE:  Division par zero detectee.

Le bloc EXCEPTION s'utilise aussi dans les fonctions, les procédures (non vues en cours) ou les triggers. Une erreur capturée peut être traitée sur place, ou relancée explicitement avec RAISE.

Exemple Ajouter un vendeur sans planter Ajout

CREATE FUNCTION f_ajouter_vendeur (p_id integer, p_nom varchar) RETURNS text AS $$
BEGIN
    INSERT INTO vendeurs (id, nom) VALUES (p_id, p_nom);
    RETURN 'ajouté';
EXCEPTION
    WHEN unique_violation THEN
        RETURN 'id ' || p_id || ' déjà utilisé';
    WHEN others THEN
        RETURN 'erreur : ' || SQLERRM;      -- SQLERRM : le message de l'erreur
END;
$$ LANGUAGE plpgsql;

-- ajouté | id 1 déjà utilisé | erreur : value too long for type character varying(50)

Quand une erreur est capturée, les modifications faites par le bloc sont annulées, mais la fonction continue et renvoie son message au lieu d'échouer.

Exercice 7 Bilan des vendeurs

Écrire une fonction f_bilan_vendeurs() qui renvoie, pour chaque vendeur, son nom, son chiffre d'affaires (0 s'il n'a rien vendu) et un statut : « objectif atteint » à partir de 50 €, « à relancer » sinon. Utiliser une boucle FOR, un IF et RETURN NEXT.

Solution proposée 
CREATE FUNCTION f_bilan_vendeurs () RETURNS TABLE (vendeur varchar, ca numeric, statut text) AS $$
DECLARE
    r record;
BEGIN
    FOR r IN SELECT v.nom, COALESCE(SUM(a.prix), 0) AS total
             FROM vendeurs v LEFT JOIN articles a ON a.id_vendeur = v.id
             GROUP BY v.id, v.nom ORDER BY v.id LOOP

        IF r.total >= 50 THEN
            statut := 'objectif atteint';
        ELSE
            statut := 'à relancer';
        END IF;
        RETURN NEXT;
    END LOOP;
END;
$$ LANGUAGE plpgsql;

-- Karim 34.00 à relancer ; Lea 27.00 à relancer ; Nadia 9.00 à relancer

Cette fonction doit renvoyer 0 pour une catégorie inconnue. Pourtant, f_ca_categorie('Bijoux') renvoie NULL. Pourquoi ? Corriger la fonction.

CREATE FUNCTION f_ca_categorie (p_cat varchar) RETURNS numeric AS $$

Solution proposée

Une requête d'agrégation sans GROUP BY renvoie toujours une ligne, même si aucune ligne ne vérifie le WHERE : elle contient NULL. FOUND vaut donc TRUE, et la fonction renvoie total, c'est-à-dire NULL. On traite le cas dans la requête :

Les triggers diapos 88–95

Une fonction s'exécute quand on l'appelle. Certaines règles doivent pourtant s'appliquer à chaque modification d'une table, quelle que soit l'application qui la fait : refuser un salaire négatif, garder un historique. Un trigger appelle une fonction automatiquement, au moment d'une opération sur la table.

Principe diapo 88

Définition Trigger

Un trigger (trigger, déclencheur) est un objet déclenché lors d'une opération particulière de manipulation sur une table (INSERT, UPDATE, DELETE). Il est associé à une fonction trigger, qu'il appelle à chaque déclenchement.

Il existe deux types de triggers :

  • le trigger par ligne (ROW), appelé pour chaque ligne affectée par l'opération ;
  • le trigger par instruction (STATEMENT), appelé une seule fois pour l'ensemble des lignes.

Dans les deux cas, il s'exécute avant ou après l'opération (BEFORE / AFTER).

Créer et supprimer un trigger diapo 89

On définit d'abord la fonction trigger, puis le trigger qui l'appelle :

-- Définition de la fonction trigger
CREATE [ OR REPLACE ] FUNCTION nom_fonction ( )
RETURNS TRIGGER AS $$
    ...
$$ LANGUAGE plpgsql;

-- Définition d'un trigger
CREATE TRIGGER nom_trigger { BEFORE | AFTER } { opération }
    ON nom_table [ FOR [ EACH ] { ROW | STATEMENT } ]
    EXECUTE PROCEDURE nom_fonction ( );

-- Destruction d'un trigger
DROP TRIGGER nom_trigger ON nom_table;

Complément Précisions sur CREATE TRIGGER

  • L'opération est INSERT, UPDATE, UPDATE OF colonne (seulement si cette colonne est modifiée), DELETE ou TRUNCATE ; on les combine avec OR : BEFORE INSERT OR UPDATE.
  • Sans FOR EACH, le trigger est par instruction.
  • Depuis PostgreSQL 11, on écrit plutôt EXECUTE FUNCTION ; EXECUTE PROCEDURE reste accepté et fait exactement la même chose.
  • DROP TRIGGER supprime le trigger, pas sa fonction, qui reste disponible pour un autre trigger.

La fonction trigger diapos 90–91

Une fonction trigger n'accepte aucun argument, et son type de retour est obligatoirement trigger : elle renvoie NULL ou une ligne (record). L'effet de cette valeur de retour dépend du type de trigger :

Complément Annuler en silence, ou modifier la ligne

Renvoyer NULL dans un trigger BEFORE par ligne ignore la ligne sans erreur : les autres lignes de la même instruction sont traitées normalement. À l'inverse, modifier NEW avant de le renvoyer change ce qui sera écrit.

CREATE TABLE t (x int);
CREATE FUNCTION f_filtre() RETURNS trigger AS $$
BEGIN
    IF NEW.x < 0 THEN
        RETURN NULL;          -- ligne ignorée, sans erreur
    END IF;
    NEW.x := NEW.x * 10;      -- on modifie la ligne avant écriture
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
CREATE TRIGGER tr_filtre BEFORE INSERT ON t FOR EACH ROW EXECUTE FUNCTION f_filtre();

INSERT INTO t VALUES (1), (-2), (3);   -- INSERT 0 2 : deux lignes insérées sur trois
SELECT * FROM t;                       -- 10, 30

Pour un DELETE, la ligne à renvoyer est OLD, car NEW vaut NULL. Un trigger BEFORE DELETE qui renvoie NEW annule donc toutes les suppressions, sans le moindre message.

Une même fonction, attachée à deux triggers AFTER sur la table t (qui contient 10 et 30) : l'un par ligne, l'autre par instruction.

CREATE FUNCTION f_trace() RETURNS trigger AS $$

CREATE TRIGGER tr_ligne AFTER INSERT OR UPDATE OR DELETE ON t
    FOR EACH ROW EXECUTE FUNCTION f_trace();
CREATE TRIGGER tr_instr AFTER INSERT OR UPDATE OR DELETE ON t
    FOR EACH STATEMENT EXECUTE FUNCTION f_trace();

UPDATE t SET x = x + 1;
-- NOTICE:  tr_ligne : AFTER ROW UPDATE sur t
-- NOTICE:     OLD = (10), NEW = (11)
-- NOTICE:  tr_ligne : AFTER ROW UPDATE sur t
-- NOTICE:     OLD = (30), NEW = (31)
-- NOTICE:  tr_instr : AFTER STATEMENT UPDATE sur t

Exemple : contrôler les employés diapos 92–93

Cas simple : « je ne veux pas que des employés aient un nom NULL ou un salaire négatif ». Oui, on pourrait gérer ce cas par des contraintes lors de la création de la table… c'est un premier cas simple ! On procède en deux temps :

  1. Créer la fonction qui vérifie les valeurs du nom et du salaire.
  2. Créer l'objet trigger qui appelle la fonction trigger à chaque insertion ou modification de données dans la table emp. Opération : UPDATE ou INSERT. Quand ? Avant la réalisation de l'opération. Combien de fois ? Autant que d'enregistrements insérés ou modifiés : un trigger par ligne.
-- table minimale pour l'exemple
CREATE TABLE emp (ename varchar(10), sal numeric(7,2));

CREATE FUNCTION emp_stamp() RETURNS trigger AS $$
    BEGIN
        -- Verifie que ename et sal sont donnés
        IF NEW.ename IS NULL THEN
            RAISE EXCEPTION 'ename ne peut pas être NULL';
        END IF;
        IF NEW.sal IS NULL OR NEW.sal < 0 THEN
            RAISE EXCEPTION '% doit avoir un salaire positif', NEW.ename;
        END IF;
        RETURN NEW;
    END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER emp_stamp BEFORE INSERT OR UPDATE ON emp
    FOR EACH ROW EXECUTE PROCEDURE emp_stamp();

À vérifier La diapo 93 affiche la condition IF NEW.sal OR NEW.sal<0 IS NULL THEN, corrigée à la main par une flèche qui ramène IS NULL après le premier NEW.sal. C'est la version corrigée, NEW.sal IS NULL OR NEW.sal < 0, qui est reprise ici ; la version imprimée provoque une erreur de type. La diapo ne montre pas la table : la table emp (ename, sal) ci-dessus est ajoutée pour pouvoir tester.

Complément La même règle par contraintes

L'équivalent déclaratif demande NOT NULL sur les deux colonnes : une contrainte CHECK (sal >= 0) seule laisse passer un salaire NULL, car la condition vaut alors « inconnu », et un CHECK ne rejette que ce qui est faux.

CREATE TABLE emp2 (ename varchar(10) NOT NULL, sal numeric(7,2) CHECK (sal >= 0));
INSERT INTO emp2 VALUES ('WARD', NULL);     -- accepté !
INSERT INTO emp2 VALUES ('X', -1);
-- ERROR:  new row for relation "emp2" violates check constraint "emp2_sal_check"

Les contraintes sont plus simples et plus rapides : on les préfère quand elles suffisent. Le trigger se justifie pour des règles qu'une contrainte ne sait pas exprimer (consulter d'autres tables, modifier la ligne, écrire ailleurs), ou pour un message d'erreur sur mesure.

Tester un trigger diapo 94

Comment savoir que ça fonctionne ? Ce n'est pas parce que CREATE FUNCTION et CREATE TRIGGER réussissent que le trigger se comporte comme souhaité ! Le trigger n'est déclenché que par une opération sur sa table. Pour le tester, il faut donc :

  1. Faire un INSERT ou un UPDATE sur la table cible.
  2. Tester des enregistrements qui déclenchent les différents traitements : un cas valide, et un cas par branche du IF.
  3. Supprimer ou réinitialiser ces enregistrements de test.
INSERT INTO emp VALUES ('ALLEN', 1600);                -- cas valide : INSERT 0 1
INSERT INTO emp VALUES (NULL, 1000);
-- ERROR:  ename ne peut pas être NULL
INSERT INTO emp VALUES ('WARD', NULL);
-- ERROR:  WARD doit avoir un salaire positif
UPDATE emp SET sal = -10 WHERE ename = 'ALLEN';         -- le trigger surveille aussi UPDATE
-- ERROR:  ALLEN doit avoir un salaire positif
INSERT INTO emp VALUES ('A', 1), ('B', -1), ('C', 3);
-- ERROR:  B doit avoir un salaire positif
SELECT * FROM emp;                                      -- ALLEN | 1600.00 seulement
DELETE FROM emp WHERE ename = 'ALLEN';                  -- nettoyage

Ajout Le dernier INSERT est instructif : une exception sur la ligne B annule toute l'instruction, A et C compris.

À vérifier La diapo 94 écrit : « Le trigger sera déclenché à chaque appel de fonction ». C'est l'inverse : chaque opération sur la table déclenche le trigger, qui appelle alors la fonction. La suite de la diapo, qui demande de faire un INSERT ou un UPDATE sur la table cible, va dans ce sens.

Exercice 9 Messages à l'insertion d'une partie

Afficher des informations lors de l'insertion d'une partie :

  • premier rôle de méchant : si le joueur n'avait pas d'avatar avec un rôle de méchant jusqu'à maintenant, alors on affichera le message « Le côté obscur de la force, redouter tu dois. » ;
  • première participation à « Cooking Fever » : si le joueur n'avait pas encore d'avatar dans ce jeu, alors on affichera le message « Cuisinez un jour, cuisinez toujours ».
Indice

Le « joueur » est le visiteur propriétaire de l'avatar : il peut avoir plusieurs avatars, et il faut regarder les parties de tous. Un trigger BEFORE INSERT par ligne a l'avantage que la nouvelle partie n'est pas encore dans la table : « jusqu'à maintenant » revient à chercher dans partie telle qu'elle est. PERFORM et FOUND disent si une telle partie existe.

Solution proposée 
CREATE FUNCTION f_messages_partie() RETURNS trigger AS $$
DECLARE
    v_visiteur bigint;
BEGIN
    -- Le « joueur » est le visiteur propriétaire de l'avatar
    SELECT id_visiteur INTO v_visiteur FROM avatar WHERE id_avatar = NEW.id_avatar;

    -- Premier rôle de méchant ?
    IF NEW.role = 'méchant' THEN
        PERFORM * FROM partie p JOIN avatar a ON a.id_avatar = p.id_avatar
        WHERE a.id_visiteur = v_visiteur AND p.role = 'méchant';
        IF NOT FOUND THEN
            RAISE NOTICE 'Le côté obscur de la force, redouter tu dois.';
        END IF;
    END IF;

    -- Première participation à Cooking Fever ?
    IF NEW.id_jeu = (SELECT id_jeu FROM jeu WHERE nom_jeu = 'Cooking Fever') THEN
        PERFORM * FROM partie p JOIN avatar a ON a.id_avatar = p.id_avatar
        WHERE a.id_visiteur = v_visiteur AND p.id_jeu = NEW.id_jeu;
        IF NOT FOUND THEN
            RAISE NOTICE 'Cuisinez un jour, cuisinez toujours';
        END IF;
    END IF;

    RETURN NEW;    -- BEFORE : sans cette ligne, l'insertion serait annulée
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER tr_messages_partie BEFORE INSERT ON partie
    FOR EACH ROW EXECUTE FUNCTION f_messages_partie();

Tests sur les données du script du TP. Sean (avatars 3, 11, 12 et 20) n'a jamais joué de méchant ni à Cooking Fever ; Billy (avatars 4, 5, 13, 14, 21 et 22) a déjà joué des méchants, mais jamais à Cooking Fever (id_jeu = 5) :

INSERT INTO partie VALUES (11, 5, 'méchant', 100);   -- Sean, avatar Eliass
-- NOTICE:  Le côté obscur de la force, redouter tu dois.
-- NOTICE:  Cuisinez un jour, cuisinez toujours
INSERT INTO partie VALUES (20, 2, 'méchant', 50);    -- Sean, avatar Etienne : plus de message
INSERT INTO partie VALUES (13, 5, 'gentil', 300);    -- Billy, avatar Youssef
-- NOTICE:  Cuisinez un jour, cuisinez toujours
INSERT INTO partie VALUES (22, 5, 'gentil', 10);     -- Billy, avatar Choukri : plus de message

-- nettoyage
DELETE FROM partie WHERE (id_avatar, id_jeu) IN ((11, 5), (20, 2), (13, 5), (22, 5));

Les messages dépendent du joueur, pas de l'avatar : le deuxième avatar de Sean ne reçoit plus le message du méchant. Avec un trigger AFTER, la nouvelle ligne serait déjà dans la table, et chaque recherche devrait l'exclure.

Exercice 10 Historique des prix

Créer une table historique_prix, de colonnes id_article, ancien, nouveau, modifie_le et par, et un trigger qui y enregistre chaque changement de prix d'un article, avec la date et l'auteur de la modification. Une mise à jour qui ne change pas le prix ne doit rien enregistrer.

Indice

Un trigger AFTER UPDATE OF prix par ligne ; comparer OLD.prix et NEW.prix ; now() et current_user peuvent servir de valeurs par défaut aux colonnes.

Solution proposée 
CREATE TABLE historique_prix (
    id_article integer,
    ancien     numeric(6,2),
    nouveau    numeric(6,2),
    modifie_le timestamp DEFAULT now(),
    par        text DEFAULT current_user
);

CREATE FUNCTION f_historique_prix() RETURNS trigger AS $$
BEGIN
    IF NEW.prix IS DISTINCT FROM OLD.prix THEN
        INSERT INTO historique_prix (id_article, ancien, nouveau)
        VALUES (OLD.id, OLD.prix, NEW.prix);
    END IF;
    RETURN NULL;   -- trigger AFTER : valeur de retour ignorée
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER tr_historique_prix AFTER UPDATE OF prix ON articles
    FOR EACH ROW EXECUTE FUNCTION f_historique_prix();

UPDATE articles SET prix = prix * 0.9 WHERE categorie = 'Chaussures';   -- 3 changements
UPDATE articles SET nom = 'Jean Levi''s' WHERE id = 1;                  -- prix non touché
UPDATE articles SET prix = prix WHERE id = 2;                           -- prix inchangé
SELECT id_article, ancien, nouveau, par FROM historique_prix;
-- 6 | 30.00 | 27.00 | postgres
-- 7 | 40.00 | 36.00 | postgres
-- 8 | 15.00 | 13.50 | postgres

IS DISTINCT FROM compare en traitant NULL comme une valeur : <> renverrait « inconnu » si l'un des prix était NULL, et le changement ne serait pas enregistré. UPDATE OF prix évite d'appeler la fonction quand la colonne prix n'apparaît pas dans le SET ; le test dans la fonction écarte le cas SET prix = prix.

Exercice 11 Contrôler et compléter un article

Écrire un trigger qui, à l'insertion d'un article, refuse un prix nul, négatif ou absent avec un message clair, et met la date du jour dans date_vente quand elle n'est pas fournie.

Solution proposée 
CREATE FUNCTION f_controle_article() RETURNS trigger AS $$
BEGIN
    IF NEW.prix IS NULL OR NEW.prix <= 0 THEN
        RAISE EXCEPTION 'Prix invalide pour « % » : %', NEW.nom, NEW.prix;
    END IF;
    IF NEW.date_vente IS NULL THEN
        NEW.date_vente := CURRENT_DATE;
    END IF;
    RETURN NEW;       -- la ligne, éventuellement complétée, est insérée
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER tr_controle_article BEFORE INSERT ON articles
    FOR EACH ROW EXECUTE FUNCTION f_controle_article();

INSERT INTO articles (id, nom, categorie, prix, id_vendeur) VALUES (20, 'Bottes pluie', 'Chaussures', 35.00, 6);
SELECT id, nom, date_vente = CURRENT_DATE AS date_du_jour FROM articles WHERE id = 20;   -- 20 | Bottes pluie | t
INSERT INTO articles (id, nom, categorie, prix, id_vendeur) VALUES (21, 'Erreur', 'Chaussures', -3, 6);
-- ERROR:  Prix invalide pour « Erreur » : -3.00

Modifier NEW n'est possible que dans un trigger BEFORE : dans un trigger AFTER, la ligne est déjà écrite.

Vocabulaire

Séquence sequence
Objet qui génère des entiers successifs ; nextval, currval, setval.
SERIAL
Raccourci PostgreSQL : colonne integer dont la valeur par défaut est tirée d'une séquence créée pour elle.
Index index
Structure auxiliaire qui accélère la recherche de lignes, au prix d'une mise à jour à chaque modification.
Rôle role
Entité qui possède des objets et des droits : utilisateur s'il a LOGIN, groupe s'il a des membres.
Super-utilisateur superuser
Rôle pour lequel aucun droit n'est vérifié, comme postgres.
Privilège privilege
Droit d'effectuer une action sur un objet (SELECT, INSERT, USAGE…), accordé par GRANT, retiré par REVOKE.
Liste de contrôle d'accès ACL
Pour chaque objet, la liste des rôles et de leurs privilèges, consultée avant toute action.
PUBLIC
Pseudo-rôle qui désigne tous les rôles.
Expression de table commune CTE
Requête nommée par WITH, utilisable comme une table le temps d'une requête.
CTE récursive
CTE formée d'un terme ancre et d'un terme récursif, répété tant qu'il produit des lignes.
Fonction de fenêtrage window function
Fonction calculée sur une fenêtre de lignes (OVER), sans regrouper : chaque ligne reste.
Partition
Sous-ensemble de lignes défini par PARTITION BY, sur lequel la fonction de fenêtrage est calculée.
Cadre frame
Lignes de la partition prises en compte pour la ligne courante ; par défaut, de la première à la ligne courante quand il y a un ORDER BY.
PL/pgSQL
Langage procédural de PostgreSQL : blocs, variables, conditions, boucles, exceptions.
Bloc
Unité de code PL/pgSQL : DECLARE, BEGIN, EXCEPTION, END.
FOUND
Variable booléenne : la dernière instruction SQL a-t-elle affecté au moins une ligne ?
Trigger trigger
Objet qui appelle une fonction trigger lors d'un INSERT, UPDATE ou DELETE sur une table, avant ou après, par ligne ou par instruction.
NEW, OLD
Dans une fonction trigger par ligne, la nouvelle et l'ancienne version de la ligne.

À retenir

L'essentiel

  • Une séquence fournit des entiers avec nextval ; SERIAL crée une séquence et l'associe à la colonne. SERIAL pour une clé primaire, jamais pour une clé étrangère. Les valeurs peuvent avoir des trous.
  • Un index accélère les recherches sélectives mais ralentit les écritures ; chaque clé primaire en a un automatiquement.
  • Un rôle est un utilisateur s'il a LOGIN, un groupe s'il a des membres ; un nouveau rôle n'a aucun droit sur les tables des autres.
  • GRANT privilège ON objet TO rôle et REVOKE … FROM ; retirer un droit à PUBLIC ne retire pas les droits accordés nommément. Un droit sur un schéma ne donne aucun droit sur ses tables.
  • Une CTE (WITH nom AS (…)) nomme une requête le temps d'une requête : on lit de haut en bas, et on peut en chaîner plusieurs.
  • Une CTE récursive = ancre + UNION [ALL] + terme récursif ; elle s'arrête quand un tour ne renvoie rien, et boucle à l'infini sur un cycle.
  • fonction() OVER (…), avec PARTITION BY et ORDER BY, calcule sur une fenêtre sans perdre de lignes ; ORDER BY dans OVER transforme la somme en cumul.
  • Les fonctions de fenêtrage sont calculées après le WHERE : pour filtrer sur un rang (top-N), on passe par une CTE.
  • PL/pgSQL : blocs DECLARE/BEGIN/EXCEPTION/END, résultat d'une requête dans une variable avec SELECT … INTO, requête sans résultat avec PERFORM, succès testé par FOUND.
  • Un trigger appelle une fonction RETURNS trigger sans argument ; en BEFORE par ligne, renvoyer NULL annule la ligne, renvoyer NEW (éventuellement modifié) la laisse passer ; une exception annule l'opération.

Auto-évaluation

Pourquoi ne faut-il jamais déclarer une clé étrangère en SERIAL ?

Une clé étrangère doit reprendre l'identifiant d'une ligne existante de la table référencée. Une colonne SERIAL génère ses propres valeurs, sans lien avec cette table. On utilise integer (ou bigint face à un bigserial).

Un rôle a USAGE sur le schéma boutique. Peut-il lire boutique.stock ?

Non : il obtient permission denied for table stock. Il lui faut aussi SELECT sur la table. Inversement, SELECT sur la table sans USAGE sur le schéma donne permission denied for schema boutique.

Pourquoi articles NATURAL JOIN vendeurs ne renvoie-t-il aucune ligne ?

La jointure naturelle se fait sur toutes les colonnes de même nom, ici id et nom : il faudrait qu'un article ait le même identifiant et le même nom qu'un vendeur. Le vrai lien, articles.id_vendeur = vendeurs.id, s'écrit avec JOIN … ON.

Quelles sont les deux parties d'une CTE récursive, et quand s'arrête-t-elle ?

Le terme ancre, exécuté une fois, qui initialise la table de travail sans référencer la CTE ; le terme récursif, qui référence la CTE et est répété sur les lignes du tour précédent. Elle s'arrête quand le terme récursif renvoie 0 ligne : jamais s'il y a un cycle dans les données.

Prix 45, 25, 18, 18, 12 triés par ordre décroissant : que donnent ROW_NUMBER, RANK et DENSE_RANK ?

ROW_NUMBER : 1, 2, 3, 4, 5. RANK : 1, 2, 3, 3, 5 (un trou après les ex-aequo). DENSE_RANK : 1, 2, 3, 3, 4.

On calcule RANK() OVER (…) AS rang. Pourquoi ne peut-on pas ajouter WHERE rang <= 2 à la même requête ?

Le WHERE est exécuté avant les fonctions de fenêtrage et avant le SELECT : la colonne rang n'existe pas encore (column "rang" does not exist). On calcule le rang dans une CTE, puis on filtre dans la requête principale.

Dans une fonction PL/pgSQL, SELECT count(*) FROM articles; seul provoque une erreur. Laquelle, et que faire ?

« query has no destination for result data » : le résultat doit aller quelque part. On écrit SELECT count(*) INTO n FROM articles; pour le garder, ou PERFORM count(*) FROM articles; pour l'ignorer (et tester FOUND).

Un trigger BEFORE INSERT par ligne renvoie NULL. Que se passe-t-il ? Et s'il est AFTER ?

En BEFORE, la ligne n'est pas insérée, sans message d'erreur ; les autres lignes de l'instruction le sont. En AFTER, la valeur de retour est ignorée : la ligne est déjà insérée. Pour refuser une opération avec un message, on lève une exception (RAISE EXCEPTION).
