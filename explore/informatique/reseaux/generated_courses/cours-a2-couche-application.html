La couche application

Au sommet de la pile, les protocoles que l'on utilise sans y penser : le web (HTTP), le courrier (SMTP, POP, IMAP), le transfert de fichiers (FTP), le terminal à distance (Telnet). Et trois services qui font marcher tout le reste : ICMP pour les messages d'erreur (ping, traceroute), DNS pour traduire les noms en adresses, DHCP pour donner une adresse aux machines qui arrivent.

Le modèle client-serveur diapos 2–4

Presque toutes les applications réseau suivent le modèle client-serveur : les serveurs hébergent les services (stockage, impression, annuaire, pages web…), les clients s'adressent à eux pour en profiter. Côté pile, l'application échange des données de bout en bout, la couche transport des segments ou datagrammes, la couche Internet des paquets, réseau après réseau.

Remarque Qu'est-ce qu'une RFC ?

Une RFC (Request For Comments) est un document numéroté qui décrit un protocole ou une pratique d'Internet. Les numéros ne sont jamais réutilisés : une nouvelle version d'un protocole reçoit un nouveau numéro, qui « remplace » l'ancien.

Telnet diapos 5–8

Dans les années 1970, l'informatique est centralisée : de gros ordinateurs, auxquels on accède par des terminaux (un écran, un clavier et une liaison série). Il faut pouvoir y accéder à distance, à travers le réseau. Telnet (Teletype Network, RFC 764 en 1980, puis RFC 854 ; options dans les RFC 855 à 866) est l'application qui le permet : c'est un terminal virtuel.

Le client Telnet ouvre une connexion TCP vers le port 23 du serveur ; tout ce que l'utilisateur tape est envoyé au serveur, qui renvoie ce qu'il affiche (diapo 8).

Attention Tout passe en clair Ajout

Telnet ne chiffre rien, pas même le mot de passe. On le remplace aujourd'hui par SSH (port 22), qui offre le même service avec chiffrement. Telnet reste utile en TP pour administrer un équipement Cisco à distance (lignes vty, annexe A1), ou pour « parler » à la main à un serveur texte (SMTP, HTTP).

Le courrier électronique diapos 9–12 et 24–29

Le courrier utilise deux familles de protocoles :

  • SMTP (Simple Mail Transfer Protocol) pour transférer les messages vers la boîte du destinataire ;
  • POP (Post Office Protocol) ou IMAP (Internet Message Access Protocol) pour que le destinataire récupère ses messages.
SigleNomRôle
MUAMail User AgentLe logiciel de messagerie de l'utilisateur (Thunderbird, Outlook…).
MTAMail Transfer AgentLe serveur qui relaie le courrier vers le domaine destinataire.
MDAMail Delivery AgentLe programme qui dépose le message dans la boîte aux lettres.

Exemple Le trajet d'un courriel (diapo 11)

  1. Le MUA de expediteur@ccna.fr remet le message en SMTP au MTA de son domaine.
  2. Ce MTA demande au DNS le serveur de messagerie (enregistrement MX) du domaine cisco.com.
  3. Il transmet le message en SMTP, éventuellement via d'autres MTA, jusqu'au MTA de cisco.com.
  4. Le MDA le range dans la boîte de destinataire@cisco.com.
  5. Le MUA du destinataire demande « ai-je reçu du courrier ? » en POP ou IMAP…
  6. … et récupère le message.

SMTP

Proposé en 1982 (RFC 821), SMTP transporte les messages, en client-serveur, sur TCP port 25. Chaque requête est une ligne de texte terminée par CRLF :

CommandeRôle
HELO <domaine>Ouvre la session ; le client donne son nom de domaine complet (FQDN).
MAIL FROM:<adresse>Adresse de l'émetteur, qui recevra les éventuels messages d'erreur.
RCPT TO:<adresse>Adresse d'un destinataire (une commande par destinataire).
DATAEnvoie l'en-tête et le corps du message, terminés par une ligne contenant un seul point.
QUITTermine la session.

La diapo date de 1990 les RFC 2554 (authentification) et 2476 : elles sont de 1999 et 1998. La RFC 5321 (2008) n'est pas « le courrier mobile » mais la version actuelle de SMTP, qui remplace la RFC 821.

POP3

POP3 (RFC 1939, TCP port 110), très répandu, sert à relever définitivement les messages : le client se connecte, les messages sont transférés vers lui et, en général, supprimés du serveur. Le client s'authentifie, par défaut avec un mot de passe en clair, sinon sous TLS/SSL.

CommandeRôle

PASSMot de passe (en clair).
STATNombre de messages dans la boîte.
RETR nTransfère le message n.
DELE nMarque le message n pour suppression.
QUITFin de session (les suppressions sont alors appliquées).

IMAP4

IMAP4 (RFC 3501, qui remplace la RFC 2060 ; TCP port 143) est plus complet que POP. Les messages restent sur le serveur ; le client s'y connecte pour les consulter, en mode connecté ou déconnecté (les courriers récupérés pendant la connexion restent alors en cache). On peut ainsi lire son courrier depuis plusieurs machines et logiciels, avec les mêmes dossiers partout.

Ses commandes (diapo 29) : AUTHENTICATE, LOGIN, LOGOUT ; CREATE, DELETE, RENAME pour les boîtes ; SELECT, EXAMINE pour en ouvrir une ; LIST, LSUB, STATUS ; EXPUNGE, CLOSE pour détruire les messages marqués ; SEARCH ; FETCH pour récupérer un message ; COPY ; CAPABILITY ; NOOP.

ICMP, ping et traceroute diapos 13–23

Définition ICMP

ICMP (Internet Control Message Protocol, RFC 792) transporte des messages de contrôle et d'erreur qui renseignent sur l'état du réseau. Il est associé à la couche réseau : ses messages voyagent directement dans des paquets IP, sans TCP ni UDP.

IP ne vérifie pas que ses paquets arrivent. Quand une passerelle ne peut pas router ou livrer un paquet, ou qu'un événement anormal survient (hôte injoignable), il faut prévenir l'émetteur : ICMP est ce mécanisme de signalement des erreurs au niveau IP.

Format

Un message ICMP commence par trois champs :

  • Type (8 bits) : la nature du message ;
  • Code (8 bits) : précise le type ;
  • Somme de contrôle (16 bits) : même calcul que pour IP, mais portant sur le seul message ICMP (celle de l'en-tête IP ne couvre que l'en-tête, pas les données).
TypeNomQuand
8Echo requestUne machine teste si un destinataire est joignable (ping).
0Echo replyToute machine qui reçoit un echo request doit y répondre.
3Destination unreachableUne passerelle ne peut pas livrer le paquet. Code 0 : réseau injoignable ; 1 : hôte injoignable ; 2 : protocole injoignable ; 3 : port injoignable ; 4 : fragmentation nécessaire mais interdite (DF) ; 5 : échec du routage par la source.
11Time exceededUn routeur a ramené le TTL à 0 : il détruit le paquet et prévient l'émetteur.

On y lit : l'adresse obtenue par le DNS ; pour chaque réponse, son numéro (icmp_seq), le TTL restant à l'arrivée et le temps aller-retour ; enfin le taux de perte et les temps minimal, moyen et maximal. Les 64 octets reçus sont les 56 octets de données plus 8 octets d'en-tête ICMP.

traceroute

traceroute (ou tracepath, tracert sous Windows) affiche les routeurs traversés jusqu'à une destination. Il s'appuie sur le TTL : chaque routeur le décrémente, et celui qui le ramène à 0 détruit le paquet et renvoie un message ICMP time exceeded à l'expéditeur, révélant ainsi son adresse.

Méthode Comment traceroute découvre le chemin Ajout

  1. Envoyer un paquet avec TTL = 1 : le premier routeur le détruit et répond ; on connaît le saut 1.
  2. Recommencer avec TTL = 2, 3… : chaque fois, le routeur suivant se dévoile.
  3. Quand le paquet atteint la destination, celle-ci répond autrement (echo reply, ou ICMP port unreachable si l'on a visé un port UDP fermé) : c'est la fin.
  4. Un routeur qui ne répond pas apparaît comme no reply ou *.

Attention « Paquet ICMP (type 30) » À vérifier

La diapo 23 attribue la trace à des paquets ICMP de type 30. Ce type (traceroute, RFC 1393) est expérimental et abandonné. En pratique, traceroute sous Linux envoie des datagrammes UDP, tracert sous Windows des echo request ; dans les deux cas, ce sont les réponses time exceeded (type 11) qui dessinent le chemin.

Sur la trace de la diapo 23, depuis une box (192.168.1.1), on voit le réseau du fournisseur d'accès, puis RENATER (le réseau de la recherche : Paris, Poitiers, Nantes), puis le pare-feu de l'université, au 18e saut. La mention asymm signale que le retour ne prend pas le même nombre de sauts que l'aller.

HTTP diapos 30–40

Le World Wide Web est une application qui fait coopérer un ensemble de serveurs pour fournir des documents typés, écrits en HTML et reliés par des liens (hypertexte). HTTP (HyperText Transfer Protocol) est le protocole qui les échange, en client-serveur, sur TCP (port 80 ; 443 pour HTTPS).

  • Contenus statiques : HTML, texte, images, son, envoyés tels quels.
  • Contenus dynamiques côté serveur (SSI, CGI, PHP… produits à chaque requête) ou côté client (JavaScript, autrefois applets Java et ActiveX).

Les versions

  • HTTP/1.0 (RFC 1945, mai 1996) : méthodes GET, HEAD, POST.
  • HTTP/1.1 (RFC 2616, juin 1999) : ajoute notamment OPTIONS, TRACE, PUT et DELETE (ces deux dernières souvent désactivées sur les serveurs) ; la connexion TCP peut servir à plusieurs requêtes.
  • HTTP/2 : approuvé le 18 février 2015 (publié en RFC 7540 en mai 2015).

URI et URL

Un URI est une chaîne qui identifie de manière unique une ressource sur Internet. En HTTP, on parle d'URL (Uniform Resource Locator), qui dit aussi où la trouver : http://<serveur>:<port>/<chemin>/<ressource>, le port (80 par défaut) et la ressource pouvant être omis.

La requête

Le navigateur envoie au serveur un ensemble de lignes :

  1. une ligne de commande : méthode, URI, version du protocole ;
  2. des champs d'en-tête (nom: valeur), facultatifs ;
  3. une ligne vide, puis éventuellement un corps (les données d'un POST).

FTP diapos 41–54

FTP (File Transfer Protocol) date de 1971 et est défini aujourd'hui par la RFC 959 (1985), complétée par des extensions de sécurité (RFC 2228), d'internationalisation (RFC 2640) et d'autres (RFC 3659). La diapo 42 cite la « RFC 141 » comme première version À vérifier : la frise et l'historique donnent la RFC 114 (avril 1971).

Ses objectifs : partager des fichiers entre machines distantes, indépendamment de leurs systèmes de fichiers, et transférer les données efficacement.

Définition Deux canaux

FTP ouvre deux connexions TCP : un canal de commande (contrôle), vers le port 21 du serveur, qui reste ouvert toute la session ; et un canal de données, ouvert pour chaque transfert (fichier ou liste de fichiers). Côté serveur, le canal de données part du port 20 en mode actif.

Mode actif et mode passif

  • Actif : le client annonce sur le canal de commande un port à lui (PORT) ; c'est le serveur qui ouvre la connexion de données, depuis son port 20.
  • Passif : le client demande PASV ; le serveur ouvre un port (ici 3267) et l'annonce ; c'est le client qui ouvre la connexion de données.

Astuce Pourquoi le mode passif est le plus utilisé

Derrière un NAT ou un pare-feu, une connexion qui vient de l'extérieur vers le client est bloquée : le mode actif échoue (voir le cours 8). En mode passif, le client ouvre lui-même les deux connexions, ce qui passe.

DNS diapos 55–85

Pourquoi un annuaire

Les machines s'identifient par des adresses IP (192.168.1.36), pénibles à retenir ; les humains préfèrent des noms (www.univ-lemans.fr). Il faut donc un service qui fasse la correspondance entre nom et adresse.

Au début d'Internet, c'était un fichier unique, /etc/hosts, qui listait toutes les machines ; chacun devait le télécharger. Cela marchait avec quelques centaines d'ordinateurs, plus avec des millions (3 100 hôtes en 1986, 137 000 en 1990, plus de 4 millions en 1995) : diffusion lente, correspondance figée, noms en double. Le fichier existe toujours, pour quelques entrées locales :

127.0.0.1         localhost
255.255.255.255   broadcasthost
::1               localhost
192.168.10.250    toto.home.lan

Définition DNS

Le DNS (Domain Name System, RFC 1034 et 1035) est un système de nommage hiérarchique qui identifie des ressources (hôtes, boîtes aux lettres, services) : l'annuaire d'Internet. C'est une base de données distribuée : l'espace des noms est un arbre, découpé logiquement (indépendamment de l'emplacement physique) en zones dont chacune est gérée par son propriétaire. On y accède en client-serveur ; la réplication assure la fiabilité, les caches la rapidité.

L'arborescence des noms

  • Le nom de domaine identifie une entité dont les machines sont reliées à Internet. Ses éléments sont séparés par des points, comme les répertoires par des / dans un chemin.
  • Sur un réseau local, une machine a un nom court (commande hostname) ; sur Internet, on lui ajoute son domaine : la machine www du domaine afnic.fr devient www.afnic.fr.
  • Un sous-domaine est un nœud intermédiaire (ni racine, ni feuille) : impots sous gouv sous fr. Un hôte est une feuille, à laquelle on associe une ou plusieurs adresses IP.
  • Les zones se juxtaposent pour former la base globale ; chacune en porte un fragment.

Attention Nom de domaine et URL

Un nom de domaine n'est qu'une partie d'une URL. Pour le domaine abcd.fr : http://www.abcd.fr, http://www.tot3.abcd.fr/doc et http://abcd.fr/info/pub/prod.htm sont des ressources web de machines du domaine et du sous-domaine tot3.abcd.fr ; root@abcd.fr et info@www.abcd.fr sont des boîtes aux lettres.

Domaines de premier niveau et registres

Les TLD (Top-Level Domains) sont juste sous la racine (RFC 1591). On distingue les TLD nationaux (ccTLD : .fr, .de) et génériques (gTLD : .com, .org). Leur gestion a été confiée à l'IANA jusqu'en 1998, à l'ICANN depuis.

Les enregistrements de ressources

Le DNS a trois composants : les enregistrements de ressources (l'information portée par chaque nœud), les serveurs de noms (un ou plusieurs par zone, pour la redondance) et les résolveurs (qui interrogent les serveurs pour le compte des applications).

  • Avec deux MX (priorités 10 et 50), on essaie d'abord mchenry ; lists sert de secours.

Complément Deux autres types courants Ajout

AAAA associe un nom à une adresse IPv6 ; PTR fait la résolution inverse (adresse → nom), dans le domaine spécial in-addr.arpa : c'est grâce à lui que tracepath affiche des noms de routeurs. La commande nslookup (ou dig) interroge le DNS à la main : nslookup -type=MX univ-lemans.fr.

Le transport des messages DNS

  • En UDP, port serveur 53 : sans connexion, rapide ; les messages sont limités à 512 octets.
  • En TCP, port 53 aussi : quand la réponse dépasse 512 octets (et pour les transferts de zone entre serveurs).

La résolution : récursive ou itérative

Mode récursif

Le client envoie sa requête au serveur DNS, qui lui renvoie une réponse complète : la correspondance cherchée ou une erreur. Si le nom n'est ni dans son cache ni dans une zone dont il a l'autorité, c'est le serveur qui interroge les autres serveurs.

Mode itératif

Le serveur renvoie la réponse s'il fait autorité, sinon une réponse partielle : l'adresse d'un autre serveur, plus proche du nom. Le client relance sa requête vers ce serveur, et descend ainsi l'arbre niveau par niveau.

Exemple Résoudre www.eni.fr (diapo 83)

  1. Le navigateur demande www.eni.fr au résolveur de son fournisseur d'accès (requête récursive).
  2. Le résolveur ne l'a pas en cache. Il demande à un serveur racine, qui répond : « pour fr, voir les serveurs de l'AFNIC ».
  3. Il demande au serveur de fr, qui répond : « pour eni.fr, voir dns.eni.fr ».
  4. Il demande à dns.eni.fr, qui fait autorité et répond : 81.80.245.20. Les étapes 2 à 4 sont itératives.
  5. Le résolveur garde la réponse en cache et la transmet au navigateur.

Les serveurs racine

  • Ils connaissent les serveurs de tous les domaines de premier niveau : sans eux, plus d'Internet. En 2002, une attaque par déni de service en a rendu 7 sur 13 inopérants.
  • Il en existe 13 logiques, nommés de A à M, dupliqués sur toute la planète grâce à l'anycast : une même adresse IP est donnée à plusieurs serveurs physiques, et le routage mène au plus proche. La diapo cite 46 instances du serveur F, toutes à l'adresse 192.5.5.241 (il y en a bien plus aujourd'hui).

DHCP diapos 86–94

Sur un grand réseau, ou quand les utilisateurs changent souvent (portables de passage, nouveaux postes), attribuer une adresse IP à chaque machine à la main n'est pas tenable. DHCP (Dynamic Host Configuration Protocol) les attribue automatiquement.

Définition Groupe et bail

Le serveur DHCP choisit l'adresse dans une plage configurée, le groupe (pool), et l'attribue temporairement, pour une durée appelée bail. Les adresses qui ne servent plus retournent automatiquement dans le groupe.

  1. Demande de bail (DHCPDISCOVER) : en arrivant sur le réseau, le client, qui n'a pas encore d'adresse, diffuse une demande : IP source 0.0.0.0, destination 255.255.255.255 ; MAC source la sienne, destination FF:FF:FF:FF:FF:FF. Sans réponse au bout d'une seconde, il recommence.
  2. Offre de bail (DHCPOFFER) : chaque serveur qui reçoit la demande propose une offre, avec l'adresse MAC du client, une adresse IP, un masque, la durée du bail (pendant laquelle l'adresse ne sera donnée à personne d'autre) et sa propre adresse.
  3. Sélection (DHCPREQUEST) : le client retient une offre, en général la première, et l'annonce par diffusion, en nommant le serveur choisi. Celui-ci sait que son offre est retenue ; les autres retirent la leur.
  4. Accusé de réception (DHCPACK) : le serveur choisi confirme, en ajoutant souvent d'autres paramètres (passerelle par défaut, serveurs DNS…).

La capture de la diapo 90 montre le premier message : Src: 0.0.0.0, Dst: 255.255.255.255, Src Port: bootpc (68), Dst Port: bootps (67), ce qui rappelle que DHCP descend de BOOTP.

Complément Renouveler le bail, et le relais Ajout

À la moitié du bail, le client demande au serveur de le prolonger (DHCPREQUEST adressé directement au serveur, sans diffusion). Comme les diffusions ne traversent pas les routeurs, un serveur DHCP placé sur un autre réseau ne voit pas les DHCPDISCOVER : il faut configurer le routeur en relais DHCP (commande ip helper-address sous IOS), qui transmet les demandes au serveur en unicast.

Exercice 2 Lire une trace

Un ping affiche ttl=49. Sachant que la machine distante émet avec un TTL initial de 64, combien de routeurs le paquet a-t-il traversés ? Et pourquoi un traceroute vers la même machine peut-il trouver un autre nombre ?

Solution proposée

\(64 - 49 = 15\) routeurs sur le chemin du retour (la réponse est un paquet émis par la machine distante). traceroute mesure le chemin aller ; les deux peuvent différer (routage asymétrique, mention asymm de tracepath).

Exercice 3 Requête HTTP

Écrire la requête HTTP/1.1 minimale pour obtenir http://www.exemple.fr:8080/cours/index.html. Quelle réponse obtient-on si la page n'a pas changé depuis la date donnée dans If-Modified-Since ? si elle n'existe pas ?

Solution proposée 
GET /cours/index.html HTTP/1.1
Host: www.exemple.fr:8080

La connexion TCP part vers le port 8080. L'en-tête Host est obligatoire en HTTP/1.1 (plusieurs sites peuvent partager une adresse IP) ; la ligne vide termine la requête. Page inchangée : 304 Not Modified, sans corps. Page absente : 404 Not Found.

Exercice 4 Lire une zone

Une zone contient : exemple.fr. IN MX 10 mx1.exemple.fr., exemple.fr. IN MX 20 mx2.exemple.fr., www IN CNAME serveur1, serveur1 IN A 192.0.2.10, mx1 IN A 192.0.2.25. Où est livré un courriel pour contact@exemple.fr ? Quelle adresse obtient un navigateur pour www.exemple.fr ?

Solution proposée

Le courriel est livré à mx1.exemple.fr (priorité 10, la plus forte), donc à 192.0.2.25 ; mx2 sert de secours. www.exemple.fr est un alias de serveur1.exemple.fr, dont l'enregistrement A donne 192.0.2.10.

Exercice 5 DHCP

(a) Pourquoi le DHCPDISCOVER part-il de l'adresse 0.0.0.0 et vers 255.255.255.255 ? (b) Pourquoi le DHCPREQUEST est-il diffusé alors que le client connaît déjà le serveur ? (c) Deux serveurs DHCP répondent ; que devient l'offre non retenue ?

Solution proposée

(a) Le client n'a pas encore d'adresse et ne connaît pas celle du serveur : il diffuse. (b) Pour que tous les serveurs qui ont fait une offre apprennent laquelle a été retenue. (c) Le serveur non choisi retire son offre : l'adresse proposée retourne dans son groupe.

À retenir

L'essentiel

  • Telnet (TCP 23) : terminal virtuel, tout en clair ; remplacé par SSH (22).
  • Courrier : SMTP (TCP 25) transfère, du MUA aux MTA ; POP3 (110) relève et télécharge ; IMAP (143) consulte en laissant les messages sur le serveur. Commandes SMTP : HELO, MAIL FROM, RCPT TO, DATA, QUIT.
  • ICMP (couche réseau) : messages d'erreur et de contrôle (type, code, somme de contrôle). Echo request 8 / reply 0 (ping), destination unreachable 3, time exceeded 11 (traceroute, qui joue sur le TTL).
  • HTTP (TCP 80) : requête = méthode + URI + version, en-têtes, ligne vide, corps. Méthodes GET, HEAD, POST, PUT, DELETE… Codes 200, 301, 302, 304, 404, 500.
  • FTP : canal de commande TCP 21, canal de données séparé. Actif : le serveur ouvre la connexion de données (depuis 20). Passif : le client l'ouvre (PASV), ce qui passe les NAT.
  • DNS : base distribuée et hiérarchique (racine, TLD, domaines, hôtes). Enregistrements A, CNAME, MX, NS, SOA. UDP 53 (TCP au-delà de 512 octets). Résolution récursive (le serveur fait tout) ou itérative (le client descend l'arbre). 13 serveurs racine logiques, en anycast.
  • DHCP (UDP 67/68) : adresse prêtée pour un bail, prise dans un groupe. Discover, Offer, Request, Ack ; les deux messages du client sont diffusés.

Auto-évaluation

Quel protocole envoie un courriel ? lesquels permettent de le lire ?

SMTP pour l'envoi et le transfert ; POP3 ou IMAP pour la lecture.

Quelle est la principale différence entre POP3 et IMAP ?

POP3 télécharge les messages sur le client (et les supprime du serveur) ; IMAP les laisse sur le serveur, consultables depuis plusieurs appareils.

Quel message ICMP renvoie un routeur qui ramène le TTL à 0 ?

Time exceeded (type 11).

Que signifie le code HTTP 304 ?

Not Modified : le document n'a pas changé depuis la date indiquée par le client, qui peut garder sa copie.

En FTP passif, qui ouvre la connexion de données ?

Le client, vers un port que le serveur lui a indiqué en réponse à PASV.

À quoi sert un enregistrement MX ?

À indiquer les serveurs de courrier (SMTP) d'un domaine, avec leur priorité.

Combien y a-t-il de serveurs racine logiques ?

13, nommés de A à M, chacun dupliqué en de nombreuses instances par anycast.

Quels sont les quatre messages DHCP, dans l'ordre ?

DHCPDISCOVER, DHCPOFFER, DHCPREQUEST, DHCPACK.
