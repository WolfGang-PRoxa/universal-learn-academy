Communiquer entre processus : les tubes

Après fork, le père et le fils ne partagent plus leurs variables. Pour échanger des données, ils ont besoin d'un canal fourni par le système. Ce cours présente les formes de communication entre processus, puis le tube, mécanisme caractéristique d'Unix : un flot à sens unique créé par pipe, et ce qui se passe quand il est vide, plein, ou qu'il n'a plus de lecteur. Il se termine par les tubes nommés, qui font communiquer des processus sans ancêtre commun.

Les formes de communication notes CM 5

Deux processus peuvent avoir besoin d'échanger des données. On classe ces communications selon l'endroit où ils se trouvent, et selon la forme que prennent les données.

Processus locaux
Ils s'exécutent sur la même machine, et communiquent par un mécanisme du système.
Processus distants
Ils s'exécutent sur des machines différentes, et communiquent par le réseau.
Communication par flot
Une communication continue : les octets arrivent les uns à la suite des autres, sans découpage.
Communication par paquet
Les données circulent par messages séparés.

Ajout Un flot ne garde pas la trace des écritures : deux write de 10 octets peuvent être lus par un seul read de 20 octets. Celui qui lit doit donc savoir où s'arrêtent les données.

Les tubes poly., p. 1–3 · notes CM 5

Le tube (pipe) est le mécanisme de communication caractéristique d'Unix : un moyen de communication par flot entre processus locaux. On peut le voir comme une file (first in, first out) : les octets en sortent dans l'ordre où ils y sont entrés. Il est unidirectionnel : les données y vont dans un seul sens. Et il ne permet pas la rémanence de l'information : ce qui y transite n'est pas conservé.

Un tube est implémenté comme un fichier, à ceci près qu'il n'a pas de nom. Il n'est donc possible qu'entre des processus ayant un ancêtre commun. Les tubes nommés, vus à la fin du cours, lèvent cette limite.

La primitive pipe poly., p. 1–2 · CM 5

Définition pipe

#include <unistd.h>

int pipe(int p[2]);

pipe crée un fichier temporaire et anonyme, avec deux descripteurs ouverts : p[0], par lequel on lit, et p[1], par lequel on écrit. On s'en sert avec les opérations classiques, read et write par exemple.

pipe renvoie 0, ou −1 en cas d'échec.

Ce fichier n'ayant pas de nom, un autre processus ne peut pas l'ouvrir avec open. Mais le fils est une copie conforme du père : si le père crée le tube avant fork, le fils en hérite, avec les mêmes descripteurs aux extrémités du tube. Le père et le fils peuvent alors s'échanger des informations par ce tube.

Un tube entre un père et un fils poly., p. 2–3 · CM 5

Après fork, chacun possède les deux descripteurs, et chacun ferme celui dont il ne se sert pas. Ici, le père écrit et le fils lit.

Exemple Le père filtre les minuscules pour son fils poly., p. 2–3

Le père lit son entrée standard et n'envoie dans le tube que les lettres minuscules. Le fils les lit dans le tube et les affiche.

#include <stdio.h>
#include <unistd.h>    /* pipe , fork , close , read , write */
#include <stdlib.h>    /* exit */
#include <sys/types.h> /* fork , wait */
#include <sys/wait.h>  /* wait */

int
main()
{
  int tube[2] ; /* tube de communication */
  char c ;

  /*-----*/

  if( pipe( tube ) )
    {
      perror("pb sur creation du tube");
      exit(-1);
    }

  switch( fork() )
    {
    case -1: /* erreur */
      {
        perror("pb fork");
        exit(-2);
      }
    case 0 : /* fils = recoit les lettres minuscules */
      {

        /* le fils n'ecrit pas dans le tube */
        close(tube[1]) ;
        /* de plus cela permet d'atteindre la fin du tube */

        /* lecture dans le tube */
        while( read( tube[0] , &c , 1 ))
          write( 1 , &c ,1 );

        printf("\n") ;
        exit(0);
      }
    default : /* pere = filtre les minuscules pour le fils */
      {
        int cr ;

        /* le pere ne lit pas dans le tube */
        close(tube[0]);

        while( (c=getchar()) != EOF )
          {
            if( (c<='z') && (c>='a') )
              {
                /* Ecriture dans le tube */
                write(tube[1] , &c , 1 ) ;
              }
          }
        /* Fermeture du tube en ecriture */
        /* (pour que le fils atteigne la fin du tube) */
        close( tube[1] );

        /* Attente fin du fils */
        wait(&cr);
      }
    }
  exit( 0 );
}
$ echo "Bonjour 123 tout le Monde" | ./minuscules
onjourtoutleonde

Comme le dit le commentaire du programme, fermer tube[1] n'est pas une simple précaution : c'est ce qui permet au fils d'atteindre la fin du tube. La suite du cours explique pourquoi.

Attention Deux tests à ne pas reprendre tels quels Ajout

Ce programme marche sur du texte ordinaire, mais deux de ses tests sont fragiles. Les deux essais ci-dessous ont été faits sur ce programme.

  • char c et EOF. getchar renvoie un int, pour que EOF se distingue de tous les octets. Rangé dans un char, ce résultat perd cette garantie : avec printf 'ab\377cd' en entrée, l'octet 0xFF est pris pour EOF, et le programme n'affiche que ab. Compilé avec -funsigned-char, comme là où char n'est pas signé, il ne s'arrête plus du tout. Il faut garder le résultat de getchar dans un int, et le copier dans un char pour write.
  • while (read(…)). Cette boucle ne s'arrête que sur 0. En cas d'erreur, read renvoie −1 : la condition reste vraie et la boucle ne se termine pas, comme on l'a vérifié sur un descripteur fermé. Le test sûr est while (read(…) > 0).

Tube vide, tube plein, tube sans lecteur poly., p. 1–2 · notes CM 5

Le système garde les octets écrits dans le tube jusqu'à ce qu'on les lise, et la taille du tube est limitée. Trois cas particuliers se présentent.

Les cas particuliers d'un tube

tube videle lecteur doit attendre
tube pleinl'écrivain est suspendu
écriture sans lecteursituation insoluble : interruption par SIGPIPE

Remarque Pas besoin que le tube soit plein

Les notes écrivent « file pleine sans lecteur ». La condition du polycopié est plus large : il suffit que le tube soit fermé en lecture par tous les processus qui l'utilisent, et qu'un processus tente d'y écrire. Il reçoit alors SIGPIPE, qui l'interrompt s'il n'est pas capturé. Dans le programme ci-dessous, le tube est vide, et c'est le tout premier octet qui déclenche le signal.

Exemple Écrire sans lecteur Ajout

/* sans_lecteur.c : écrire dans un tube que plus personne ne lit */
#include <stdio.h>
#include <stdlib.h>
#include <errno.h>
#include <string.h>
#include <signal.h>
#include <unistd.h>

int main(int argc, char *argv[])
{
    int tube[2];

    pipe(tube);
    close(tube[0]);                   /* plus aucun lecteur */
    if (argc > 1)
        signal(SIGPIPE, SIG_IGN);     /* on ignore le signal */
    printf("avant write\n");
    fflush(stdout);
    int n = write(tube[1], "x", 1);
    printf("write renvoie %d (%s)\n", n, strerror(errno));
    return 0;
}
$ ./sans_lecteur
avant write
$ echo $?
141
$ ./sans_lecteur x
avant write
write renvoie -1 (Broken pipe)

Le traitement par défaut de SIGPIPE est la terminaison : le processus s'arrête dans write, et le shell rapporte \(141 = 128 + 13\), 13 étant le numéro de SIGPIPE sous Linux. Si le signal est ignoré ou capté, write renvoie −1, avec errno à EPIPE.

Ajout Sous Linux, un tube garde 65 536 octets : un programme qui écrit octet par octet sans bloquer en écrit 65 536 avant d'obtenir EAGAIN. Cette valeur dépend du système, et un programme ne doit pas compter dessus.

Exercice 1 yes | head -1 Ajout

La commande yes écrit y sans fin. Pourquoi yes | head -1 se termine-t-il, alors que yes n'a aucune raison de s'arrêter ?

Solution proposée

head se termine après une ligne, et ferme ainsi le seul descripteur de lecture du tube. Le write suivant de yes déclenche SIGPIPE, qui le termine. Le shell donne le code de chaque commande :

$ yes | head -1
y
$ echo ${PIPESTATUS[*]}
141 0

Détecter la fin de la communication poly., p. 2 · notes CM 5

Un fichier a une fin, et read renvoie 0 quand on l'atteint. Un tube, lui, peut être vide sans que la communication soit terminée : l'écrivain n'a peut-être simplement pas encore écrit.

Propriété Fin de lecture

read renvoie 0 lorsque la fin de fichier est atteinte, c'est-à-dire si le tube est vide et si tous les processus qui l'utilisent l'ont fermé en écriture.

La seule façon de placer une fin de fichier dans un tube est donc de le fermer en écriture dans tous ces processus.

Remarque Ce que disent les notes

Les notes disent que le retour 0 de read « fonctionne dans un fichier, mais pas pour un pipe ». Il faut le comprendre ainsi : un tube vide ne suffit pas à conclure. Sur un tube vide qui a encore un écrivain, read ne renvoie pas 0, il attend. Il renvoie 0 exactement dans le cas de la vraie fin, et la boucle de lecture du fils fonctionne donc sur un tube comme sur un fichier.

Attention Un close oublié, et le programme ne finit jamais Ajout

La fin de lecture demande que tous les descripteurs d'écriture soient fermés, y compris celui du lecteur lui-même, reçu par fork. S'il l'oublie, il attend un écrivain qui n'est autre que lui :

/* sans_close.c : le fils a gardé son descripteur d'écriture */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
    int tube[2];
    char c;

    pipe(tube);
    if (fork() == 0) {
        /* close(tube[1]) oublié */
        while (read(tube[0], &c, 1) > 0)
            putchar(c);
        printf("fils : fin de lecture\n");
        exit(0);
    }
    close(tube[0]);
    write(tube[1], "ok\n", 3);
    close(tube[1]);
    wait(NULL);
    printf("pere : fin\n");
    return 0;
}

À l'exécution, le fils affiche ok, puis reste bloqué dans read, et le père dans wait : le programme ne se termine pas, et il a fallu l'arrêter. Avec close(tube[1]); dans le fils, il se termine.

Exercice 2 Un dialogue Ajout

Un tube va dans un seul sens. Écrire un programme où le père envoie à son fils les entiers 1, 2 et 3 ; le fils lui renvoie le double de chacun, et le père affiche les réponses. Le fils s'arrête quand le père a fini.

Indice

Il faut deux tubes. Comment le fils sait-il que le père a fini ?

Solution proposée 
/* deux_tubes.c : le fils renvoie au père le double de ce qu'il reçoit */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
    int aller[2], retour[2];
    int x;

    pipe(aller);
    pipe(retour);
    if (fork() == 0) {                       /* fils */
        close(aller[1]);
        close(retour[0]);
        while (read(aller[0], &x, sizeof x) == sizeof x) {
            x = 2 * x;
            write(retour[1], &x, sizeof x);
        }
        exit(0);
    }
    close(aller[0]);                         /* père */
    close(retour[1]);
    for (int i = 1; i <= 3; i++) {
        write(aller[1], &i, sizeof i);
        read(retour[0], &x, sizeof x);
        printf("%d -> %d\n", i, x);
    }
    close(aller[1]);                         /* le fils voit la fin de fichier */
    wait(NULL);
    return 0;
}
$ ./deux_tubes
1 -> 2
2 -> 4
3 -> 6

Chaque processus ferme les deux descripteurs qui ne le concernent pas. Le père ferme aller[1] pour finir : read renvoie alors 0 dans le fils, qui sort de sa boucle.

Complément Ce que fait le shell pour ls | wc -l

Le polycopié et les notes s'arrêtent à read et write. Avec dup2 et exec, un tube relie deux programmes qui n'en savent rien : dup2(tube[1], 1) fait du tube la sortie standard. Le programme lancé écrit sur sa sortie standard comme d'habitude, car les descripteurs traversent exec.

/* ls_wc.c : ce que fait le shell pour ls | wc -l */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
    int tube[2];

    pipe(tube);
    if (fork() == 0) {                 /* premier fils : ls */
        close(tube[0]);
        dup2(tube[1], 1);              /* sa sortie standard devient le tube */
        close(tube[1]);
        execlp("ls", "ls", (char *) NULL);
        perror("execlp ls");
        exit(127);
    }
    if (fork() == 0) {                 /* second fils : wc */
        close(tube[1]);
        dup2(tube[0], 0);              /* son entrée standard devient le tube */
        close(tube[0]);
        execlp("wc", "wc", "-l", (char *) NULL);
        perror("execlp wc");
        exit(127);
    }
    close(tube[0]);                    /* sinon wc n'aurait jamais la fin de fichier */
    close(tube[1]);
    wait(NULL);
    wait(NULL);
    return 0;
}
$ ls
a  b  c
$ ../ls_wc
3

Le père doit lui aussi fermer ses deux descripteurs : sinon, wc attendrait pour toujours la fin de fichier. Les deux fils ne sont pas père et fils l'un de l'autre, mais ils ont un ancêtre commun, et cela suffit à un tube ordinaire.

Les tubes nommés poly., p. 1, 3–6

Les tubes nommés allient les propriétés des tubes et celles des fichiers. Comme un fichier, un tube nommé a un nom : tous les processus locaux à la machine qui connaissent ce nom peuvent l'utiliser, sans ancêtre commun. Comme un tube, il est de taille limitée, les lectures et les écritures s'y font en mode file, les informations lues sont obligatoirement extraites, et les opérations de type seek sont interdites.

Créer un tube nommé poly., p. 4

Définition mknod

#include <sys/stat.h>

int mknod(const char *reference, mode_t mode, dev_t droits);

mknod crée un i-nœud pour le fichier de nom reference. Sa fonction générale est de créer des catalogues et des fichiers spéciaux ou ordinaires, et n'importe quel processus peut s'en servir pour créer un tube nommé.

mode précise le type et les droits d'accès : S_IFIFO pour un tube nommé, et les droits des trois classes d'usagers (user, group, others). Par exemple, S_IFIFO | 0666 crée un tube nommé accessible en lecture et en écriture par tous.

Remarque Trois écarts avec Linux

À vérifier Ce qui précède reprend le polycopié. Sur trois points, l'exécution sous Linux donne autre chose.

  • Le troisième paramètre. Le polycopié le nomme droits, alors que les droits sont dans mode. C'est un numéro de périphérique, appelé dev dans le manuel, qui ne sert pas pour un tube : les exemples y mettent 0. Avec mknod("t", S_IFIFO | 0600, 0777), on obtient prw-------.
  • « Accessible par tous ». Les droits demandés sont réduits par le masque de création du processus (umask). Avec le masque usuel 022, S_IFIFO | 0666 donne prw-r--r-- : le groupe et les autres peuvent seulement lire. Il faut un masque à 0 pour obtenir prw-rw-rw-.
  • L'usager ordinaire. D'après le polycopié, il ne peut créer que des tubes nommés avec mknod. Sous Linux, il peut aussi créer des fichiers ordinaires et des sockets. Les catalogues et les périphériques lui sont refusés (EPERM).

Ajout La commande mkfifo nom, et la fonction mkfifo(nom, 0666) de sys/stat.h, créent aussi un tube nommé, sans qu'on ait à préciser le type. ls -l l'affiche avec le type p.

Ouvrir un tube nommé poly., p. 4

Tout processus qui veut communiquer par un tube nommé doit connaître son nom. Il l'ouvre par open, en lecture ou en écriture selon l'opération qu'il doit faire.

Propriété Chaque ouverture attend l'autre extrémité

  • Un processus qui ouvre un tube nommé en lecture est suspendu jusqu'à ce qu'un processus l'ouvre en écriture.
  • Un processus qui l'ouvre en écriture est suspendu jusqu'à ce qu'un processus l'ouvre en lecture.

Ajout Une fois ouvert, il se comporte comme un tube ordinaire. read renvoie 0 quand tous les écrivains l'ont fermé, et écrire alors que tous les lecteurs l'ont fermé déclenche SIGPIPE, ou EPIPE si le signal est ignoré. lseek y renvoie −1 avec ESPIPE. Ces trois résultats ont été vérifiés à l'exécution.

Un exemple en trois programmes poly., p. 4–6

Exemple Communication entre deux processus indépendants poly., p. 4–6

Le premier programme crée le tube nommé. Le deuxième y écrit les minuscules de son entrée standard, comme le père du programme minuscules.c. Le troisième les lit et les affiche. Chacun reçoit le nom du tube en argument.

#include <stdio.h>
#include <stdlib.h>   /* exit */
#include <sys/stat.h> /* mknod */

int
main( int nb_arg , char * tab_arg[])
{
  if( nb_arg != 2 )
    {
      fprintf( stderr , "%s - Creation d'un tube nomme\n\n" , tab_arg[0] );
      fprintf( stderr , "usage : %s <nom du tube nomme>\n" , tab_arg[0] );
      exit(-1);
    }

  if( mknod( tab_arg[1] , S_IFIFO | 0666 , 0 ) )
    {
      perror("Pb sur creation du tube nomme");
      exit(-2);
    }

  printf("Creation du tube %s reussie\n" , tab_arg[1] );

  exit(0);
}
#include <stdio.h>
#include <unistd.h>    /* close , read , write */
#include <stdlib.h>    /* exit */
#include <sys/types.h> /* open */
#include <sys/stat.h>
#include <fcntl.h>

int
main( int nb_arg , char * tab_arg[])
{
  char c ;
  int fd_tube ;

  /*-----*/

  if( nb_arg != 2 )
    {
      fprintf( stderr , "%s - Ecriture d'un tube nomme\n\n" , tab_arg[0] );
      fprintf( stderr , "usage : %s <nom du tube nomme>\n" , tab_arg[0] );
      exit(-1);
    }

  /* Ouverture du tube en ecriture */
  if( (fd_tube=open( tab_arg[1] , O_WRONLY , 0 )) == -1 )
    {
      perror( "Pb sur ouverture du tube nomme en ecriture" );
      exit(-2) ;
    }

  /* Filtrage des minuscules */
  while( (c=getchar()) != EOF )
    {
      if( (c<='z') && (c>='a') )
        {
          /* Ecriture dans le tube */
          write( fd_tube , &c , 1 ) ;
        }
    }

  if( c == EOF )
    {
      fprintf( stdout , "Fin de Fichier --> fermeture du tube\n");
    }

  /* Fermeture du tube */
  close( fd_tube );

  exit( 0 );
}
#include <stdio.h>
#include <unistd.h>    /* close , read , write */
#include <stdlib.h>    /* exit */
#include <sys/types.h> /* open */
#include <sys/stat.h>
#include <fcntl.h>

int
main( int nb_arg , char * tab_arg[])
{
  char c ;
  int fd_tube ;

  /*-----*/

  if( nb_arg != 2 )
    {
      fprintf( stderr , "%s - Lecture d'un tube nomme\n\n" , tab_arg[0] );
      fprintf( stderr , "usage : %s <nom du tube nomme>\n" , tab_arg[0] );
      exit(-1);
    }

  /* Ouverture du tube en lecture */
  if( (fd_tube=open( tab_arg[1] , O_RDONLY , 0 )) == -1 )
    {
      perror( "Pb sur ouverture du tube nomme en lecture" );
      exit(-2) ;
    }

  /* Lecture dans le tube */
  while( read( fd_tube , &c , 1 ) )
    write( 1 , &c ,1 );

  printf("\n");

  /* Fermeture du tube */
  close( fd_tube );

  exit( 0 );
}

On crée le tube une fois :

$ ./creer_tube montube
Creation du tube montube reussie
$ ls -l montube
prw-r--r-- 1 piaur piaur 0 Oct 31 18:16 montube

Dans un premier terminal, le lecteur reste suspendu dans open. Il se débloque quand l'écrivain est lancé dans un second terminal :

$ ./lire_tube montube
onjourtoutleonde
$ echo "Bonjour 123 tout le Monde" | ./ecrire_tube montube
Fin de Fichier --> fermeture du tube

Les deux programmes finis, le tube reste dans le catalogue, avec une taille de 0. Une seconde création échoue, et il faut le supprimer comme un fichier :

$ ./creer_tube montube
Pb sur creation du tube nomme: File exists
$ rm montube

Les deux remarques sur char c et sur while (read(…)) valent aussi pour ces programmes.

Ajout Le nom persiste, mais pas les données : c'est l'absence de rémanence annoncée au début du cours. À l'essai, deux octets écrits puis jamais lus ont disparu une fois le dernier descripteur fermé : rouvert, le tube est vide.

Exercice 3 Un tube nommé dans le shell Ajout

Dans un catalogue qui contient les fichiers a, b et c, on tape mkfifo tube, puis ls > tube. La commande ne rend pas la main. Pourquoi ? Que fait wc -l < tube, tapé dans un autre terminal, et quel nombre affiche-t-il ?

Solution proposée

Pour la redirection, le shell ouvre tube en écriture avant de lancer ls. Faute de lecteur, cette ouverture est suspendue, et ls n'a même pas démarré.

wc -l < tube ouvre le tube en lecture, ce qui débloque les deux ouvertures. ls écrit alors sa liste et se termine, wc voit la fin de fichier et affiche 4 : les fichiers a, b et c, et tube lui-même.

À retenir

L'essentiel

  • Une communication est locale ou distante, par flot ou par paquet ; le tube est un flot local.
  • Un tube est unidirectionnel : pipe(tube) donne tube[0] en lecture et tube[1] en écriture.
  • C'est une file, sans rémanence de l'information, et sa taille est limitée.
  • Il n'a pas de nom : on le crée avant fork, et le fils en hérite. Il faut donc un ancêtre commun.
  • Chaque processus ferme le descripteur dont il ne se sert pas.
  • Tube vide : le lecteur attend. Tube plein : l'écrivain attend.
  • Écrire sans lecteur déclenche SIGPIPE, ou EPIPE si le signal est ignoré ou capté.
  • read renvoie 0 quand le tube est vide et que tous les processus l'ont fermé en écriture : c'est la seule façon de placer une fin de fichier.
  • Pour dialoguer dans les deux sens, il faut deux tubes.
  • Un tube nommé se crée par mknod avec S_IFIFO, et relie tous les processus locaux qui connaissent son nom.
  • Il s'ouvre par open : l'ouverture en lecture attend un écrivain, et l'ouverture en écriture attend un lecteur.
  • Lire extrait les données, seek est interdit, et seul le nom reste quand tout est fermé.

Auto-évaluation

Pourquoi crée-t-on le tube avant fork ?

Parce que le tube n'a pas de nom : on ne peut pas l'ouvrir ensuite. fork copie les descripteurs, et le père et le fils partagent ainsi le même tube.

Lequel de tube[0] et tube[1] sert à écrire ?

tube[1]. tube[0] sert à lire : comme l'entrée standard (0) et la sortie standard (1).

Un lecteur appelle read sur un tube vide, qui a encore un écrivain. Que se passe-t-il ?

Il attend : read ne renvoie pas 0, car la communication n'est pas terminée.

Le fils lit jusqu'à la fin, mais le programme ne se termine pas. Quelle est la cause la plus probable ?

Un descripteur d'écriture est resté ouvert, souvent dans le fils lui-même : la fin de lecture n'arrive jamais.

Que se passe-t-il si un processus écrit dans un tube dont tous les lecteurs ont fermé ?

Il reçoit SIGPIPE, qui le termine par défaut. Si le signal est ignoré ou capté, write renvoie −1 avec EPIPE.

Deux processus veulent dialoguer. Un seul tube suffit-il ?

Non : un processus pourrait lire ce qu'il vient d'écrire lui-même. On utilise deux tubes, un par sens.

Deux processus sans ancêtre commun veulent communiquer. Que choisir ?

Un tube nommé : un tube ordinaire n'est accessible que par héritage, alors qu'un tube nommé s'ouvre par son nom.

Un processus ouvre un tube nommé en lecture, et personne ne l'a ouvert en écriture. Que se passe-t-il ?

Il reste suspendu dans open jusqu'à ce qu'un processus l'ouvre en écriture. C'est symétrique pour l'ouverture en écriture.

Où met-on les droits d'accès dans mknod ?

Dans mode, avec le type : S_IFIFO | 0666. Ils sont ensuite réduits par le masque umask du processus.

Tous les processus ont fermé un tube nommé. Que reste-t-il ?

Son nom dans le catalogue, mais aucune donnée. Il faut le supprimer avec rm pour pouvoir le recréer.
