Compiler un TP en C sous Windows et sous Linux

Les TP de C se font sous Linux à la fac et sous Windows à la maison. Un programme en C standard se compile des deux côtés avec les mêmes Makefile ; un programme POSIX (processus, verrous, signaux, threads) demande un vrai Linux, que Windows fournit avec WSL. Cette page fait le point sur ce qui est installé sur le PC, sur ce qui manque, et donne les commandes de chaque système.

Objectifs

  • Savoir si un TP est en C standard ou en C POSIX, et donc où il se compile.
  • Compiler et lancer un TP avec run.bat (Windows) ou run.sh (Linux), ou à la main avec make.
  • Installer gcc et make dans WSL, et y ouvrir le dossier du Drive.
  • Reconnaître les erreurs d'environnement les plus fréquentes, et les corriger.

Prérequis

  • Ouvrir un terminal : cmd ou PowerShell sous Windows, bash sous Linux.
  • Compiler un fichier C avec gcc ; savoir à quoi sert un Makefile.

Deux familles de programmes C

Avant de compiler, il faut savoir de quelle bibliothèque dépend le programme : c'est elle, et non le langage, qui décide des systèmes où il fonctionne.

C standard
Le programme n'utilise que la bibliothèque de la norme ISO : stdio.h, stdlib.h, string.h, math.h… Il se compile sur tout système qui a un compilateur C. Ce sont les TP de codage.
C POSIX
Le programme appelle aussi les services d'un système Unix : processus (fork, wait), verrous (fcntl), signaux (sigaction, kill), threads et sémaphores (pthread.h, semaphore.h), files de messages (sys/msg.h). Ce sont les TD et TP de programmation système.

MinGW produit des programmes Windows natifs : il n'offre que ce que Windows sait faire. Sur le PC, sys/wait.h, pthread.h, semaphore.h et sys/msg.h sont absents. unistd.h, fcntl.h et signal.h existent, mais sans struct flock, F_SETLKW ni SIGQUIT, et fork n'est pas déclaré : l'édition de liens échoue sur undefined reference to `fork'. WSL, au contraire, fait tourner un vrai noyau Linux : un programme s'y comporte comme sur les machines de la fac.

Attention Un programme juste sous Windows peut se tromper sous Linux

Le gcc de MinGW compile pour Windows 32 bits, alors que Linux, à la fac comme dans WSL, travaille en 64 bits. Mesuré sur le PC le 30 septembre : int fait 4 octets des deux côtés, mais long, les pointeurs et size_t font 4 octets avec MinGW et 8 sous Linux. Un calcul qui déborde un long sous Windows passe sous Linux, un pointeur rangé dans un int est tronqué sous Linux, un format printf qui convient d'un côté provoque un avertissement de l'autre. Avant de rendre un TP, on le compile et on le lance à la fac, ou dans WSL.

Compiler un TP en C standard

Les TP de codage suivent tous la même organisation : un Makefile principal, trois fichiers inclus, et deux lanceurs qui compilent puis exécutent. Les mêmes fichiers servent sous Windows et sous Linux.

L'organisation d'un dossier de TP

Makefile
Les cibles : all compile tout, clean efface les fichiers produits.
Makefile.dir
Le seul endroit où l'on déclare les dossiers du projet : build_dir, puis les dossiers des modules à mesure qu'ils sont créés.
Makefile.compilation
Le compilateur et ses options : -Wall -g -D_DEBUG_ tant que DEBUG=yes.
Makefile.depend
Les dépendances entre dossiers : un Makefile ne compile que les fichiers de son dossier, et demande les autres .o au Makefile de leur dossier.
build/
Les fichiers objets et l'exécutable, recréés par make all et effacés par make clean.
run.bat, run.sh
Les lanceurs, pour Windows et pour Linux : ils compilent tout, puis lancent l'exécutable.

Sous Windows : run.bat

Dans l'Explorateur, taper cmd dans la barre d'adresse du dossier du TP ouvre un terminal au bon endroit ; on y lance run.bat. Un double-clic sur run.bat marche aussi, mais la fenêtre se ferme dès la fin du programme, avant qu'on ait pu lire ses messages.

cd /d "C:\Users\piaur\prog\ula\romain\L3\Codage\TP\TP2"
run.bat

Le lanceur fait, dans l'ordre :

  1. il se place dans le dossier du TP, d'où qu'on le lance ;
  2. il ajoute C:\Program Files\Git\usr\bin au PATH si sh.exe est introuvable : les recettes des Makefile emploient mkdir -p et rm -rf, et sans sh, mingw32-make les confie à cmd, qui ne les comprend pas ;
  3. il prend make s'il existe, sinon mingw32-make ;
  4. il passe la console en UTF-8 (chcp 65001), pour les accents ;
  5. il compile avec make all, s'arrête si la compilation échoue, puis lance build\<programme>.exe.

Sous Linux : run.sh

À la fac, dans un terminal ouvert dans le dossier du TP :

$ ./run.sh
mkdir -p ./build
gcc -c -Wall -g -D_DEBUG_ -Wno-misleading-indentation generateur.c -o ./build/generateur.o -I./
gcc  ./build/generateur.o -Wall -g -D_DEBUG_ -Wno-misleading-indentation -o ./build/generateur -lm

make affiche chaque commande qu'il lance, puis vient la sortie du programme. run.sh fonctionne aussi sous Windows, dans Git Bash : il y trouve mingw32-make tout seul.

Sans lanceur

Les lanceurs ne font que deux commandes, que l'on peut taper soi-même : compiler, puis lancer. make clean efface build/, pour tout recompiler.

set PATH=%PATH%;C:\Program Files\Git\usr\bin
mingw32-make all
build\generateur.exe
mingw32-make clean
$ make all
$ ./build/generateur
$ make clean

Pour un fichier isolé, sans Makefile : gcc -Wall -g -o prog prog.c, puis ./prog sous Linux ou prog.exe sous Windows.

Compiler un programme POSIX sous Windows : WSL

WSL (Windows Subsystem for Linux) fait tourner Ubuntu à côté de Windows. On y retrouve les commandes de la fac, à condition d'installer les outils une fois, et de monter le lecteur du Drive à chaque démarrage.

Installer gcc, make et gdb (une fois)

La commande wsl, tapée dans un terminal Windows, ouvre le shell d'Ubuntu. On y installe le paquet build-essential (gcc, make et les en-têtes de la bibliothèque C), et gdb :

$ sudo apt update
$ sudo apt install build-essential gdb
$ gcc --version

Le TP Transports affiche son écran avec ncurses : il lui faut aussi sudo apt install libncurses-dev.

sudo demande le mot de passe choisi à l'installation d'Ubuntu, celui de l'utilisateur piaur.

Astuce Mot de passe oublié

Depuis un terminal Windows, wsl -u root ouvre une session d'administrateur sans mot de passe : wsl -u root passwd piaur en définit un nouveau.

Ouvrir le dossier studies

Depuis le 12 novembre 2026, ula (ex-studies) est sur le disque C: (C:\Users\piaur\prog\ula), que WSL voit sous /mnt/c sans rien faire :

$ cd "/mnt/c/Users/piaur/prog/ula/romain/L3/SE_PS/TP"

Un dossier sur un autre lecteur, comme l'ancien G: de Google Drive, doit d'abord être monté :

$ sudo mkdir -p /mnt/g
$ sudo mount -t drvfs G: /mnt/g

Le montage a été essayé sur le PC le 30 septembre : le dossier studies s'y lit normalement. Il ne survit pas à un redémarrage de WSL : on le refait à chaque fois. Le run.bat du TP Route fait ce montage lui-même, sans mot de passe (wsl -u root), avant de lancer run.sh dans WSL.

Compiler et lancer

Dans le dossier du TP, on procède exactement comme à la fac : ./run.sh, ou make all puis l'exécutable. Les fichiers sont ceux du PC : ce que l'on modifie sous Windows se retrouve dans WSL, et inversement.

À retenir

L'essentiel

  • Un TP en C standard (codage) se compile sous Windows avec MinGW comme sous Linux, avec les mêmes Makefile : run.bat d'un côté, run.sh de l'autre.
  • Un programme POSIX (processus, verrous, signaux, threads, files de messages) ne se compile pas avec MinGW : sous Windows, il passe par WSL.
  • Sur le PC, make s'appelle mingw32-make, et le sh de Git for Windows n'est pas dans le PATH : run.bat règle les deux.
  • MinGW compile en 32 bits : long et pointeurs font 4 octets, contre 8 sous Linux. On vérifie un TP à la fac, ou dans WSL, avant de le rendre.
  • Dans un WSL neuf, gcc et make s'installent une fois pour toutes : sudo apt install build-essential gdb libncurses-dev. C'est fait sur ce PC.
  • WSL ne voit pas un autre lecteur que C: (l'ancien G: du Drive, par exemple) : sudo mount -t drvfs G: /mnt/g, à chaque démarrage.
  • Un run.sh en CRLF ne tourne pas sous Linux : sed -i 's/\r$//' run.sh.

Auto-évaluation

Un TP utilise fork et wait. Peut-on le compiler avec le gcc de MinGW ?

Non : sys/wait.h n'existe pas dans MinGW, et fork n'y est pas défini. On le compile dans WSL, ou sur les machines Linux de la fac.

Pourquoi run.bat ajoute-t-il C:\Program Files\Git\usr\bin au PATH ?

Pour que mingw32-make trouve sh.exe. Sans lui, make exécute les recettes avec cmd, qui ne comprend ni mkdir -p ni rm -rf.

Un programme affiche sizeof(long) : 4 sous Windows, 8 à la fac. Pourquoi ?

Le gcc de MinGW produit des programmes Windows 32 bits ; Linux travaille en 64 bits, où long et les pointeurs font 8 octets. C'est pourquoi on vérifie un TP sous Linux avant de le rendre.

Dans WSL, ./run.sh répond /bin/bash^M: bad interpreter. Que s'est-il passé ?

Le script a des fins de ligne Windows (CRLF) : Linux lit l'interpréteur /bin/bash suivi d'un retour chariot, qui n'existe pas. sed -i 's/\r$//' run.sh remet des fins de ligne Unix.

Où se trouve C:\Users\piaur\prog\ula dans WSL ?

Dans /mnt/c/Users/piaur/prog/ula : WSL voit le disque C: sous /mnt/c. Un autre lecteur (l'ancien G: du Drive, par exemple) n'y apparaît qu'une fois monté avec sudo mount -t drvfs G: /mnt/g.
